# 把大白话升级成可引用的专业框架（升级层）

> 这篇是"升级层"。底层那两篇学习文（前端 e2e、企业级架构）是让你**想清楚**用的，全是大白话。
> 这篇是让你**讲得专业**用的——给每个大白话配一个有出处、能引用的行业术语，并补几个真正专业的框架。
> 用法：永远先用大白话把道理讲懂，再甩一个专业名字"锚定"。**别堆术语**——堆术语是新手才干的事，资深的人是"大白话讲透 + 一个精准术语收口"。

## 第 0 段 · 先学会一件最专业的事：源头甄别

在用这些文章之前，先把它们分三档。**一个资深的人读行业文章会做这件事，新手会把营销数字当事实复述、然后被追问当场穿帮。**

**第一档·可信、能引用、含金量最高：**
- **Birgitta Böckeler《Harness Engineering for Coding Agent Users》**（Thoughtworks 杰出工程师，发布在 Martin Fowler 网站，2026-04-02）。这是本篇绝大多数框架的来源，有控制论根基、不吹数字、还自己列了一堆"尚未解决的问题"——这正是可信的标志。
- **LangChain《The Anatomy of an Agent Harness》**：`Agent = Model + Harness` 这个公式出自这里。
- **Thoughtworks Technology Radar：Architectural Fitness Function**（架构适应性函数）。
- **OpenAI《Harness engineering: leveraging Codex》**：Codex 的一线工程实践。

**第二档·框架可用，但数字和出处必须丢掉：**
- `核心定义`篇的"三代范式（Prompt→Context→Harness）""三层架构""六大组件"，`skill+cli`篇的 **ICCR、风险分级表、熵管理、公私分离**——这些是好用的脑图，可以讲。
- 但同篇里的**"Mitchell Hashimoto 正式命名""OpenAI 官方实验报告验证""执行成功率 90%+""Token 成本降 80%""准确率提升 40%""迭代速度 10 倍"**——这些是营销话术，你自己的知识地图早标了"查无实据"。**框架拿来用，数字一个都别往嘴里搬。**

**第三档·已被证伪、当反面教材：**
- `AI Agent Harness Engineering 技术白皮书.md`：92% 数字、OpenHarness、`check_permission` 空壳那套，绝大部分是虚构的。它的用处只有一个——当你想讲"怎么识别一篇 AI 营销软文"时拿它举例。

> **面试金句**：被问"你怎么看 harness 这个概念现在很火"——你可以答："概念是真的，`Agent = Model + Harness` 是 LangChain 提的、Thoughtworks 的 Birgitta 给了最扎实的框架；但市面上一堆白皮书把它包装成有'92% 成功率'的成熟产品，这些数字基本查无实据。我更信 Birgitta 那篇——因为它老实列了一堆还没解决的问题。" 这一答，立刻把你和"读了篇软文就来面试的人"区分开。

## 第 1 段 · 最值钱的一组对照：客观内核/主观残留 = Computational / Inferential

这是整篇最该记住的一组。我们前端文档里反复说的"**每段的对＝客观内核＋主观残留**"，业界有正式的、可引用的名字：

> **Computational（计算型/确定性）vs Inferential（推理型/语义判断型）。** 出自 Birgitta 那篇。

- **Computational**：能用程序确定性判的——类型检查、ESLint、单元测试、AST 结构检查、依赖图分析、覆盖率。特点：快、便宜、可重复、结果非黑即白。**＝我们说的"客观内核、交给代码判"。**
- **Inferential**：只能靠模型/人做语义判断的——需求有没有理解错、是不是过度设计、根因分析合不合理、测试是不是在迎合实现、修复有没有掩盖真问题。特点：理解力强，但贵、慢、不稳定。**＝我们说的"主观残留、才上模型判"。**

而 Birgitta 给的核心原则，和我们说的"能代码判的绝不用模型判"**一字不差是同一句**：

> "能通过确定性规则判断的问题，不要优先交给另一个 LLM 判断。"（例：判'Controller 有没有直接依赖 Repository'，用 AST 或依赖图比让 Review Agent 读代码更便宜更稳。）

**怎么用**：你讲前端测试拆"对"的时候，先用大白话讲"客观内核+主观残留"，然后收一句："这在业界就是 Birgitta 说的 Computational 和 Inferential 之分——能 Computational 判的绝不交给 Inferential。" 面试官立刻知道你不是自己瞎琢磨，是站在行业框架上的。

## 第 2 段 · Guides vs Sensors：把你做过的事，归进控制论的两个格子

Birgitta 把整个 harness 切成两半，用的是**控制论**的词（这是这篇显得专业的根）：

```
Harness
├── Guides：行动前的引导  →  前馈控制 (Feedforward Control)
└── Sensors：行动后的检测  →  反馈控制 (Feedback Control)
```

- **Guides（前馈）**：在 agent 动手之前给方向，降低它走错的概率。包括项目规则、架构原则、**SDD/Spec**、API 文档、示例代码、脚手架、Skills、Codemod。
  - 关键洞察：**最有效的 Guide 往往不是自然语言，而是程序结构**——一个强类型接口、一个只能按正确方式调用的内部 SDK、一个固定目录结构，比写一段文字要求更难被忽略。
  - **对到你身上**：你给自愈 agent 挂的那份"组件库定位知识包"，就是一个 Guide；而且是推理型 Guide。如果哪天你把它做成"只能按正确方式定位的封装"，它就升级成了更强的程序型 Guide。
- **Sensors（反馈）**：agent 动完之后观察结果、把问题喂回去。包括类型检查、测试、Playwright、覆盖率、架构依赖检查、AI Code Review、运行时监控。
  - 关键洞察：**好的 Sensor 不只说"错了"，要输出可操作信息**——把"违规位置 + 正确做法"一起返回，因为这段报错本身就是 agent 下一轮的修复上下文。
  - **对到你身上**：你那道 swc 防作弊闸门、沙箱重跑、唯一性检查，全是 Sensors，而且是 Computational Sensors。

为什么必须两个都有（Birgitta 的原话逻辑）：只有 Guides 不知道它到底做到没有；只有 Sensors 就是 agent 不停犯错、不停返工。**两个合起来才是闭环：Guide 降低出错概率 → Sensor 抓住剩下的错 → 反馈让 agent 修 → 错误经验再反哺 Guide。**

> **怎么用**：被问"你的 harness 都包含什么"，别列一堆零件，先分两类："我把它分成行动前的 Guides 和行动后的 Sensors——这是 Birgitta 借控制论的前馈/反馈分法。我的组件库知识包是 Guide，swc 闸门和沙箱重跑是 Sensor。" 一句话就有了骨架。

## 第 3 段 · Steering Loop：你"作弊未遂做成陷阱题"的专业名字

你最得意的那个实践——**抓到 agent 把断言删了作弊，不是单纯骂它一顿，而是做成一道陷阱题永久入库、并把'只许改定位'做成提交前的强制闸门**——这件事 Birgitta 有个正式名字：**Steering Loop（操舵循环）**。

它的定义是：

```
Agent 犯错
  → 人去分析"为什么现有的 Harness 没拦住它"
  → 调整 Guide 或 Sensor
  → 以后同类错误更少发生
```

核心是人的角色转变：

> 从"每次告诉 agent：你这里又错了"，变成"**为什么我的系统允许这种错误重复发生？**"

Birgitta 直接点出这和 **SRE、平台工程、质量工程**是同一个思想：**不只修这一次故障，还要修产生故障的系统条件。** 

> **怎么用**：这是你拉开"会修脚本的人"和"懂系统的人"的最强一击。讲完作弊那个故事，收一句："这其实就是 Birgitta 说的 Steering Loop，和 SRE 的思路一样——我没有满足于改好这一次，而是去问'为什么我的闸门当初没拦住它'，然后把那条规矩从软提示升级成提交前的确定性校验。修的是系统条件，不是单个 case。" 这句话的份量，比你讲十遍自愈细节都重。

## 第 4 段 · 三种 Harness：你的前端 agent 是最难那种（Behaviour Harness）

Birgitta 按"系统想维持什么状态"把 harness 分三种，难度递增。**这是给你的项目定位用的**：

1. **Maintainability Harness（可维护性）**：管代码内部质量——重复代码、圈复杂度、超大文件、循环依赖、死代码、架构漂移。最容易建，因为传统工具一大堆（ESLint/SonarQube/Semgrep/ArchUnit）。但它**证明不了"软件做对了"**。
2. **Architecture Fitness Harness（架构适应性）**：持续保持架构特征——"UI 层不能访问数据库""跨模块只能走公开接口""核心接口延迟不超阈值"。把"好架构"变成能自动跑的验证条件（见下一段）。
3. **Behaviour Harness（行为）**：Birgitta 认为**最难**的一类，回答"软件最终是否真按业务需要运行"——用户真能登录吗、退款金额对吗、租户数据隔离吗。

**你的前端 e2e 测试 agent，本质就是一个 Behaviour Harness——三种里最难的那种。** 这个定位本身就值钱：你不是在做"可维护性检查"那种谁都能做的事，你在啃业界公认最难、最不成熟的一块。

而 Behaviour Harness 难在哪，Birgitta 的诊断和你的实践**完全咬合**：

> 常见做法是"给 agent 需求 → 它写代码 → 它顺手写测试 → 测试过了 → 认为对了"。**问题是：代码和测试可能同时误解了需求。** 比如需求是"普通用户不能删已发布的应用"，agent 理解成"不能删任何应用"，实现和测试一致、全绿，但业务是错的。

Birgitta 给的解法叫 **Approved Fixtures（人预先批准的固定输入与预期输出）**：**由人预先批准关键输入和预期输出，避免实现 agent 同时掌握'写代码'和'判定对错'两个权力。**

**这就是你的 gold set + "裁判≠被考模型" + 防作弊闸门的专业出处。** 你做的"标准答案从 git 历史白拿、人类标注 gold set、自愈不许碰断言"——全都是在防"同一个 agent 既当运动员又当裁判"。

> **怎么用**：被问"你这套和普通自动化测试有什么不一样"——答："普通自动化测试是 Maintainability 那一层，谁都能搭。我做的是 Birgitta 三类里最难的 Behaviour Harness——验证业务真的对。它最大的坑是'代码和测试同时理解错需求'，所以我必须让判定标准独立于实现：标准答案从历史白拿、断言锁死不许 AI 碰、主观判定用独立 gold set 校准。这就是 Approved Fixtures 的思路。"

## 第 5 段 · Architecture Fitness Function：把"好架构"变成能跑的代码

这个概念（Thoughtworks 提出，可引用）是企业级那篇文档的专业支撑。一句话：

> **架构不能只活在 PPT 和架构师脑子里，要尽量变成能持续自动执行的验证条件。**

例子：
```ts
expect(controllerDependencies).not.toContain("repository");
```
或者一条能跑的命令：`pnpm test:architecture` / `pnpm test:tenant-isolation`。

它能管的不只是代码结构，还有性能、安全、弹性、可观测性、数据隔离。

**怎么对到企业级文档**：我们说"控制面把审批/权限做成执行前强制生效、不靠提示词"——这背后的通用思想就是 Architecture Fitness Function：**把规范从'文档里的要求'变成'流水线里过不去的硬规则'。** 你讲企业级约束时，可以收一句"这就是 Thoughtworks 说的架构适应性函数——架构特征要可执行、可持续验证，而不是写在 wiki 上等人遵守。"

## 第 6 段 · 企业级"为什么要限制架构种类"：Harnessability + Ashby 必要多样性定律

这一段是给你企业级文档**加理论深度**用的，回答一个高级问题："企业为什么要逼大家用统一的'黄金路径'，而不是让各团队自由发挥？"

Birgitta 给了三个递进的概念：

- **Harnessability（可驾驭性）**：不同代码库被 harness 管理的难易程度天差地别。强类型、清晰分层、统一目录、完整测试的项目天然好管（TypeScript 项目白送一个类型检查 Sensor）；而隐式全局变量、动态依赖、无测试、知识全在人脑里的老项目，**最需要 harness，却最难建**。
- **Ambient Affordances（环境给的便利）**：不用每次都告诉 agent，**项目结构本身就在引导它走对路线**。比如固定的分层结构，让"Controller→Service→Repository"可以被自动检查。
- **Ashby 必要多样性定律（Law of Requisite Variety，控制论）**：**一个控制系统要管住一个复杂系统，它自己的状态空间必须能覆盖对方的可能状态。** 推论很硬：如果你允许 agent 想生成什么架构就生成什么架构，harness 永远穷尽不了所有情况、永远管不住；**但如果企业先把架构收敛成少数几种标准拓扑（黄金路径 / Harness Template），控制难度立刻断崖式下降。**

> **怎么用**：被问"企业为什么要搞统一脚手架/黄金路径，不是限制创新吗"——答："这不是管理偏好，是控制论的硬约束。Ashby 必要多样性定律说，控制系统的多样性必须匹配被控对象的多样性。你让 AI 自由生成任意架构，你的 harness 就永远覆盖不全、管不住；把架构收敛成几种标准拓扑，可驾驭性（Harnessability）才上得去。所以企业级的黄金路径，本质是用'限制解空间'换'可治理'。" 这一答的理论密度，足够让面试官重新评估你。

## 第 7 段 · 企业级治理词汇表（框架可用，数字别引）

下面这些来自第二档文章（`核心定义`/`skill+cli`）。**框架是好用的脑图，但出处偏营销、数字别搬。** 挑能让你企业级叙事更顺的几个：

- **ICCR 四原则**：**I**nform（精准上下文按需注入）· **C**onstrain（架构规则代码化）· **C**ontrol（工具与环境最小权限）· **R**eflect（自动化反馈闭环）。好记、好用，可以当企业级 harness 的设计 checklist。注意：别说"这是 OpenAI 官方验证的黄金法则"——那个出处查无实据，就说"一个常见的设计原则归纳"。
- **风险分级管控**：低风险（只读）自动执行 / 中风险（写文件）记日志可自动 / 高风险（push、改数据）人工确认 / 极高风险（删数据、改系统配置）禁止自动接入。**这张表直接能用**，和我们 OpsPilot 的 risk_gate、读写路径治理完全咬合。
- **熵管理（Entropy Management）**：定期清理冗余/过期/低使用率的 Skills 和工具。这一条 Birgitta 也独立提过（Harness 自身需要版本管理、一致性检查、废弃机制）——所以它**两个来源都支持，可以放心讲**。它对应企业级那篇"防腐烂"的具体动作。
- **公私分离**：通用能力做成公共库、部门专属做成私有库。对应"控制面统一、数据面各异"。
- **成本归因**：按部门/项目/任务统计调用量和 token，成本可追溯。对应"模型网关唯一入口 + 用量可算"。

## 第 8 段 · 如何评价 harness 本身好不好（这组指标让你显得想得比对方深）

Birgitta 老实承认这是个**尚未解决的开放问题**，但他列出了候选指标。**你主动把这个"开放问题"讲出来，本身就是高阶信号**——说明你不只会搭，还在想"怎么知道我搭的这套到底有没有用"。

他指出一个反直觉的陷阱：

> 如果一个 Sensor 从来不报错，可能是代码质量极好，**也可能是这个 Sensor 根本没有检测能力**（空壳）。

这正是我们前端文档里"覆盖率能被空壳测试刷满"的同一个病——所以测试可以用**变异测试（Mutation Testing）**来验"测试本身有没有用"，而 harness 整体目前还缺这种成熟指标。他列的候选：

- Harness 覆盖率
- **错误拦截率**（拦住了多少本该拦的）
- **误报率 / 漏报率**（＝我们前端文档的 Precision/Recall）
- **自修复成功率**（＝你的自愈 83%）
- **人工升级率**（多少最终还是转人了）
- **单任务验证成本**（验证一次烧多少钱/多少时间）

> **怎么用**：被问"你怎么知道你这套 harness 是有效的、不是自我感觉良好"——答："这其实是 Birgitta 那篇都承认还没解决的开放问题。我的做法是借测试圈的成熟指标：用变异测试防 Sensor 变空壳，用误报率/漏报率（就是 Precision/Recall）+ 自修复成功率 + 人工升级率 + 单任务验证成本这一组向量来看，绝不揉成一个总分。" 这一答把你从"做了个工具"抬到"在度量这个工具"的层次。

## 第 10 段 · 一条铁律：怎么用这些术语而不翻车

**先大白话讲透，再甩一个术语收口。** 顺序反了就翻车——上来一连串 Computational、Feedforward、Requisite Variety，面试官只会觉得你在背词、且怀疑你没真懂。

模板（套任何一组）：
> "（大白话讲清这件事是什么、为什么这么做、我踩过什么坑）……这个在业界就是 X 说的 **〔术语〕**。"

反例（别这么干）：
> "我用了 Guides 和 Sensors 构成前馈反馈闭环，Computational Sensor 做确定性校验，配合 Steering Loop 实现 Ambient Affordances……"——这是在念词，不是在讲懂。

**术语是用来"锚定"你已经讲懂的东西、让对方知道你站在行业框架上的，不是用来代替讲懂的。** 你最大的本钱永远是前端那些真趟过的细节（swc 闸门、teleport 坑、字段名排序那行）——术语只是给这些细节贴上"我知道它在行业地图的哪个位置"的标签。
