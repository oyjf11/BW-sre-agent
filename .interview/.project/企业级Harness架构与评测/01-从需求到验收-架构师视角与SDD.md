# 一个十万人的公司怎么搭 harness：从需求到验收（学习文）

> 这篇是写给"开口能讲两句、但建不起架构师那种系统级视角"的你。
> 它只有一条推导链，从一句话起头，往下每一步都是上一步逼出来的——不是我换话题，是上一步不解决就出事，所以必须有下一步。
> 你读的时候只问自己一句："为什么非得有下一步？" 答得上来，这条线你就走通了。
> 背的时候只记每段第一句，剩下现场推。
> 这篇讲的是架构师怎么想。想给它配上能报出处的行业框架（Architecture Fitness Function、Ashby 必要多样性定律、ICCR、风险分级、熵管理），配读 `专业框架对照/01-把大白话升级成可引用的专业框架.md`。

---

## 第 0 段 · 先把你的恐惧拆掉

你说你"建立不起企业级的系统级架构思维"。我先告诉你一个反常识的事实：

**企业级 harness 的内核，和你一个人在 OpsPilot / 前端测试上搭的那套，是同一个内核，没有变。** 不存在"另一套更高深的东西"在等着你去掌握。

为什么敢这么说？因为不管多大规模，搭 harness 都是同样八步，顺序也不变：

```
选场景 → 定标准 → 建执行骨架 → 接能力 → 设约束 → 拿证据 → 跑评测 → 沉淀知识
```

你一个人搭，这八步是几个本地文件加几个脚本；十万人搭，这八步是几个平台。**形态变了，八步没变。** 所以"架构师视角"不是要你学一套新东西，是要你看清楚：**规模到底新增了什么、没新增什么。** 这一段就是把"新增了什么"找出来——找到了，恐惧就没了，因为剩下的全是你已经会的。

---

## 第 1 段 · 推导链起头

**起头第一句（只记这句）：一个人搭 harness，难在"怎么把模型管住"；十万人搭 harness，难在"怎么让这套管法，在几千人手里、好几年时间里，不腐烂"。**

下面一步步说清楚，为什么从这句话出发，最后一定会走到 SDD、控制面、模型网关、评测门禁、和两个常设岗位上。

---

## 第 2 段 · 规模到底新增了哪三个问题

你一个人搭 agent，从来不会遇到下面这三件事。它们全是"人一多、时间一长"才冒出来的：

**问题一：几千人同时改，怎么不互相踩。**
你自己改提示词、改工具，改坏了你自己知道。几千个工程师在共享的底座上各改各的，一个人改坏一个公共组件，可能几百个团队的 agent 一夜同时出问题。

**问题二：好几年时间里，所有东西都在悄悄变，怎么不腐烂。**
模型半年换一代，文档写完没人维护就过期，评分标准定完三个月就有人忘了为什么这么定。你一个人做 demo，跑通那一刻就结束了；企业要的是这套东西**三年后还准**。

**问题三：出了事，几百个团队、几百万次调用，怎么追责、怎么不把钱烧光。**
你自己烧 token 心里有数。一个平台上几百个团队在调模型，谁烧的、烧在哪、哪个团队的 agent 在死胡同里反复重试烧钱——不设计，根本看不见。

**记住这三个就行**（互相踩 / 会腐烂 / 难追责控本）。后面所有的企业级设计，**每一样都在对着这三个问题里的某一个**。你以后看任何企业架构图，就拿这三个问题去套：这个框是在防"互相踩"、防"腐烂"、还是在做"追责控本"？套不上的框，多半是为汇报而画的。

---

## 第 3 段 · 架构师的第一反应：不是"造正确"，是"把风险量出来、框住"

这一步是整条链的脊梁，承接我们之前聊评测时打的那块地基。

新手搭 agent，脑子里想的是"我要让它做对"。架构师不这么想——他知道**模型的"对"是证明不了的，只能被测量**。所以架构师交付的从来不是"一个对的 agent"，而是：

> **一套能持续告诉你"每个 agent 现在错多少"、并且"不让某个 agent 的错误扩散出去"的系统。**

把这句话拆成两半，正好是企业 harness 的两条腿：

- **"持续告诉你错多少"** = 评测体系（量出来）。
- **"不让错误扩散出去"** = 控制面里的闸门：权限、审批、灰度、熔断（框住）。

为什么这是架构师和新手的根本分水岭？因为新手追求的"做对"是个**没有边界的目标**——你永远不知道它做到没有。架构师把它换成两个**有边界、能验收**的目标：错误率我量得出来（有数字），扩散范围我框得住（有半径）。**一个企业级系统，从来不是"被证明是对的"，而是"风险被量出来、并且被框在可接受范围内"。** 你下次讲企业架构，起手就立这句，立刻就是架构师的口气，而不是工程师的口气。

---

## 第 4 段 · 从需求到验收的主线，第一站：需求怎么定——这里逼出 SDD

好，开始走"从需求到验收"这条主线。第一站是需求：**怎么把"这个 agent 要做什么、什么算做对"定下来？**

传统软件的答案是"写需求文档"。但需求文档有个老毛病，五十年没治好：**它是死的。** 写完没人维护，跟代码越走越远，最后没人信它。到了 AI 时代这个毛病更要命——因为现在"读需求、照着干"的不只是人，还有模型，而模型会一字不差地照着一份过期文档把事做错。

所以企业级 harness 在需求这一站，需要一个**不会变成死文档**的东西。这个东西，就是 **SDD（Spec-Driven Development，规格驱动开发）**。

---

## 第 5 段 · SDD 到底深在哪（你最没底的一点，单独讲透）

你说"SDD 我不知道它深奥在哪里"。我先把它的字面意思说清楚，再点破它真正深的那一下。

**字面：** 普通开发是"先写代码，回头补文档、补测试"。SDD 反过来——**先写一份说清楚"什么算做对"的规格（spec），AI 再照着这份 spec 生成代码，最后还拿这份 spec 来验收。** 顺序倒过来了：规格先行，代码后到。

听到这你可能觉得："不就是'先想清楚再写'吗？这有什么深的？" ——对，**表面上它平平无奇，深的地方在下面这一句**：

> **SDD 里那份 spec，和你评测集里那道题的"标准答案 + 可接受范围 + 陷阱选项"，是同一个东西。**

我们之前反复说过一句话：**"五十年前靠写需求文档，今天靠建评测集。"** SDD 就是这句话落成开发流程之后的样子。把这层关系铺开，你就懂它深在哪了：

1. **它把"需求"从一张死文档，变成了一份"机器能自动校验"的活契约。** 老需求文档的命门是"没人能自动检查代码到底符不符合它"，于是它必然腐烂。SDD 的 spec 从一开始就写成"能被自动判过没过"的形式——也就是评测集那种"输入 + 期望 + 陷阱"。它不会腐烂，因为每次代码一改，spec 立刻自动判一遍，不符合当场红。

2. **它把"对错的定义"挪到了生成之前。** 这正是我们聊评测时那块地基的另一种说法：**你没法在事后证明 AI 对，你只能在事前把"什么算对"定死、并且定成机器能判的形式。** SDD 是这个原则在"写代码"上的应用，评测集是它在"考 agent"上的应用——**同一个原则，两张脸。**

3. **所以 SDD 和评测集在企业里其实是一套基础设施。** 一个团队写 spec 来驱动开发，平台拿同一批 spec 当评测题来守门——你不用建两套东西。这就是为什么架构师会把 SDD 看得很重：它不是一个开发风格，它是**整个企业"什么算对"这件事的唯一事实源**。

**想通这三点，SDD 就不悬了**：它和你已经懂的评测集是一回事，深就深在"它让需求第一次变得既能驱动 AI 生成、又能自动验收、还不会腐烂"。下次面试官问 SDD，你别去背它的工具流程（什么 spec kit、什么三段式），你直接说这一句：**"SDD 的内核就是评测先行——把'什么算对'在生成前写成机器能判的契约，它和评测集是同一个东西的两种用法。"** 这一句比背十个工具名都值钱。

---

## 第 6 段 · 第二站：谁来执行——控制面和数据面必须掰开

需求（spec）有了，下一站：谁来干活、谁来管着干活。

你一个人做的时候，"干活的代码"和"管着它的代码"（打分、限流、审批、留记录）混在一起也没关系，就你一个人，乱不到哪去。但回到第 2 段的问题一（几千人互相踩）：**如果每个团队都各自搭一套监控、各写一套审批逻辑、各搞一套打分**，那就是几千套互不相同、没人能统一管的东西——这本身就是最大的"互相踩"和"会腐烂"。

所以企业级第一刀，必须把这两类东西掰开：

- **数据面**：真正干业务的部分——agent 一个节点一个节点处理任务。这部分允许各业务线不一样。
- **控制面**：只管控制、不亲自下场的部分——打分、限流、权限、审批、留记录。这部分**抽出来，由一支平台团队统一做一次，所有业务线共用。**

为什么非得分开？因为分开之后：① 你给全公司加一道新的安全检查，只改控制面，不用去碰几百个业务 agent 的代码（防腐烂）；② 任何一个团队想绕过审批、想越权，绕不过去，因为闸门不在它自己手里，在公共控制面上（防互相踩、防扩散）。**控制面与数据面分离，不是为了好看，是为了让"管法"能独立演进、能被强制执行。** 这是企业 harness 的骨架。

---

## 第 7 段 · 第三站：模型怎么调——必须有唯一入口（模型网关）

继续走。agent 要调模型，企业级这里又冒出一个单人版没有的硬约束：**所有模型调用，必须走同一个入口（模型网关）。**

为什么非得唯一入口？还是回到第 2 段那三个问题，它一次戳中两个：

- **防腐烂**：网关里把每个模型**写死具体版本号、禁用"自动用最新版"**。否则厂商哪天悄悄升级一版模型，全公司的分数一夜漂移，你都不知道是自己改坏了还是模型变了。**当裁判用的那个模型尤其要钉死版本**——它一动，所有评测分都不能信了。
- **追责控本**：所有调用从一个口子过，才能按团队、按项目、按任务算清楚谁烧了多少钱，才能给死循环烧钱的 agent 设单任务费用熔断。

记住这一站的一句话：**模型是可替换的商品，所以更要把"换"这件事收口到一个地方——唯一入口，版本钉死，用量可算。**

---

## 第 8 段 · 第四站：怎么验收、怎么不退步——CI 评测门禁

到验收这一站了。这是"从需求到验收"主线的终点，也是第 2 段"防腐烂"问题的正面答案。

单人版你改完跑一遍看看就行。企业级不行——几千人天天在改，你怎么保证**没有人的改动悄悄把公共能力改坏了？** 答案是把评测接进 CI（代码一提交就自动跑的流水线），做成**门禁**：

- **任何改动都要先过题库回归才许合入**——注意，不只是改代码要过，**改一行提示词、改一份 spec、换一个模型版本，全都算"改动"，全都要重跑评测。** 这是 AI 时代 CI 最大的变化：以前 CI 防的是"代码写错"，现在它还要防"提示词/配置/模型悄悄变坏"。
- **门禁分层**：随手改跑个几十题的快检（几分钟，只防雪崩级大问题）；正式合入前跑全量题库（精度够，决定放不放行）；另外留一批"藏题"定期突击考，防团队对着固定题库刷分。

为什么这一步是"防腐烂"的核心？因为腐烂从来不是一次塌掉的，是几千个"看起来没问题"的小改动一点点累积坏的。**评测门禁就是那道不让任何一个小改动蒙混过关的关卡。** 一句话：**在 AI 时代，CI 从"防人写错代码的质检站"，变成了"持续盯着 agent 有没有变坏的体检线"。**

---

## 第 9 段 · 最容易被忽略的一站：组织——两个常设岗位

走到这你可能以为架构讲完了。没有。**企业级 harness 最关键的一块，不是技术，是组织。** 这一步最容易被新手漏掉，也最能区分"懂不懂企业级"。

为什么组织是架构的一部分？回到我们聊评测时的那个结论：**评测体系本质是一个组织产物，不是一份代码。** 题库会过期（业务变了，老题不再代表现实）、金标会失效（标准没人维护就漂）、spec 写完没人更新就又变回死文档。**这些东西不会自己保鲜，必须有专人天天养。** 所以企业级 harness 要新设两个常设岗位：

- **题库负责人**：通常由资深业务专家转岗。管评测题库——保证题目持续代表真实业务、脏数据按真实比例进题、每抓到一次 agent 作弊未遂就补一道陷阱题。
- **金标负责人**：管那批人类专家标注的标准答案，给"模型当裁判"发上岗证——裁判任何改动，先在金标集上重新及格才许上岗。

**这就是为什么一个 demo 永远到不了企业级**：不是技术不够，是它在"组织"这一维上天然是零——一个人做的东西，没有题库负责人、没有金标负责人、没有让度量长期保鲜的岗位。你面试时这点要主动说，它恰恰证明你看懂了企业级的真正难点不在技术。

判断一个团队懂不懂这套，有个最准的尺子：**看它的人力分配。评测和这两个岗位如果吃掉了三分之一到一半的人力，这个团队是真懂了；如果评测是"上线前找个人随便跑跑"，那它还停在 demo 阶段。**

---

## 第 10 段 · 把链兜回来 + 架构师的脑子平时在跑什么

完整答案兜回起头那句：**十万人搭 harness，难的不是技术，是让"管法"在几千人手里、好几年里不腐烂。** 顺着这个难处，被逼出来的就是这一串：

> 规模新增三问（互相踩 / 会腐烂 / 难追责控本）→ 架构师不造正确、只量风险和框风险 → 需求站用 SDD（= 评测先行，活契约不腐烂）→ 执行站把控制面和数据面掰开（统一管、能强制）→ 模型站收口到唯一网关（版本钉死、用量可算）→ 验收站把评测做成 CI 门禁（任何改动先过题库，防腐烂）→ 组织站设题库负责人和金标负责人（让度量长期保鲜）。

最后送你一个东西，治你"建不起架构师视角"的根——**架构师拿到任何一个需求或一张架构图，脑子里其实就反复跑两个问句**，你把这两句练成本能，就有架构师视角了：

1. **"这个框/这个能力，有没有一个'带评测曲线的具体场景'在拉着它？"** 没有场景拉、纯粹因为"显得高级"而存在的框（比如一上来就建全量知识图谱、就上五个 agent 圆桌辩论），一律先砍或先质疑。**复杂性必须挣进来，不许预先建。**
2. **"你为什么不能在低一级做？"** 任何方案，默认用最简单的形态，想加复杂度（多一个 agent、多一层平台、多一个组件），提出者必须拿硬理由回答这句，答不上就降级。

**架构不是被"选"出来的，是被三件事逼出来的：活能不能切开、裁判贵不贵、一个窗口装不装得下。** 你拿这两个问句去戳任何宏大架构图，戳到答不上来的地方，就是它没想清楚的地方。一张什么都有、每个框都很合理的愿景图，恰恰说明**还没有人在上面做过任何一个艰难的取舍**。

## 诚实边界（面试前必读，照着说）

- 这套企业级架构，我能讲清楚**它有哪些组件、为什么需要、按什么顺序落地**。但我要老实说：**我没有从头到尾交付过一个完整的企业级 harness 平台。** 我的真实一手经验在前端测试这个能力域（见隔壁那篇）。
- 所以正确的讲法是：**"我理解企业平台的组件和落地路径，也能从架构师视角推演它为什么长这样；我亲手趟过的是其中一个能力域的 harness。"** 别把"我理解"说成"我做过"——资深面试官三个细节追问就能戳穿编造的交付经历。
- SDD 那一节，我给的是"它和评测集是同一个内核"这个**判断**，这个判断是扎实的、可深挖的；但具体某家公司的 SDD 工具链流程（spec kit 之类）我没实操过，被问到就老实说"我理解的是它的内核，具体工具流程没上手过"。

## 一页速记（背这张就够）

```
起头：十万人搭 harness，难在"管法"不腐烂，不在技术。
内核不变：选场景→定标准→建骨架→接能力→设约束→拿证据→跑评测→沉淀。规模只改形态。
规模新增三问：① 互相踩 ② 会腐烂 ③ 难追责控本。看任何企业设计都拿这三问去套。
架构师不造正确，造"量风险 + 框风险"两条腿：评测量出错多少，闸门框住扩散。
从需求到验收一条线：
```
