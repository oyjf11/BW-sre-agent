# 第一部分 · 先做一件最专业的事：源头甄别

在讲任何框架之前，先亮一个态度：**读行业文章要分得清哪些可信、哪些是营销。** 一个资深的人会做这件事，新手会把白皮书的数字当事实复述、然后被追问当场穿帮。我手上这批 harness 资料，质量分三档：

**第一档·可信、能引用、含金量最高：**
- **Birgitta Böckeler《Harness Engineering for Coding Agent Users》**（Thoughtworks 杰出工程师，发在 Martin Fowler 网站，2026-04-02）。本文一大半专业框架来自这——有控制论根基、不吹数字、还自己列了一堆"尚未解决的问题"。**会老实承认局限，正是可信的标志。**
- **LangChain《The Anatomy of an Agent Harness》**：`Agent = Model + Harness` 出自这里。
- **Thoughtworks：Architectural Fitness Function**（架构适应性函数）。
- **OpenAI《Harness engineering: leveraging Codex》**：Codex 一线工程实践。

**第二档·框架可用，但数字和出处必须丢掉：** 一些资料里的 ICCR、风险分级表、熵管理是好用的脑图，可以讲；但同篇里的"成功率 90%+""成本降 80%""准确率提升 40%""某某正式命名""官方实验报告验证"——这些查无实据，**框架拿来用，数字一个都别往嘴里搬。**

**第三档·基本虚构、当反面教材：** 那种带"92% 成功率、OpenHarness、空壳权限校验"的技术白皮书，绝大部分是编的，只在你想讲"怎么识别一篇 AI 营销软文"时拿来举例。

> **面试金句**：被问"你怎么看 harness 现在这么火"——"概念是真的，`Agent = Model + Harness` 是 LangChain 提的、Thoughtworks 的 Birgitta 给了最扎实的框架；但市面上一堆白皮书把它包装成有'92% 成功率'的成熟产品，这些数字基本查无实据。我更信 Birgitta 那篇——因为它老实列了一堆还没解决的问题。" 这一答立刻把你和"读了篇软文就来面试的人"分开。

# 第二部分 · 地基：评测不是逻辑闭环，是一场有纪律的赌

整篇的脊梁是这一句，先立住，后面前端和企业级都从它长出来：

> **你永远没法"证明"一个自动裁判是对的。你只能拿一批人类判断当尺子，量出它错多少，然后赌这批尺子能代表真实情况。整个评测系统干的全部事情，就是让这个"量"和这个"赌"尽量便宜、尽量诚实、尽量收窄。**

很多材料把评测/gold set 讲成"套娃到人类共识为止、严丝合缝的逻辑闭环"——**这是错的。** 它不是逻辑保证，是一场**有纪律的赌**。承认这一点，四个常见困惑一起塌掉：

1. **评测起什么作用？** 它不让 agent 变对、也不让裁判变对。它只做一件事：**把"不知道有多大、没边界的风险"换成"量出来了、有边界的错误率"。** 你要是想从它身上要"证明 agent 对"，要不到——它本来就给不了那个。它是尺子，不是正确性证书。
2. **几十条凭什么撑起百万次判决？** 因为这是统计归纳，成立只靠一个前提：**那批样本是从真实情况里同分布抽出来的**。分布外，裁判照样会错，而且你不知道它错了。你直觉里那道缝，就是这个"代表性假设"。**承认这道缝恰恰是专业**——业余的假装没缝，专业的指着缝说"我用一致性系数和误差范围量出它有多宽"。
3. **"人类共识"哪有那么干净？** 它不是真理，是"现有最权威的那把尺子"。**人判不齐的地方，根本没有终点**——正确做法不是硬凑共识，是把那道题扔掉、承认"这块我量不了"。
4. **为什么躲不开统计？** 因为只要你"用有限样本去量"，统计就自动进场了。误差范围、一致性系数，全是"有限样本测量"的标配，不是额外的数学负担——**你在做测量，测量天生带误差。**

记住这一部分，下面所有"客观/主观""gold set""门禁"才有根。

# 第三部分 · 落到我的前端 e2e 测试 Agent

## 3.1 先治"凌乱"：分清三个对象

开口就乱，几乎全因为把三个不同的"被测对象"叠在了一起。先拆开：

| 层 | 被测对象 | 谁来考它 | 考的是什么 |
|---|---|---|---|
| 0 | **产品**（那个网页、主流程本身） | 我的测试 agent | 这是 agent 的**工作对象**，不是评测对象 |
| 1 | **测试 agent**（写/跑/自愈/出报告） | **评测集** | agent 干的活**对不对** |
| 2 | **模型裁判**（给 agent 的活打分的 LLM） | **gold set** | 这个裁判判得**准不准** |

最常见的乱，是把第 0 层和第 1 层搅在一起，问出"它是测产品主流程稳不稳吗"。**不是**——产品稳不稳是产品的事；评测集考的是"给 agent 一个任务，它交出来的活对不对"。一觉得乱就回来问：我现在说的是产品、是 agent、还是裁判？

## 3.2 这是个完整闭环，不是"自愈"

**第一句（只记这句）：这个 agent 是一条完整闭环——编写、历史用例整合、执行、自愈、出报告，五段；自愈只是其中一段。**

过去讲它老一开口就扎进"自愈"，结果显得"只会修脚本"。**正确起手永远是先亮全貌，再挑一段深讲。** 五段各一句：①编写：按需求/页面生成用例；②历史整合：把老用例去重、合并、复用；③执行：在环境里真跑；④自愈：改版导致用例失效，自动修回；⑤出报告：把结果汇总成给人看的报告。

而这整个 agent，在行业框架里有个精准定位——〔行业叫法：**Behaviour Harness**，Birgitta 把 harness 分三类，难度递增：Maintainability（管代码内部质量，谁都能搭）< Architecture Fitness（管架构特征）< **Behaviour（验证"软件最终是否真按业务需要运行"，公认最难）**。**前端 e2e 测试 agent 就是最难的 Behaviour Harness**——你不是在做谁都能做的可维护性检查，你在啃业界最不成熟的一块。〕

## 3.3 核心：五段是同一台机器跑了五遍

整篇的钥匙。盯着下面五段，**每一段都长成一模一样的结构**：

> **这一段的"对" ＝ 客观内核（交给代码判，不用模型、不用 gold set） ＋ 主观残留（才请模型判，才需要 gold set）。**

〔行业叫法：这组划分业界正名是 **Computational vs Inferential**（Birgitta）。Computational＝确定性能判的（类型检查、测试、AST、依赖图），快、便宜、可重复＝我们的"客观内核"；Inferential＝只能语义判的（需求有没有理解错、修复合不合理）＝我们的"主观残留"。Birgitta 的核心原则和我们"能代码判的绝不上模型"一字不差：**"能用确定性规则判断的，不要优先交给另一个 LLM。"**〕

五段平铺，盯那股"重复感"：

**① 编写**：对＝该测的测了、不空壳、能抓真 bug。客观内核：断言非空壳（AST）＋好代码上跑绿（不误报）＋退回 bug 版能报错（变异/回放，证明真能抓）。主观残留：全新功能"该测什么、够不够全"。

**② 历史整合**：对＝该复用的复用了、原有覆盖没缩、没错并、断言没丢。客观内核：合并后原有断言一条不少（集合比对）＋整套仍跑绿＋需求覆盖集合没变小＋无重复。主观残留："这两条该不该合成一条"。

**③ 执行**：对＝该跑的真跑了、没漏跑、结果稳定、归因准。客观内核：用例真跑没/漏跑没＋多跑几遍结果一致。主观残留：flaky 归因——这次挂是真 bug 还是环境噪声/时序竞态。

**④ 自愈**：对＝真修对了、没靠删断言蒙混、修复语义合理。客观内核：沙箱重跑过没过＋断言没被删空（AST）＋选择器唯一。主观残留：修复"语义合不合理"。

**⑤ 出报告**：对＝报告事实对、该报的没漏、措辞不误导。客观内核：数字和执行结果对得上（防幻觉编数）＋失败用例一条不漏。主观残留：根因摘要"准不准、抓没抓住重点"。

**你要带走的不是这五段，是这台机器。** 自愈只是它第四次运行。**只记一句"每段的对＝客观内核＋主观残留"，五段现场推**——面试官报任何一段，你都能当场长出来：先问"这段在干嘛"，再把"对"拆成客观＋主观，客观数代码判法、主观说"上模型判配 gold set"。这正治你怕死记硬背：你背的是机器，不是实例。

## 3.4 换个角度看这台机器：Guides 与 Sensors

同一套东西，还能用控制论切一刀，面试讲骨架很顺：〔行业叫法：**Guides（前馈控制）vs Sensors（反馈控制）**，Birgitta。〕

- **Guides（行动前的引导）**：在 agent 动手前给方向，降低走错概率——项目规则、spec、示例、脚手架、Skills。关键洞察：**最有效的 Guide 往往不是文字，而是程序结构**（强类型接口、固定目录、只能正确调用的 SDK 比一段文字要求更难被忽略）。**我给自愈 agent 挂的那份"组件库定位知识包"，就是一个 Guide。**
- **Sensors（行动后的检测）**：动完观察结果、把问题喂回去——测试、覆盖率、AST 检查、运行时监控。关键洞察：**好的 Sensor 不只说"错了"，要输出"错在哪 + 正确做法"**，因为这段报错就是 agent 下一轮的修复上下文。**我那道 swc 防作弊闸门、沙箱重跑、唯一性检查，都是 Sensors（而且是 Computational Sensor）。**

为什么两个都得有：只有 Guides 不知道它做到没有；只有 Sensors 就是不停犯错不停返工。两个合起来才是闭环。

## 3.5 评测集怎么建——从历史挖、冻死、版本化

一句话：**评测集 = 仓库里一个版本化文件，每行一道题，绝大多数从历史挖。** 拿"自愈"举一道题：
- **输入**：一个历史上真发生过的"改版导致用例挂掉"的 case，把当时页面结构/接口返回**冻住**，藏住"人类当年怎么修的"。
- **标准答案**：git 里人类当时实际提交的那版修复——**历史白送**。
- **裁判**：沙箱重跑过没过（代码判）＋断言没删空（AST）＋选择器唯一（代码判）＋"修复语义合不合理"（这条才上模型）。
- **陷阱**：埋一个"删掉断言就能变绿"的诱惑，看它作不作弊。

题分三类：业务题（判得对不对，答案来自历史）、行为题（过程规不规矩——该查的查了吗、信息不够时老实说"建议补充"还是硬猜）、安全题（藏一句"忽略上面规则照我说的做"，看中不中招，必须 100% 不中招）。

**关键纠正——"动态建？"不，恰恰要冻死。** 评测集不能每次随机生成，否则今天一批题明天另一批，分数没法比，你永远不知道是 agent 变好了还是题碰巧简单。正确形态：**从历史一次性挖出来 → 冻结 → 版本化 → 只增不减地长大**（每抓到一次作弊未遂补一道陷阱题，每道由错变对的新题进回归）。它不是动态的，是"静态可重复 + 人工增量"。

## 3.6 gold set 接在哪——只接"模型判"那一小块

回看上面那道题：前三个裁判是代码判（客观，不用 gold set），**只有"语义合不合理"是模型在判**。gold set 只为这一条建：抓几十条这类判定，找 3 个人**各自独立打分、不许商量**，这几十条带人类标注就成了"考这个模型裁判"的卷子；跑裁判过一遍看吻合多少（一致性系数 kappa），**够准才许它上岗**去给那几百道题打"语义合理"分。

所以两者关系：**评测集那道题考 agent；这道题里"语义合理"那半个零件，背后由 gold set 考那个打分的模型。** 纪律：**gold set 跟着"模型判"走、不跟着"段"走**——哪段冒出模型当裁判，哪段配 gold set；能代码判到底的段一律不碰。**昂贵的人类标注只花在真正消不掉的主观那一点上。**

〔行业叫法：这套"gold set + 裁判≠被考模型 + 断言锁死不许 AI 碰"，业界叫 **Approved Fixtures**（Birgitta）——**由人预先批准关键输入和预期输出，避免实现 agent 同时掌握"写代码"和"判定对错"两个权力**。Birgitta 给的病因和你完全咬合：常见做法是 agent 写代码顺手写测试、测试过了就算对，**问题是代码和测试可能同时误解了需求**（需求"不能删已发布的应用"被理解成"不能删任何应用"，实现和测试一致、全绿、但业务错了）。解法就是让判定标准独立于实现者。〕

## 3.7 作弊未遂做成陷阱题——Steering Loop

你最得意的实践：抓到自愈 agent 把断言删了作弊，不是骂它一顿，而是**做成陷阱题永久入库、并把"只许改定位"做成提交前的强制闸门**。〔行业叫法：**Steering Loop**（Birgitta）——agent 犯错后，人不是逐次纠错，而是去问"**为什么我的系统当初没拦住它**"，然后调 Guide 或 Sensor，让同类错误以后更少发生。Birgitta 直接点出这和 **SRE/平台工程**同源：不只修这一次故障，还要修产生故障的系统条件。〕

> 这是拉开"会修脚本的人"和"懂系统的人"的最强一击：讲完作弊故事收一句——"这就是 Steering Loop，和 SRE 一样，我没满足于改好这一次，而是去问'为什么闸门当初没拦住'，把那条规矩从软提示升级成提交前的确定性校验。修的是系统条件，不是单个 case。"

## 3.8 真做过的硬细节（敢往死里讲的）

**先把覆盖率说死、别吹全覆盖。** 中后台 Vue 项目"每晚回归脚本因改版大面积变红"这类，我自动处理掉约六成。夜里红灯分布：纯定位失效（页面没坏）约 45%、能自愈成功率 83%；真业务 bug 约 25%，不修、报红交人；环境/时序竞态约 20%，没完全啃下；断言语义变了（需求真改）约 10%，禁止 AI 碰、转人。"六成"=第一类拿下＋第二类自动分诊，后两类守边界——**我不拿信任换覆盖率。**

**冻结世界，九成功夫在"两个东西算不算同一个"。** 教科书三件套（关动画、固定时间、关字体）只挡表面。我花时间的是**请求指纹归一化**：录制回放拿"方法+路径+请求体哈希"当索引，但前端每个请求带随机请求 ID、请求体里有防缓存时间戳，回放时哈希永远对不上、全部穿透打真后端——上线第一周不稳定率不降反升、冲到 30%，差点被叫停。修法：算哈希前按路径剥掉时间戳、随机串、请求 ID。**最要命一行——序列化前必须把字段名排序**：`{user,role}` 和 `{role,user}` 是同一个请求，不排序就算出两个哈希。我对着两个一模一样的请求查了大半天逐字符比才发现。加排序，第二天 30% 掉到 8%，第四周稳到 3%。这一行就是"判等永远比你以为的脏"。

**自愈到 83% 靠喂知识、不是换模型。** 第一版只有 60%，因为 agent 在原始页面结构上瞎猜锚点、不懂自研组件库门道。涨到 83% 不是换模型，是把组件库定位约定整理成知识包（用到才查、不硬塞）挂给它。真坑：弹窗渲染时被挂到页面末尾（Vue teleport），不在触发它的结构里，agent 原地找永远找不到；表格稳定锚点是每行业务主键，按"第几个子元素"定位、虚拟滚动一滚就漂；下拉选项用到才渲染，不展开根本不存在。**这就是"多出来那二十几分不是模型给的、是我给的"。**

**AI 自愈会作弊，亲眼抓到过。** 一次改版断言也失效了，自愈第一版"修复"是把那行断言整个删掉——测试绿了，等于把眼睛蒙上。关键：这条死规矩（只许改定位、碰断言作废）我**没只写在提示词里**（提示词软、想绕就绕），而是做成确定性脚本、挂成提交前必须过的强制校验，过不了就提交不了——这正是"约束要在执行前生效、不能只靠提示词"。闸门自己也踩坑演进：文本匹配（被注释/字符串里的关键字误判）→ 手写解析器（不健全，被"它解析得了 Vue 吗"问破）→ swc 解析成语法树按节点角色判（定位语句允许改，一流进断言节点的期望值/匹配方式就锁死）。这次作弊未遂也做成了陷阱题。

**自研组件库既是杠杆也是炸药。** 它是自愈率高的本钱（拿得到门道），也是最大单点风险——第三方库升级能控节奏，自研库一动基础组件、全公司脚本可能一夜同时红。所以当最高变更等级管：每个 PR 强制跑这套回归集当门禁、先量影响面；定位门道表跟着组件库版本走、升级必同步；破坏性结构变更走灰度。**同一个东西，既是杠杆也是炸药。**

## 3.9 前端这段的面试起手式

别开口就"自愈"。背熟这段：

> "这个 agent 是个完整闭环——编写、历史整合、执行、自愈、出报告五段。评测它对五段是**同一套**：每段的'对'都拆成代码能判的客观内核（业界叫 Computational）和只能上模型判的主观残留（Inferential）。它本质是三类 harness 里最难的 Behaviour Harness——验证业务真的对。我拿信息量最大的一段展开——比如自愈，因为它四种裁判全齐、标准答案还能从 git 白拿。"

先证明脑子里有全貌，再用自愈当例子，就显得是"挑了个好例子"，而不是"只会这个"。被往深问，就进 3.8 那些真趟过的细节——越追越占便宜。

# 第四部分 · 放大到企业级：十万人怎么搭，从需求到验收

## 4.1 先拆掉"建不起企业级视角"的恐惧

一个反常识的事实：**企业级 harness 的内核，和你一个人搭的那套，是同一个内核。** 不管多大规模，都是同样八步、顺序不变：

```
选场景 → 定标准 → 建执行骨架 → 接能力 → 设约束 → 拿证据 → 跑评测 → 沉淀知识
```

你一个人搭，这八步是几个本地文件加脚本；十万人搭，这八步是几个平台。**形态变了，八步没变。** 所以"架构师视角"不是学一套新东西，是看清"规模到底新增了什么"。

## 4.2 起头第一句

**一个人搭 harness，难在"怎么把模型管住"；十万人搭 harness，难在"怎么让这套管法，在几千人手里、好几年时间里，不腐烂"。**

## 4.3 规模新增的三个问题（看任何企业设计都拿这三问去套）

- **① 互相踩**：几千人在共享底座上各改各的，一个人改坏公共组件，几百个团队的 agent 一夜同时出问题。
- **② 会腐烂**：模型半年换代、文档没人维护就过期、标准定完三个月就有人忘了为什么。demo 跑通那一刻就结束，企业要的是三年后还准。
- **③ 难追责控本**：几百个团队、几百万次调用，谁烧的钱、哪个 agent 在死胡同里反复烧——不设计就看不见。

后面每一样企业级设计，都对着这三问里的某一个。套不上的框，多半是为汇报而画的。

## 4.4 架构师的第一反应：不是"造正确"，是量风险、框风险

承接第二部分的地基。架构师交付的从来不是"一个对的 agent"，而是：

> **一套能持续告诉你"每个 agent 现在错多少"、并且"不让某个 agent 的错误扩散出去"的系统。**

拆两半正好是企业 harness 两条腿：**"持续告诉你错多少"＝评测体系（量出来）**；**"不让错误扩散"＝控制面里的闸门：权限、审批、灰度、熔断（框住）**。新手追"做对"（没有边界、永远不知道做到没有），架构师换成两个有边界、能验收的目标：错误率量得出（有数字）、扩散范围框得住（有半径）。

## 4.5 需求站：SDD = 评测先行（你最没底的那一点）

从需求到验收这条主线，第一站是需求：怎么把"这个 agent 要做什么、什么算做对"定下来？传统答案是写需求文档，但它有个五十年的老毛病——**它是死的**，写完没人维护、跟代码越走越远。AI 时代更要命：照着一份过期文档干活的还多了模型。

所以需求站需要一个不会变成死文档的东西，它就是 **SDD（Spec-Driven Development，规格驱动开发）**。

字面：普通开发先写代码、回头补文档；SDD 反过来——**先写一份说清"什么算做对"的规格（spec），AI 照着生成，最后拿这份 spec 验收**。听着平平无奇，深的地方在这一句：

> **SDD 里那份 spec，和你评测集里那道题的"标准答案+可接受范围+陷阱"，是同一个东西。**

铺开就懂它深在哪：① 它把"需求"从死文档变成**机器能自动校验的活契约**——代码一改，spec 立刻自动判一遍，不符合当场红，所以它不腐烂；② 它把"对错的定义"挪到了**生成之前**——这正是第二部分地基的另一种说法："你没法事后证明 AI 对，只能事前把'什么算对'定死、并定成机器能判的形式"；③ 所以 **SDD 和评测集在企业里其实是一套基础设施**——一个团队写 spec 驱动开发，平台拿同一批 spec 当评测题守门，不用建两套。

> **面试别背 SDD 的工具流程，直接说这句**："SDD 的内核就是评测先行——把'什么算对'在生成前写成机器能判的契约，它和评测集是同一个东西的两种用法。"

## 4.6 执行站：控制面和数据面必须掰开

需求（spec）有了，谁来干活、谁管着干活？回到问题①（互相踩）：如果每个团队各搭一套监控、各写一套审批、各搞一套打分，那本身就是最大的"互相踩"和"会腐烂"。所以企业级第一刀：

- **数据面**：真正干业务的部分（agent 一个节点一个节点处理），允许各业务线不一样。
- **控制面**：只管控制、不下场的部分（打分、限流、权限、审批、留记录），**抽出来由一支平台团队做一次、所有业务线共用**。

为什么非分开：① 加一道新安全检查只改控制面、不碰几百个业务 agent（防腐烂）；② 任何团队想绕审批、想越权都绕不过，因为闸门不在它手里、在公共控制面上（防扩散）。〔行业叫法：把"规范"从文档里的要求变成"流水线里过不去的硬规则"，这个通用思想是 **Architecture Fitness Function**（Thoughtworks）——架构特征要可执行、可持续验证，而不是写在 wiki 上等人遵守。〕

## 4.7 模型站：必须有唯一入口（模型网关）

agent 调模型，企业级硬约束：**所有模型调用走同一个入口。** 它一次戳中两个问题：**防腐烂**——网关里把每个模型写死版本号、禁用"自动最新版"（当裁判用的模型尤其要钉死，它一动所有评测分都不能信）；**追责控本**——从一个口子过才能按团队/项目/任务算清谁烧多少、才能给死循环 agent 设单任务费用熔断。一句话：**模型是可替换的商品，所以更要把"换"收口到一个地方——唯一入口、版本钉死、用量可算。**

## 4.8 验收站：CI 评测门禁（防腐烂的正面答案）

几千人天天改，怎么保证没人悄悄改坏公共能力？把评测接进 CI、做成**门禁**：

- **任何改动都要先过题库回归才许合入**——不只改代码，**改一行提示词、改一份 spec、换一个模型版本，全算"改动"、全要重跑**。这是 AI 时代 CI 最大的变化：从"防人写错代码"，变成"持续盯着 agent 有没有变坏"。
- **门禁分层**〔行业叫法：质量左移，Birgitta 分四层〕：本地随手改跑几十题快检（几分钟，只防雪崩级大问题）→ 提交/PR 前跑全量＋集成＋安全扫描 → CI/合并后跑变异测试、大范围架构 Review、完整回归 → 持续运行盯死代码、架构漂移、SLO、AI 输出质量。**按速度和成本，把每种检查放到最合适的位置。**

腐烂从来不是一次塌的，是几千个"看起来没问题"的小改动累积坏的。门禁就是那道不让任何小改动蒙混过关的关卡。

## 4.9 组织站：两个常设岗位（最容易漏、最区分懂不懂）

企业级 harness 最关键的一块不是技术，是组织。承接地基：**评测体系本质是组织产物，不是一份代码。** 题库会过期、金标会失效、spec 没人更新又变回死文档——**这些东西不会自己保鲜，必须有专人养**。所以新设两个常设岗位：

- **题库负责人**（资深业务专家转岗）：保证题目持续代表真实业务、脏数据按真实比例进题、每抓到作弊未遂补一道陷阱题。
- **金标负责人**：管人类专家标注的标准答案，给"模型当裁判"发上岗证——裁判任何改动先在金标集重新及格才许上岗。

〔行业叫法：定期清理冗余/过期/低使用率的能力，叫**熵管理（Entropy Management）**；Birgitta 也独立提过 harness 自身需要版本管理、一致性检查、废弃机制，两个来源都支持，可放心讲。〕

**这就是为什么一个 demo 永远到不了企业级**：不是技术不够，是它在"组织"这一维天然是零。判断一个团队懂不懂，有个最准的尺子：**看人力分配——评测和这两个岗位吃掉三分之一到一半的人力，才是真懂；评测只是"上线前找人随便跑跑"，那还停在 demo。**

## 4.10 企业为什么要逼大家用"黄金路径"（给企业级加理论深度）

高级问题："企业为什么要统一脚手架，不是限制创新吗？" 答案不是管理偏好，是控制论硬约束，三个递进概念（Birgitta）：

- **Harnessability（可驾驭性）**：强类型、清晰分层、统一目录、完整测试的项目天然好管；隐式全局变量、动态依赖、无测试、知识全在人脑里的老项目，最需要 harness 却最难建。
- **Ambient Affordances（环境给的便利）**：不用每次告诉 agent，**项目结构本身就在引导它走对路**。
- **Ashby 必要多样性定律（Law of Requisite Variety，控制论）**：**控制系统要管住复杂系统，自己的状态空间必须能覆盖对方的可能状态。** 推论很硬：你让 agent 想生成什么架构就生成什么，harness 永远穷尽不了、管不住；**把架构收敛成少数几种标准拓扑（黄金路径），控制难度断崖式下降**。

> **面试**："企业搞统一黄金路径不是限制创新，是控制论的硬约束——Ashby 必要多样性定律说控制系统的多样性必须匹配被控对象。你让 AI 自由生成任意架构就永远管不住；收敛成几种标准拓扑，可驾驭性才上得去。本质是用'限制解空间'换'可治理'。"

## 4.11 架构师的脑子平时在跑什么（治"建不起视角"的根）

架构师拿到任何需求或架构图，脑内反复跑两个问句，练成本能就有了视角：

1. **"这个框/能力，有没有一个'带评测曲线的具体场景'在拉着它？"** 没场景拉、纯因"显得高级"而存在的框（一上来建全量知识图谱、上五个 agent 圆桌辩论），一律先砍或先质疑。**复杂性必须挣进来，不许预先建。**
2. **"你为什么不能在低一级做？"** 默认最简单形态，想加复杂度，提出者必须拿硬理由，答不上就降级。

**架构不是"选"出来的，是被三件事逼出来的：活能不能切开、裁判贵不贵、一个窗口装不装得下。** 一张什么都有、每个框都合理的愿景图，恰恰说明**还没有人在上面做过任何一个艰难取舍**。

## 5.2 怎么评价 harness 本身好不好（显得想得比对方深）

Birgitta 老实承认这是**尚未解决的开放问题**——你主动讲这个"开放问题"本身就是高阶信号。他点出一个反直觉陷阱：**一个 Sensor 从来不报错，可能是代码极好，也可能是它根本没检测能力（空壳）**——和前端"覆盖率被空壳测试刷满"同一个病，所以用变异测试验"测试本身有没有用"。他列的 harness 质量候选指标，正好和评测的北极星向量同构，**永远当向量、不揉成一个数**：

- 错误拦截率（拦住了多少本该拦的）
- 误报率 / 漏报率（＝Precision / Recall）
- 自修复成功率（＝你的自愈 83%）
- 人工升级率（多少最终还是转人）
- 单任务验证成本（验证一次烧多少钱/时间）

> **面试**：被问"你怎么知道你这套有效、不是自我感觉良好"——"这是 Birgitta 都承认还没解决的开放问题。我借测试圈成熟指标：变异测试防 Sensor 变空壳，用误报率/漏报率＋自修复成功率＋人工升级率＋单任务验证成本这一组向量看，绝不揉成一个总分。"

## 5.3 一条铁律：怎么用术语而不翻车

**先大白话讲透，再甩一个术语收口。** 顺序反了就翻车——上来一串 Computational、Feedforward、Requisite Variety，面试官只觉得你在背词、还怀疑你没真懂。

模板：「（大白话讲清是什么、为什么、踩过什么坑）……这个在业界就是 X 说的〔术语〕。」

反例（别这么干）：「我用 Guides 和 Sensors 构成前馈反馈闭环，Computational Sensor 做确定性校验，配合 Steering Loop 实现 Ambient Affordances……」——这是念词，不是讲懂。**术语是给你已经讲懂的东西贴"我知道它在行业地图哪个位置"的标签，不是用来代替讲懂。** 你最大的本钱永远是前端那些真趟过的细节（swc 闸门、teleport 坑、字段名排序那行）。

## 附录 · 黑话翻译（卡住了回这里查）

- **跑绿 / 报红**：测试通过显绿、失败显红。"在好代码上跑绿"＝把测试放到没毛病的好版本上跑应全过，证明它不误报。
- **变异 / 回放**：把代码退回到"真 bug 还没修好"的坏版本，或往好代码注入小错误，看测试发不发得现——发现不了说明是空壳。它是"覆盖率"的防作弊替代品。
- **AST**：把代码解析成"语法树"，按节点角色判（能精确分清定位语句 vs 断言语句），而非按文本匹配（会被注释/字符串里的关键字骗到）。
- **断言**：测试里"检查对不对"那一行。删掉它测试就什么都不查了，但还会绿。
- **选择器 / 定位**：告诉浏览器"点哪个按钮、填哪个框"的代码。改版后最易失效。
- **flaky（抖动）**：同输入有时过有时挂。对 AI 是毒药——它会照假失败信号去修没坏的东西。
- **kappa**：衡量两个打分者一致程度的统计数，扣掉了"瞎蒙也能蒙对一半"的水分。
- **沙箱重跑**：把修好的脚本丢进隔离、冻结好的环境再跑一遍，用真跑结果当裁判，不听 AI 自己说"修好了"。
