## Q1 取证要调一堆云上工具（K8s/SLB/CMS/RDS/OSS），为什么不让各节点直接调 SDK，非要套一层网关？

**核心**：因为「调工具」这件事除了发请求，还连着**校验、重试、超时、审计、脱敏、追踪**六件横切的事——这些不能散落在每个节点里各写一遍，必须收口到一个统一的**工具网关（Tool Gateway）**。

**展开**：
- **关注点分离**：节点只负责「我要查什么」，网关负责「怎么把这次查询做安全、做可观测」。节点里看不到一行重试或脱敏代码，全在网关一处。
- **声明式契约**：每个工具用一份元数据声明自己的参数 schema、风险等级、是否需要审批、超时、重试次数。网关拿着这份契约统一执行，新接一个工具只是多注册一条元数据，不改任何调用方。
- **统一返回壳**：底层五类数据源返回结构天差地别，网关一律包成统一的 `ToolResponse`（success / result / error / latency_ms）。下游永远只面对一种结构，跟具体是哪个云、哪个工具彻底解耦。

**项目印证**：`gateway.py` 里 33 个工具全部 `register_tool(ToolMetadata(...))` 注册，带 `risk_level / requires_approval / timeout_ms / retries`；`ToolGateway.call_tool` 是唯一入口，内部固定管线：fixture 短路 → 起 tracing span → 工具存在性校验 → 参数 schema 校验 → 选适配器 → 带重试执行 → 审计落库 → 返回统一 `ToolResponse`。

**追问预判**：「这不就是个 facade 吗？」→ 是 facade，但价值在于它是**强制收口点**：风险分级、审批开关、敏感信息脱敏、调用审计这些合规和安全要求，只有收口到一个网关才能保证「不可能绕过」。散在节点里就总会有一处漏掉。

## Q2 切到真实环境后，某个工具的真实适配器还没接好，这一路会怎么走？为什么不悄悄退回 mock？

**核心**：**fail-closed（关门挡掉）**——真实模式下没有对应真实适配器，网关直接返回失败，绝不偷偷退回 mock 造一份假数据出来。

**展开**：
- **为什么不退回 mock**：运维场景里，「假装查到了」比「明说没查到」危害大得多。一份以假乱真的 mock 数据会顺着取证流程一路灌进诊断，让模型基于假证据下一个看似很有底气的错误结论。宁可这一路明确失败、反映到质量分上，也不能让假数据进场。
- **失败是显式的、可归因的**：这一路会被标成失败状态，覆盖度因此下降，质量门控（critic）看得到，必要时退回重查或转人工。失败不是被吞掉，而是变成一个下游能消费的信号。
- **能力可探测**：网关提供「不执行就能问某工具在当前模式下可不可用」的能力描述接口，编排层可以提前知道哪些路在真实模式下根本走不通，而不是等执行失败才知道。

**项目印证**：`gateway.py` 的 `call_tool` 在 real 模式下选不到真实适配器时，直接返回 `success=False`（不落到 mock 分支）；未接入的工具其桩函数抛 `RuntimeError("... not configured")`；`describe_capability` 提供「可用性探测」而不触发真实调用。

**追问预判**：「fail-closed 会不会太脆，动不动整条流程就挂？」→ 不会挂整条，只挂这一路。配合并发取证的失败隔离（Q5）和质量门控的退回机制（02-Q5），单路 fail-closed 只是让覆盖度降一格，整体流程照常往下走。

## Q3 这些工具调用涉及生产数据，团队级怎么做到「每一次调用都可审计、又不泄露敏感信息」？

**核心**：**调用审计 + 敏感字段脱敏**两件一起做——每次工具调用全程留痕落库，但留痕之前先把密钥、令牌一类敏感字段递归打码。

**展开**：
- **全程留痕**：每次调用记录 run_id、工具名、参数、走的是哪个适配器、耗时、成功失败、错误信息，既写进进程内审计日志，也持久化到独立的审计表，做到「谁在哪次工单里调了什么工具、结果如何」可回溯。
- **写库前先脱敏**：审计内容落库前过一遍脱敏，命中 password / secret / token / api_key / access_key / authorization / cookie 这类敏感键就替换成打码占位符，且是**递归**处理嵌套结构，不会因为敏感字段藏在深层 dict 里就漏掉。
- **审计失败不拖垮主流程**：审计落库本身包了异常兜底，写库失败只记一条告警并回滚，绝不让「记日志失败」反过来搞挂正在处置故障的主流程——审计是旁路，不是主路。

**项目印证**：`gateway.py` 的 `_log_audit` 双写内存 `audit_log` + DB 表 `IncidentToolAudit`；`_sanitize_for_audit` 递归遍历 dict/list，命中 `SENSITIVE_KEYS` 集合即替换为 `***REDACTED***`；落库逻辑 `try/except + rollback`，失败只 `logger.warning`。

**追问预判**：「为什么脱敏放在网关而不是各适配器？」→ 同 Q1，收口才能保证不可绕过。脱敏一旦下放到适配器，总会有人新写一个适配器时忘了脱敏。放在网关这个唯一出口，是「结构上保证」而不是「靠自觉」。

## Q4 取证里有一路工具偶发超时或抖动，怎么处理？会不会因为一路慢把整轮取证拖垮？

**核心**：**多层兜底**——单工具自带重试（指数退避）+ 每工具声明超时 + 整轮取证一个总超时上限，不让「一路慢」演变成「整轮卡死」。

**展开**：
- **单工具重试**：网关对每次调用做有限次重试（默认 2 次）并用指数退避，吸收偶发抖动；但重试次数有上限、不无限重试，避免在一个坏工具上空转。
- **声明式超时**：每个工具在元数据里声明自己的超时（只读查询十几到三十秒不等），慢工具到点即断；底层各真实客户端（数据库、K8s）也都设了连接/查询超时，双重保证不无限等。
- **整轮总超时兜底**：并发扇出外面再包一个总超时，到点强制收口，已经回来的证据照常用，没回来的按失败处理——保证「取证阶段的总耗时有天花板」，不被最慢一路无限拖累。

**项目印证**：`gateway.py` 用 `tenacity @retry(stop_after_attempt(2), wait_exponential(min=1,max=10))`；每工具 `timeout_ms` 在 `ToolMetadata` 声明；专家池并发扇出用 `asyncio.wait_for(asyncio.gather(...), timeout=150.0)` 做整轮总超时，超时则该批全部按失败兜底。

**追问预判**：「重试会不会把写操作重复执行？」→ 取证全是只读，重试天然安全。真正有副作用的写操作（执行修复动作）不在取证阶段，且走的是另一套带幂等键、需人工审批的执行通道，不在这个重试范围里。

**细化追问**：「你是怎么做的指数退避？」→ 我们把指数退避收口在 `ToolGateway`，不是每个节点各写一套。`call_tool()` 先做工具存在性校验、参数 schema 校验和适配器选择，确认这是一次合法工具调用后，才进入 `_execute_with_retry()`。这个方法用 `tenacity` 装饰：`stop_after_attempt(2)` 表示最多尝试 2 次，`wait_exponential(multiplier=1, min=1, max=10)` 表示失败后按指数退避等待，等待时间最小 1 秒、最大 10 秒封顶，`reraise=True` 保证最终失败能被网关统一捕获并包装成 `ToolResponse(success=False)`。这样既能吸收 K8s/CMS/RDS 这类只读查询的瞬时抖动，又不会无限重试拖垮整轮取证。

**再追问**：「工具元数据里的 `retries` 有没有真正用上？」→ 当前代码里每个 `ToolMetadata` 已经声明了 `retries/timeout_ms` 这类策略位，但实际重试装饰器仍是网关统一的 2 次策略。生产级演进上，会把 `metadata.retries` 接进动态 retry policy，让日志、指标、K8s、数据库这几类工具按耗时、稳定性和下游限流策略分别配置；但不会对参数错误、工具不存在、真实适配器未配置这类确定性失败做重试。

## Q5 取证是并发发起的，其中一路抛异常了，会不会把整个并发批次一起带崩？

**核心**：**失败隔离**——并发收集时让每一路的异常「就地捕获、各自落地」，单路炸了只标自己失败，绝不冒泡炸掉整批。

**展开**：
- **异常不冒泡**：并发聚合时显式声明「收集异常而不是抛出」，于是某一路 panic 只会在结果列表里占一个「异常」位置，其余各路的正常结果照收不误。
- **可降级 vs 不可降级**：每个取证任务带一个「失败了能不能降级」的标志。可降级任务失败就标记失败、继续往下；极少数不可降级的关键任务失败才会向上抛、触发更强的处理。绝大多数取证路径都是可降级的。
- **失败也产出结构化结果**：挂掉的一路不是「什么都没有」，而是产出一条带失败状态和错误摘要的记录，进入后续打分。失败本身是一条证据——证明「这个方向没查通」。

**项目印证**：`nodes/__init__.py:497` `asyncio.gather(..., return_exceptions=True)`；`_collect_one` 内 `try/except`，按 `degrade_on_failure` 决定是吞掉标失败还是 `raise`；聚合时 `if isinstance(r, Exception): continue` 跳过异常位、不影响其他路入库。

**追问预判**：「并发写同一个 state，不会有竞态吗？」→ 见 Q6，这正是原子写要解决的问题。

## Q6 多路并发往同一份 state 里追加证据，会不会写进「半截脏数据」？

**核心**：**Agent 级原子写**——每一路（专家 Agent）的证据是「要么整批进 state，要么整批回滚」，不允许一路写到一半失败、留下半截脏数据污染下游。

**展开**：
- **为什么要原子**：一路可能产出多条证据。如果写到第二条时出异常，state 里就留下了「这一路的部分证据」，下游打分会基于一份残缺数据误判覆盖度。
- **怎么做**：先把这一路的证据攒齐成一批，再尝试整批写入；一旦写入过程出问题，就按 id 把这批刚加进去的证据全部撤掉，回退成「这一路彻底失败」的干净状态，并补一条静态失败壳，保证下游拿到的永远是「完整的成功」或「明确的失败」，没有中间态。
- **失败有兜底壳**：一路彻底失败时不是留空，而是放一个静态的「这一路失败了」占位结果，让聚合阶段能正确把它算成未覆盖。

**项目印证**：当前专家池路径 `_evidence_fanout_v2`（`nodes/__init__.py:584-605`）对每个 agent 先攒 `agent_evidence` 再 `extend`，异常时用 `set(id(e))` 把本批刚加入的证据剔除回滚，并 append 一个 `_build_llm_failed_shell_static` 失败壳。

**追问预判**：「Python 的 asyncio 是单线程，哪来的并发写竞争？」→ 严格说不是线程级数据竞争，而是**逻辑级一致性**问题：一路在多个 await 点之间被打断、或中途抛异常，会留下逻辑上不完整的写入。原子写保证的是「这一路的证据集合在 state 里要么完整要么不存在」这个不变量。

**细化追问**：「你一方面说原子写入，一方面又说攒齐成一批再写入，到底是原子写入还是批量写入？」→ 批量写入是实现手段，原子写入是语义目标。这里的“原子”不是说 Python `list.extend()` 有数据库事务能力，而是说我们在 Agent 维度保证一个状态不变量：一个专家 Agent 产出的证据，要么整批对下游可见，要么整批不可见。实现上先在局部变量里攒成 `agent_evidence`，完整成功后再 `extend` 到 `state["evidence_items"]`；如果写入或后续处理失败，就按这批 evidence 的对象 id 从 state 里剔除，补偿式回滚，再补一条失败壳。所以更严谨的表述是：**批量提交 + 失败补偿回滚，实现 Agent 级逻辑原子可见性**。

**举例追问**：「能举个例子吗？」→ 比如 `K8sAgent` 一次要产出 3 条证据：`deployment_status`、`pod_events`、`recent_restarts`。如果边生成边写，写完前两条后第三条解析失败，state 里就只剩半截 K8s 证据，下游可能误以为 K8s 路径部分成功，从而高估覆盖度。我们的做法是先把 3 条都放进局部 `agent_evidence`，三条全部成功后才一次性 `extend` 到全局 state；如果这一路失败，就把本批 evidence 按 `id(e)` 从 state 里剔除，并追加一条 `k8s_failed_shell`。这样下游只能看到两种状态：K8s 整批成功，或者 K8s 整路失败，不会看到半成功半失败的脏状态。

## Q7 取证失败你分了 FAILED_CONFIG 和 FAILED_RUNTIME 两种，分这么细图什么？

**核心**：因为这两种失败**归因不同、处置动作也不同**——CONFIG 是「这条路根本没接通/没权限」，RUNTIME 是「接通了但这次查砸了」，混成一种就丢掉了「该找谁修」的信息。

**展开**：
- **FAILED_CONFIG（接入类）**：真实适配器没接、凭据缺失、权限不足这类。这是**平台/接入层面**的问题，重试多少次都没用，得靠人去补接入或补权限。
- **FAILED_RUNTIME（运行类）**：超时、目标服务临时不可达、偶发报错这类。这是**运行时**的问题，可能重试一轮、或换个时间窗就好了，对应的处置是「再查一轮」。
- **为什么要分**：质量门控决定「退回重查」还是「转人工」时，这两种失败给的信号完全不同——满屏 RUNTIME 失败值得再试一轮，满屏 CONFIG 失败再试也是白试、该直接叫人。分类是为了让下游做对决定。

**项目印证**：`evidence_utils.py` 的 `classify_result` 把失败分流到 `FAILED_CONFIG` / `FAILED_RUNTIME`；四态枚举 `SUCCESS_USABLE / SUCCESS_EMPTY / FAILED_CONFIG / FAILED_RUNTIME` 是后续打分和门控决策的基础。

**追问预判**：「这两种失败怎么判定的？」→ 当前由网关返回的错误信息归类（接入类错误带明确特征）。团队级的演进方向是让适配器统一抛带 `error_code` 的结构化异常，分类只读 code、不依赖文本——这样分类规则更稳、跨适配器一致。这是这块明确的收敛点。

## Q8 怎么判断一路「查到了有用东西」还是「查了个空」？返回非空就算查到了吗？

**核心**：不是简单判非空——而是**每一类数据源各自定义「什么才算查到了」**，按工具语义判空，而不是看 dict 是否为空。

**展开**：
- **语义判空**：查日志要看日志数组到底有没有行（空数组等于没查到）；查指标要看时序里有没有真实数据点；查 K8s 要看有没有 status/pods/events 这些实体字段。同样是「返回了一个 dict」，有的算查到、有的算空，得按这一类数据「长什么样才算有内容」来判。
- **剔除元字段再判**：返回体里那些下划线开头的元数据字段（比如标记走了哪个适配器的字段）不能算业务内容，判空前先把它们剔掉，否则会把「只有元数据、没有业务数据」的空结果误判成「查到了」。
- **空结果是独立一档**：查通了但结果为空，单独归成 `SUCCESS_EMPTY`，既不算成功覆盖、也不算失败——它和「查报错了」是两回事，对诊断的含义也不同（空结果本身可能就是线索，比如「这个时间段确实没有错误日志」）。

**项目印证**：`evidence_utils.py` 的 `is_payload_usable` 对 `query_logs / query_metrics / query_k8s_* / query_db_* / query_lb_*` 分别写了判定规则；`_semantic_payload` 过滤 `_` 开头的元字段后再判；判空结果驱动 `SUCCESS_USABLE` vs `SUCCESS_EMPTY` 的分档。

**追问预判**：「每个工具写一套判空规则，工具一多不就爆炸了？」→ 所以兜底有一条通用规则（剔除元字段后还有业务字段就算有内容），只有需要精细判定的核心数据源才单独写规则。团队级方向是让每个适配器自带「我这类数据怎么算 usable」的声明，把判空规则从中心函数下沉到适配器自描述。

## Q9 质量分到底怎么算出来的？为什么要把它单独拎成一个函数？

**核心**：质量分 = **多专家证据链的可信完成度**，综合专家覆盖度、专家置信度、降级惩罚和截断惩罚；单独拎成纯函数，是为了让「打分」可独立测试、可独立演进，跟编排和门控彻底解耦。

**展开**：
- **覆盖度**：看 `k8s / db / logs / metrics / deployments` 这 5 类 specialist agent 有多少类有效完成。单个专家再自信，也不能代表全局可靠。
- **置信度**：每个 `SpecialistAnalysis` 带自己的 `confidence`，aggregate 对有效 agent 的 confidence 做平均，作为基础质量。
- **降级与截断惩罚**：`partial=True` 说明只是降级分析，置信度要打折；`truncated=True` 说明因为超时、轮次或上下文限制没有完整分析，整体质量要扣 penalty。
- **为什么做成纯函数**：打分逻辑输入就是一批 `SpecialistAnalysis`，输出就是质量分，不碰外部 I/O。这样能单测覆盖「全失败、部分降级、多个截断、低覆盖高置信」这类边界，改权重不用拖着整张图跑。
- **打分与决策解耦**：打分（aggregate）只负责算分和列缺口，决策（critic）只负责拿分做放行/退回。两边职责单一、各自可测——这是 02-Q4「材料审核员 vs 方案评委」在工程上的落地。

**项目印证**：`aggregator.py` 的 `_compute_weighted_quality` 是无副作用纯函数：跳过 `LLM_FAILED` agent；对有效 agent 的 `confidence` 求平均；`partial` 时置信度乘 0.5；按 `truncated_count` 施加整体 penalty；再乘以 `active_count / 5.0` 的覆盖度。当前专家池聚合路径 `_evidence_aggregate_v2` 把结果写入 `state["evidence_quality_score"]`，`critic_node` 只读不重算。

**追问预判**：「为什么不只看平均 confidence？」→ 因为单点高置信会骗人。比如 logs agent 0.95，但 k8s/db/metrics/deployments 全没完成，平均置信度看起来高，实际上证据链很窄。所以必须把 confidence 和 coverage 绑在一起，再惩罚 partial/truncated，避免「局部很确定」伪装成「全局很可靠」。

## Q10 防失控除了「最多 2 圈」，工程上还做了什么让它停得「干净」？

**核心**：不只是停——停的时候要留下**机器可读的停机原因**，并且把模型那份「假装很确定」的结论一起降级，不给下游留误导尾巴。

**展开**：
- **结构化终止原因**：循环耗尽转人工时，不是甩一句日志了事，而是写一份结构化的终止原因：错误码（标成「证据循环耗尽」）、发生在哪个阶段、缺了哪些类目、哪些工具失败了。前端和下游能直接消费这份结构，运维一眼看清「为什么停、卡在哪」。
- **同时压结论置信度**：转人工的同时，把诊断给出的根因候选置信度全部压到 0.5 以下，并打上「需立即人工介入」标记。因为这是个没查透的结果，不能让它带着高置信度流到下游，让人误以为很可靠。
- **停机是一等公民**：「停下来」被当成一种正常的、要好好交代清楚的结果来设计，而不是异常崩溃。Agent 工作流里，「优雅地承认自己搞不定并交班」和「给出答案」一样重要。

**项目印证**：`critic_node`（`nodes/__init__.py:1086-1107`）loop_count 到顶时写 `terminal_reason={code:"EVIDENCE_LOOP_EXHAUSTED", stage, missing, failed_tools}`，set `requires_immediate_human=True`，并把所有候选 `confidence = min(confidence, 0.5)`。

**追问预判**：「为什么要专门压置信度，转人工不就行了？」→ 因为状态是会被下游和前端读的。如果只改路由不改数据，下游某个环节或前端展示仍可能读到「置信度 0.9 的根因」，跟「需人工介入」的状态自相矛盾。压置信度是为了让**数据和状态保持一致**，不留逻辑矛盾的尾巴。

## Q11 取证扇出从旧动态扇出切到当前专家 Agent 池，团队级怎么安全上线？

**核心**：**feature flag 灰度**——新老两套实现并存在同一个节点入口后面，靠一个配置开关决定走哪套，能灰度放量、能一键回退，不靠「删旧代码上新代码」这种一刀切。

**展开**：
- **同一入口，双实现**：节点对外是同一个函数，进来第一件事是读开关：关着走老的动态扇出，开着走新的专家 Agent 池。上层编排图完全不感知背后换了实现。
- **可回退**：新架构万一在线上出问题，把开关一关就退回老实现，不用回滚发布、不用改图。这是把「上新功能」的风险从「发布级」降到「配置级」。
- **配置从统一来源读**：开关（以及 mock/real 适配器模式）从统一的配置对象读，不直接读环境变量，避免「同一个配置在不同地方读出不同值」的配置漂移。

**项目印证**：`evidence_fanout_node` / `evidence_aggregate_node` 入口都按 `settings.agent_feature_specialist_pool` 分流到旧动态扇出路径 `_original_*` 或当前专家池路径 `_*_v2`；`TOOL_ADAPTER_MODE` 等配置统一走 `get_settings()` 而非 `os.getenv`（防配置漂移）。

**追问预判**：「两套实现长期并存，不是技术债吗？」→ 是债，但是**受控的、有偿还计划的债**。灰度期并存是为了安全过渡，新架构在生产验证稳定、放量到 100% 后再删老实现。比「直接换、出事再说」的代价小得多。关键是别让它无限期并存。

## Q12 你说取证全是只读、还有 mock 适配器——那离线评测时怎么保证结果可复现，不被 mock 的随机数据污染？

**核心**：评测时在网关入口做**fixture 短路**——命中评测场景就返回固定的桩数据，且只读工具返回「受控的空」而不是 mock 的随机数据，保证同一条用例每次跑结果完全一致。

**展开**：
- **为什么不能直接用 mock**：mock 适配器是为了让系统在没接真实环境时能跑通，里面常带随机/仿真成分。拿它做评测，同一条用例两次跑可能给不同证据，评测结果就不可复现，没法用来判断「我改的代码到底让效果变好还是变差」。
- **fixture 短路**：评测进入一个「固定数据作用域」后，网关在选适配器之前就拦截：用例显式给了 fixture 的工具返回 fixture，写类工具返回成功桩，其余只读工具返回一个**受控的空结果**（明确的空，而不是 mock 的随机内容）。这样每条用例的输入完全可控、可复现。
- **仍走契约校验**：短路路径不是完全绕过网关，工具存在性、参数 schema 这些契约校验照走，保证评测跑的链路和生产链路在「契约」这一层是一致的，不会评测能过、生产因参数不合法挂掉。

**项目印证**：`gateway.py` 的 `_maybe_eval_fixture_response` 在 `call_tool` 最前面执行（早于 mock/real 选择），命中 `fixture_scope` 时：有 fixture 的工具回 fixture，`write_*`/`execute_action` 回成功桩，其余只读工具回受控 `{}`；短路前仍执行工具存在性与参数校验。

**追问预判**：「这跟普通 mock 测试有啥本质区别？」→ 普通 mock 是「替换掉某个函数」，作用域是测试代码层；fixture 短路是「在网关这个统一出口按场景注入确定数据」，作用域是整条工具调用链路。后者能保证不管哪个节点、走多少层、调多少工具，拿到的都是这条评测用例预设的确定输入——这是离线评测能拿来做回归基线的前提。

## Q13 Agent run 为什么不能跟普通 HTTP 请求绑死？你这里后台跑图真的安全吗？

**核心**：Agent run 是长任务，生命周期必须和客户端连接解耦；当前实现用 `POST /runs` 快速返回 `run_id`，再用 `BackgroundTasks + GraphRunner` 后台执行，状态、事件、checkpoint、evidence 都落库，让用户断开页面后还能回来查进度。

**展开**：
- **为什么不能绑 HTTP**：一次取证可能包含 LLM、K8s、DB、日志、指标等多个慢 I/O，普通 HTTP 长时间挂住会撞上 Nginx/ALB 超时、浏览器刷新、移动网络断连等问题。
- **任务和连接分离**：创建 run 只负责写入 `incident_runs` 并返回 `run_id`；真正的 graph 执行在后台线程里跑，前端通过轮询或 SSE 看状态。
- **后台执行不是无状态裸跑**：GraphRunner 每个节点完成后同步 run 进度、保存 checkpoint、持久化 evidence/RCA、写事件。即使前端断开，后端仍能继续推进和留痕。
- **现状边界**：当前使用 FastAPI `BackgroundTasks` 和同步 SQLAlchemy Session，适合单实例/开发到小规模生产；如果要多实例高可用，应该演进成任务队列 + 独立 Worker + lease/heartbeat。

**项目印证**：`incidents.py:create_run` 调 `RuntimeService.create_run()` 后立即 `background_tasks.add_task(_run_graph_bg, run_id, initial_state)`；`_run_graph_bg` 独立创建 DB session 并 `asyncio.run(runtime.start_run(...))`；`GraphRunner.run` 在 graph `astream` 每个节点输出后 `_save_checkpoint / _persist_evidence / _emit NODE_COMPLETED`。

**追问预判**：「BackgroundTasks 不是可靠队列，进程挂了任务不就没了？」→ 对，这是当前架构边界。因为状态和 checkpoint 已落库，具备恢复基础；生产级下一步是把 `incident_runs` 当任务表或接 MQ，Worker 通过 lease 领取 RUNNING/QUEUED 任务，崩溃后由超时 lease 重新领取，而不是依赖 API 进程内后台任务。

## Q14 多 Worker 或多实例部署时，为什么不能只靠内存 EventBus 和本地状态？

**核心**：多 Worker 是多进程，内存不共享；用户创建 run、订阅 SSE、审批恢复可能落到不同进程，所以 Agent 的唯一事实状态必须在数据库里，内存只能做短期推送优化。

**展开**：
- **进程内存不共享**：Uvicorn 多 worker 下每个进程都有自己的 `event_bus`、subscriber 列表和后台线程；A 进程发布的内存事件，B 进程的 SSE subscriber 看不到。
- **重启会丢内存**：部署重启或 worker 崩溃后，内存队列和订阅者全部消失；如果状态只在内存里，run 直接丢失。
- **DB 是事实源**：run 状态、事件、checkpoint、evidence、RCA 都要落库；内存 EventBus 只负责把新事件实时推给当前进程内 subscriber。
- **生产演进**：多实例下 SSE 推送应改成 DB 增量拉取、Redis Pub/Sub 或消息队列；订阅端重连时用 last_event_id 从 DB 补历史。

**项目印证**：`EventBus` 当前 `_subscribers` 是进程内 dict，`publish()` 同时写 `IncidentRunEvent` 表并 `_notify()` 内存订阅者；`RuntimeService.get_events()` 可从 DB 拉历史事件；`GraphRunner._save_checkpoint()` 把 state_json 写入 checkpoint 表。

**追问预判**：「那当前 SSE 断线能不能自动补发漏掉的事件？」→ 实时流本身不能。当前 `/stream` 新建 subscriber 后只收新事件；历史补偿靠 `GET /runs/{run_id}/events` 增量查询。要实现标准 SSE `Last-Event-ID` 恢复，需要 stream 端读取 Last-Event-ID，先从 DB 补发缺失事件，再订阅实时事件。

## Q15 SSE 事件流在这个模块里怎么保证可靠？断线、代理缓冲、心跳怎么处理？

**核心**：SSE 只是展示通道，不是任务可靠性的来源；可靠性靠 DB 事件表和 checkpoint，SSE 断了任务不能停，用户可以通过 events API 补历史。生产环境还需要补 Last-Event-ID、心跳和代理缓冲配置。

**展开**：
- **SSE 不驱动任务**：客户端断开只是看不到实时进度，GraphRunner 后台照常执行、落库、写事件。
- **历史事件要能补**：每个节点开始/完成/失败、checkpoint 保存、run 完成都写入事件表，前端刷新后可以通过 `/events` 拿历史。
- **代理风险**：Nginx 默认响应缓冲会破坏流式效果；ALB/Nginx idle timeout 可能在长节点执行期间断开连接。
- **生产补强**：服务端应每 15-30 秒发 heartbeat；Nginx 配 `proxy_buffering off` 和足够长 `proxy_read_timeout`；stream 端支持 Last-Event-ID 从 DB 补发。

**项目印证**：`incidents.py:stream_events` 用 `EventSourceResponse(generate())` 推送 `event_bus.iter_events(run_id)`；`EventBus.publish()` 先写 DB 再通知内存 subscriber；`get_run_events()` 已支持 `last_event_id / last_event_ts` 参数做增量查询。

**追问预判**：「既然 events API 能补历史，为什么还要 SSE？」→ SSE 是体验优化，让用户实时看到节点进度；DB events 是可靠性底座。二者职责不同：SSE 负责低延迟展示，DB 负责断线恢复和审计。

## Q16 checkpoint、evidence、事件是分开写的，如何避免状态和产物不一致？

**核心**：当前是**节点完成后的顺序持久化**：先同步 run 进度，再存 checkpoint，再持久化 evidence/RCA，再发 NODE_COMPLETED；这保证了大多数恢复场景有状态可回放，但它还不是严格事务原子提交。生产级要用单事务或 outbox 把状态、产物、事件绑定。

**展开**：
- **为什么会不一致**：如果 checkpoint 写成功、evidence 写失败，恢复时 state 里有 evidence，但 DB evidence 表缺一条；如果事件写成功但事务失败，前端可能看到一个实际没提交的完成事件。
- **当前兜底**：GraphRunner 用 `_persisted_evidence_ids` 做 evidence 去重，resume 时从 state 初始化已持久化集合；单条 evidence 持久化失败只 warning，不拖垮主流程。
- **严格做法**：节点输出、checkpoint、evidence 元数据、事件 outbox 应在同一个 DB 事务里提交；事务提交后由 outbox publisher 异步推 SSE/MQ。
- **为什么不把所有原始证据都塞进事务**：大 payload 会拖慢事务、撑爆 DB；应该 DB 存元数据、hash、URI，原始大对象进 OSS。

**项目印证**：`GraphRunner.run` 每个节点后依次 `_sync_run_progress()`、`_save_checkpoint()`、`_persist_evidence()`、`_persist_rca()`、`_emit(NODE_COMPLETED)`；`_persist_evidence()` 用 evidence_id 去重，异常只 `logger.warning`。

**追问预判**：「为什么不直接把这几个写操作放一个 SQLAlchemy transaction？」→ 可以，这是生产级收敛方向。但要注意 EventBus.publish 当前内部 `db.commit()`，会打破外层事务边界；要做原子提交，需要把事件先写 outbox 表，不在 publish 里直接 commit，再由后台 publisher 发送。

## Q17 如果 GraphRunner 在某个节点完成后、checkpoint 前崩了，恢复时会发生什么？

**核心**：恢复能力取决于**最近一次 checkpoint**；节点完成但 checkpoint 前崩溃，恢复只能回到上一个 checkpoint，因此节点可能被重跑。取证阶段是只读，允许重跑；写操作阶段必须靠幂等键和审批结果防重复执行。

**展开**：
- **checkpoint 是恢复边界**：GraphRunner 在每个节点输出后保存 state；崩溃后只能从最新 checkpoint 还原，不存在的 checkpoint 不能凭空恢复。
- **取证可重跑**：planner、fanout、aggregate、diagnose、critic 基本是只读/计算节点，重跑的主要代价是多一次工具查询或 LLM 调用，不会改线上状态。
- **写操作不可裸重跑**：executor 这类有副作用节点必须带 idempotency_key、approval_id、action_id，确保恢复或重试不会重复执行危险动作。
- **证据去重**：即使恢复后重新持久化证据，也要用 evidence_id 或唯一约束避免重复插入。

**项目印证**：checkpoint 由 `CheckpointsRepo.save(cp_id, run_id, node_name, serialized)` 写入；approval 恢复从 checkpoint 载入 state，`ApprovalRuntime.prepare_resume_state` 设置 `_resume_from_node`；取证 evidence 持久化用 `_persisted_evidence_ids` 做进程内去重。

**追问预判**：「进程内 `_persisted_evidence_ids` 重启后不就没了？」→ resume 时会从 checkpoint state 的 `evidence_items` 初始化一遍，但更硬的生产保障应该是 DB 层对 `(run_id, evidence_id)` 加唯一约束，进程内 set 只能做性能优化，不能当唯一正确性保障。

## Q18 这个模块能不能同时跑 100 个 run？怎么做并发准入控制？

**核心**：不能无限接。Agent run 是 LLM + 多工具 I/O 的复合长任务，必须有 admission control：限制同时运行的 run 数、每个 run 的专家并发、每类工具并发和模型并发，否则会把线程池、DB 连接池、LLM 连接池和云 API 配额打爆。

**展开**：
- **当前风险**：`POST /runs` 每次都 `background_tasks.add_task`，没有全局并发上限；100 个 run 会启动 100 个后台任务，fanout 再放大成数百个工具调用。
- **限制层级**：入口层限制 active run；fanout 层限制每个 run 的 agent 并发；工具网关按 tool/provider 限制并发；模型网关限制 LLM 请求并发和 token budget。
- **超限策略**：可以 429 拒绝，也可以进入 QUEUED 状态等待 Worker 领取；SRE 场景更推荐队列化，避免高峰时直接丢任务。
- **容量估算**：并发上限要结合 DB pool、LLM QPS、K8s/CMS/RDS API 限流、单 run 平均工具数和平均耗时算，不是随便配一个大数字。

**项目印证**：当前 `create_run` 没有检查 active run 数，专家池路径 `_evidence_fanout_v2` 里每个 run 自己 `asyncio.gather` 多个 SpecialistAgent，网关也没有全局 semaphore。这是后端拷打时要主动承认的明确改进点。

**追问预判**：「你会在哪里加？」→ 入口 `RuntimeService.create_run/start_run` 前加 `max_concurrent_runs` 准入；fanout 内加 per-run semaphore；ToolGateway 加按 tool/provider 维度的 semaphore；LLM client 前加模型并发和 token budget。生产再往后应改 Worker 队列，而不是 API 进程直接跑长任务。

**追问预判**：「超限后既然队列化，那队列化怎么实现？用什么工具？」→ 首选 **DB-backed queue**，不一上来就引 Kafka。OpsPilot 的 run、checkpoint、event、evidence 本来就在数据库里，队列也放在同一个事实源里，最容易做到可恢复、可审计、可查询状态。吞吐上来后，再迁移领取层到 Redis/Celery/RabbitMQ。

**展开补充**：
- **入队**：`POST /incidents/runs` 不直接 `BackgroundTasks.add_task()` 跑图，而是创建 `incident_run`，状态设为 `QUEUED`，返回 `run_id`。用户看到的是「已排队」，不是请求阻塞。
- **队列表字段**：可以扩展 `incident_runs`，也可以新建 `incident_run_queue`。关键字段包括 `status`、`priority`、`available_at`、`lease_owner`、`lease_expires_at`、`heartbeat_at`、`attempt_count`、`max_attempts`。
- **领取任务**：多个 Worker 用数据库行锁抢任务，典型 SQL 是 `SELECT ... WHERE status='QUEUED' AND available_at <= now() ORDER BY priority DESC, created_at ASC LIMIT 1 FOR UPDATE SKIP LOCKED`。`SKIP LOCKED` 保证多 Worker 并发领取时，同一个 run 只会被一个 Worker 拿到。
- **租约与心跳**：领取后把 run 改成 `RUNNING`，写入 `lease_owner` 和 `lease_expires_at`。Worker 执行期间定期刷新 `heartbeat_at/lease_expires_at`；如果 Worker 崩溃，lease 过期后 reaper 把任务重新放回 `QUEUED`。
- **恢复边界**：重新领取后从最近 checkpoint 恢复，不从头跑。队列系统按 at-least-once 设计，所以取证阶段必须只读，执行阶段必须靠 `idempotency_key / action_id / approval_id` 防重复副作用。
- **工具选型**：当前阶段用数据库队列最稳；如果只是 Python Worker 池，可以用 Celery + Redis/RabbitMQ，Celery 成熟但运维复杂；RQ 更轻但能力弱；RabbitMQ 适合任务分发和 ack；Kafka 更适合高吞吐事件流和回放，不是 run 执行队列的首选。

**一句话总结**：队列化不是简单塞一个 list，而是 `QUEUED + lease + heartbeat + SKIP LOCKED + checkpoint resume + 幂等执行` 这一整套可靠执行模型。

## Q19 外部工具调用成功但客户端超时，能不能重试？怎么避免重复副作用？

**核心**：取证阶段都是只读，超时重试通常安全；但一旦进入写操作，不能按网络错误无脑重试，必须用业务幂等键判断「外部到底执行没执行」，必要时走查询确认或补偿。

**展开**：
- **只读和写操作分开**：本模块 fanout 查 K8s、DB、日志、指标，都是只读，重试只会增加查询压力，不会改变线上状态。
- **超时语义不确定**：客户端超时只说明调用方没收到结果，不代表服务端没执行。对写操作，无脑重试可能执行两次。
- **幂等键**：写操作必须携带 `idempotency_key`，外部系统或本地执行审计用它去重；同一个动作重试时得到同一个结果。
- **补偿不是万能回滚**：有些外部动作无法完全撤销，所以更高风险动作要先 dry-run、审批、再执行，失败后进入人工补偿流程。

**项目印证**：取证工具在 ToolGateway 里声明 `requires_approval=False`，重试逻辑主要覆盖只读查询；执行动作在后续 `ControlledExecutor` 中有 `idempotency_key` 和审计，不属于 fanout 的普通重试范围；risk_gate/approval_interrupt 把高风险写操作挡在取证模块之后。

**追问预判**：「模型重试会不会导致同一个工具被执行两次？」→ 取证工具重复执行是可接受的只读重复查询；写工具不能暴露给模型自由调用，必须通过 remediation 生成 ActionSpec、risk_gate 审核、approval 后由 executor 带幂等键执行。

## Q20 大型证据和工具响应都写数据库，会不会把库打爆？怎么设计存储分层？

**核心**：数据库不应该承载所有原始大 payload；生产级应该 DB 存索引元数据和摘要，OSS/对象存储存原始证据，DB 里保留 URI、hash、大小、类型和脱敏摘要。

**展开**：
- **为什么不能全塞 DB**：日志、K8s events、metrics 时序、DB 诊断结果可能很大；全写 JSON 列会导致表膨胀、索引变慢、备份恢复变重。
- **分层存储**：DB 存 `evidence_id/run_id/tool/category/summary/raw_uri/hash/size/created_at`；原始 payload 写 OSS；必要时只把脱敏后的精简 payload 放 DB。
- **审计与复现**：hash 用来证明对象未被篡改，URI 用来复盘时拉原始证据，summary 用来列表页快速展示。
- **生命周期管理**：热数据保留在 DB，冷数据归档到 OSS；事件表和证据表按时间或 run_id 做分区/归档。

**项目印证**：当前 `EvidenceRepo.insert` 会把 `raw_payload` 写入 DB JSON 字段，适合开发和小规模数据；项目已有 OSS adapter 的 `write_evidence_to_oss / write_rca_to_oss`，说明归档通道已经预留。生产级应把大 payload 改成 OSS URI + DB 元数据。

**追问预判**：「那 diagnose 需要读原始证据怎么办？」→ diagnose 不应该吞整份原始日志，而应该读 aggregate 产出的摘要、异常信号和必要 evidence_ref；需要深挖时再按 URI 拉取局部证据，并做截断和脱敏，避免把大 payload 直接塞进 prompt。

## 这一份的「主心骨」（一句话穿起来）

**取证与质量门控的工程化，核心就一件事：把「调用外部世界」这件不可控的事，用一个统一网关包成「可校验、可重试、可审计、可隔离、可复现、可灰度」的受控操作——让模型只在确定性骨架划好的安全边界内做归纳。**
