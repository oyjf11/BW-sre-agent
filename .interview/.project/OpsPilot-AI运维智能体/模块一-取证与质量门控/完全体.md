# 运维故障智能体的高级功能与优化方向

从 Datadog 的智能运维助手、亚马逊云科技的运维智能体、PagerDuty 的智能运维平台等产品公开能力来看，业界正在把这类系统从"故障发生后的辅助分析工具"，升级成：

1. 持续理解系统
2. 主动发现异常
3. 自动开展调查
4. 受控执行处置
5. 验证系统恢复
6. 从历史事故中持续学习

当前这个智能体已经具备比较完整的证据采集、候选根因分析和质量门控骨架。

继续向上演进，真正高级的能力主要集中在以下十四个方面。

---

## 一、智能告警降噪与故障事件聚合

### 1. 解决什么问题

在真实生产环境中，一个故障可能同时触发：

- 20 个服务告警
- 200 条监控事件
- 数千条异常日志
- 多个容器实例重启
- 多个下游服务超时

如果每个告警都单独启动一次智能体调查，会导致：

- 相同故障被重复调查
- 模型和工具调用成本暴涨
- 多个调查任务得出相互冲突的结论
- 事故协作群中出现大量重复信息
- 值班人员难以判断哪些告警属于同一事故

因此，在故障接入节点之前，需要增加一层事件治理流程：

1. 接收原始事件
2. 统一事件格式
3. 合并重复事件
4. 关联相关事件
5. 聚合成故障事件
6. 创建智能体调查任务

### 2. 事件关联维度

系统可以从以下维度判断多个事件是否属于同一故障：

- 发生时间是否接近
- 涉及服务在拓扑上是否相邻
- 调用链标识是否相同
- 请求标识是否相同
- 错误指纹是否相同
- 是否来自同一次发布
- 是否依赖同一个下游服务
- 是否运行在同一个基础设施节点
- 异常指标变化趋势是否一致
- 影响用户范围是否重叠

> **一个告警 ≠ 一个事故。一组具有共同原因或共同影响链路的告警 = 一个事故。**

### 3. 可以增加的模块

- 事件格式统一器
- 告警去重器
- 事件关联器
- 事故合并器
- 事故拆分器

**事故拆分器同样重要。**有些告警虽然发生时间接近，但根因可能完全不同。系统在后续获得更多证据后，应允许将错误聚合的事故重新拆分，而不是一次聚合后永久固定。

## 二、动态服务拓扑和依赖关系图

这是运维故障智能体最重要的高级能力之一。

### 1. 普通实现的问题

如果系统只知道 `疑似异常服务 = 支付服务`，调查计划通常只能围绕支付服务本身展开。

但真实调用链可能是：

1. 支付服务
2. 订单服务
3. 缓存服务
4. 数据库
5. 第三方支付网关

**支付服务报错，不代表根因一定在支付服务。**它可能只是最先暴露问题的受影响节点。

### 2. 高级实现

系统需要建立统一的运行时服务关系图。

图中的节点可以包括：

- 业务服务
- 容器实例
- 计算节点
- 数据库
- 消息队列
- 缓存
- 接口
- 发布记录
- 代码仓库
- 服务负责人
- 故障处理手册
- 服务等级目标
- 云资源
- 配置项

节点之间的关系可以包括：

- 调用
- 依赖
- 部署到
- 归属负责人
- 读取
- 写入
- 生产消息
- 消费消息
- 被某次变更影响
- 被某个监控项观测
- 共享基础设施
- 共享数据库

### 3. 拓扑数据来源

可以从以下系统持续同步：

- 分布式调用链
- 容器编排平台接口
- 配置管理数据库
- 服务注册中心
- 接口网关
- 代码仓库
- 持续集成与发布系统
- 基础设施配置文件
- 云厂商资源接口
- 服务目录
- 人工维护的架构关系

### 4. 对智能体的提升

调查计划不再只是 `查询支付服务日志`，而是能够自动扩展调查边界：

1. 发现支付服务异常
2. 查询直接上游服务
3. 查询直接下游服务
4. 查询共享数据库和缓存
5. 查询同期发布记录
6. 查询关联基础设施
7. 评估可能受影响的其他服务

可以增加一个"拓扑调查范围扩展器"。

| 维度 | 内容 |
|------|------|
| 输入 | 疑似异常服务、故障类型、调查时间范围 |
| 输出 | 受影响的局部拓扑、关键依赖项、故障影响范围、可能涉及的服务负责人、优先调查的上下游节点 |

## 三、基于系统变更的根因优先级排序

生产故障经常与系统变更有关，例如：

- 代码发布
- 配置修改
- 功能开关变更
- 数据库结构变更
- 容器编排配置变更
- 第三方依赖升级
- 权限策略修改
- 网络规则修改
- 扩缩容策略调整
- 基础设施配置变更

### 1. 建立统一变更事件模型

系统需要将来自不同平台的变更记录统一为一个标准结构：

| 字段 | 字段 | 字段 |
|------|------|------|
| 变更编号 | 变更类型 | 涉及服务 |
| 运行环境 | 开始时间 | 完成时间 |
| 操作人员 | 代码提交编号 | 发布版本 |
| 变更资源 | 风险等级 | 审批记录 |
| 回滚方式 | | |

### 2. 计算变更与故障的关联度

可以综合以下因素计算：

- 变更与异常发生时间的接近程度
- 变更节点与异常节点的拓扑距离
- 变更影响范围与故障影响范围的重叠度
- 同类变更历史上引发故障的概率
- 变更完成时间与指标突变时间的吻合度
- 新旧版本实例之间的异常差异

例如：

```
14:00  发布 2.8 版本
14:03  错误率上升
14:04  延迟上升
       → 只有新版本实例出现异常
```

这时，**"新版本引入回归问题"应当获得很高的根因优先级。**

### 3. 避免错误归因

不能因为故障前刚好发生了发布，就直接认为发布是根因。

还需要执行反事实检查：

- 旧版本实例是否正常
- 未参与发布的实例是否也异常
- 同一版本在其他环境是否正常
- 回滚后指标是否恢复
- 异常是否在发布前已经出现
- 共享下游是否同时出现问题

> **变更记录只能提高某个假设的调查优先级，不能单独作为根因结论。**

## 四、显式假设树与证伪机制

当前系统已经有 `生成根因候选 → 质量审核`，更高级的实现是把候选根因升级为一棵显式假设树。

### 1. 假设对象需要保存什么

每个根因假设至少包含：

- 假设编号
- 假设描述
- 初始概率
- 支持证据
- 反对证据
- 仍需执行的检查
- 当前状态
- 当前置信度
- 父级假设
- 子级假设

假设状态可以统一为：

| 状态 | 含义 |
|------|------|
| 待验证 | 尚未收集到足够证据 |
| 已经验证 | 证据充分支持该假设 |
| 已经否定 | 证据明确推翻该假设 |
| 暂时无法确认 | 当前工具无法获取所需证据 |

### 2. 调查过程

1. 提出多个候选假设
2. 识别每个假设缺少什么证据
3. 选择最能区分多个假设的检查
4. 调用工具获得证据
5. 更新各个假设的概率
6. 淘汰不成立的假设
7. 对高概率假设继续深入

例如当前有三个候选：

- 假设一：新版本代码出现回归问题
- 假设二：数据库连接池耗尽
- 假设三：第三方服务超时

不需要把三个方向全部查到底。可以先执行最有区分度的一项检查：

> 新旧版本实例的错误率是否存在明显差异？

如果只有新版本异常 → 假设一的概率明显上升，假设二和假设三的概率下降。

### 3. 核心优化目标

这种设计的本质是：**让每一次工具调用尽可能减少最大的不确定性。**

这样可以同时降低：

- 调查时间
- 工具调用数量
- 模型调用成本
- 无效调查路径
- 重复查询

## 五、完整事故时间线与因果顺序分析

简单的事件关联只能看到 `发生了发布 + 错误率也升高了`。高级系统需要重建完整事故时间线：

```
13:58  配置发生修改
14:00  发布开始
14:02  新容器实例进入就绪状态
14:03  数据库连接数升高
14:04  高分位延迟升高
14:05  服务错误率告警
14:07  自动扩容
14:09  下游服务开始超时
```

### 1. 多源时间对齐

不同系统记录的时间可能存在：

- 时区不同
- 主机时钟漂移
- 日志写入延迟
- 数据采集延迟
- 聚合窗口不同
- 秒级和分钟级粒度不同

因此每条事件最好同时保存三项时间：**事件真实发生时间、监控系统观察到的时间、数据进入平台的时间。**

### 2. 变化点识别

不能只判断指标是否超过固定阈值，还要识别指标从什么时候开始发生统计变化。例如：

- 平均值突然改变
- 波动幅度突然增大
- 原有周期规律被破坏
- 多个关联指标同步变化
- 指标变化速度突然加快

### 3. 因果顺序约束

根因至少应满足：**原因发生时间 ≤ 结果发生时间。**

例如：服务在 14:05 已经开始报错，数据库在 14:20 才出现异常 → 数据库异常更可能是故障传播后的结果，而不是最初根因。

**时间线不能直接证明因果关系，但可以排除明显不符合时间顺序的候选根因。**

## 六、证据溯源、证据快照和调查重放

系统走向生产后，必须做到：**对于任何一个根因结论，都可以重新找到当时的原始数据、查询条件和推理过程。**

### 1. 证据对象不能只保存摘要

每条证据至少应记录：

| 字段 | 字段 | 字段 |
|------|------|------|
| 证据编号 | 数据来源类型 | 使用的工具 |
| 原始查询语句 | 查询参数 | 查询时间范围 |
| 采集时间 | 原始数据快照位置 | 标准化后的内容 |
| 内容校验值 | 解析器版本 | 工具版本 |
| 智能体版本 | 访问权限范围 | |

### 2. 证据快照

将当时查询到的原始日志、指标、调用链和变更记录保存到对象存储。

这样可以避免：

- 日志过期
- 指标滚动聚合
- 数据被后续修改
- 原监控系统无法重现
- 事故复盘时找不到原始上下文

### 3. 确定性重放

使用 `原始证据 + 新模型 / 新提示词 / 新诊断逻辑` 重新运行根因分析和质量审核。

这样可以判断：

- 新模型是否比旧模型更准确
- 新提示词是否引入回归
- 新门控规则是否更合理
- 某次结论变化到底来自哪里

### 4. 反事实重放

例如：

- 如果当时没有发布记录证据，系统是否会错误地把数据库判断为根因？
- 如果去掉某条关键日志，质量门控是否仍然会错误放行？

这类能力对离线评测、事故复盘和模型升级非常重要。

## 七、多层记忆，而不是简单知识库检索

生产级运维智能体至少需要四类记忆。

### 1. 稳定知识记忆

保存相对稳定的系统知识：

- 架构文档
- 服务说明
- 故障处理手册
- 服务等级目标
- 常见故障手册
- 服务负责人
- 数据库结构
- 接口说明
- 依赖关系
- 权限边界

### 2. 历史事故记忆

保存过去发生过的真实事故：

- 事故症状
- 告警组合
- 证据组合
- 最终根因
- 修复动作
- 验证结果
- 人工修正
- 事故影响
- 复盘结论

### 3. 调查方法记忆

保存"某类问题应该怎么查"：

- 缓存故障应该优先检查哪些指标
- 发布故障需要检查哪些证据
- 数据库连接问题需要执行哪些查询
- 某个团队常用哪些诊断命令
- 某个服务有哪些特殊排障步骤

### 4. 当前任务记忆

保存一次调查过程中不断变化的状态：

- 已经验证的假设
- 已经否定的假设
- 尚未完成的检查
- 工具调用失败记录
- 当前调查预算
- 剩余调查时间
- 当前最高概率根因

### 5. 相似事故检索优化

相似事故不能只依靠告警文本相似度。还应该综合：

- 服务拓扑相似度
- 指标变化模式
- 错误指纹
- 变更类型
- 证据组合
- 最终根因
- 故障传播路径
- 处置动作

> **事故相似度 ≠ 文本相似度。**两个事故的告警描述可能完全不同，但拓扑位置、指标模式和根因可能高度相似。

## 八、分级自治与受控自动修复

成熟系统不会简单设置 `自动修复开启 / 自动修复关闭`，而是建立分级自治机制。

### 1. 推荐五级自治

| 等级 | 智能体权限 |
|:----:|-----------|
| 一级 | 只观察、整理和总结 |
| 二级 | 提出调查方向和检查建议 |
| 三级 | 自动执行只读取证 |
| 四级 | 生成修复方案，人工批准后执行 |
| 五级 | 低风险动作自动执行，高风险动作必须审批 |
| 最高级 | 对经过充分验证的特定故障类型实现闭环自治 |

### 2. 动作风险计算

动作风险可以综合以下因素：

- 影响范围
- 是否容易回滚
- 根因判断置信度
- 服务重要程度
- 数据敏感程度
- 动作是否可能造成数据损坏
- 是否经过历史验证

### 3. 适合自动执行的动作

- 重跑无状态任务
- 清理临时缓存
- 扩容到预设上限
- 切换已经验证过的功能开关
- 回滚到已知健康版本
- 重启单个无状态实例
- 暂时摘除异常实例

### 4. 不适合直接自动执行的动作

- 删除数据库数据
- 修改安全权限策略
- 跨区域切换流量
- 数据库主从切换
- 执行未经验证的数据修复语句
- 修改大范围网络规则
- 批量删除云资源

### 5. 每个动作必须携带的安全信息

| 字段 | 字段 | 字段 |
|------|------|------|
| 执行前置条件 | 预期效果 | 验证查询 |
| 回滚动作 | 执行超时时间 | 幂等标识 |
| 最大允许影响范围 | 允许执行次数 | 审批要求 |

### 6. 安全执行链路

1. 检查执行前置条件
2. 生成执行计划
3. 策略引擎审核
4. 小范围试运行
5. 观察关键指标
6. 扩大执行范围或自动回滚

这里的小范围试运行可以是：

- 只处理一个实例
- 只处理少量流量
- 只切换一个可用区
- 只对测试租户生效
- 只运行一个短观察窗口

## 九、闭环验证不能只看"告警消失"

很多基础智能体会把 `命令执行成功` 错误地当成 `故障已经修复`。但命令成功只说明工具执行完成，不代表系统恢复。

高级验证必须覆盖：

1. 技术指标恢复
2. 业务指标恢复
3. 用户体验恢复
4. 没有产生新副作用
5. 恢复状态持续稳定

### 1. 技术指标

- 错误率回落
- 高分位延迟恢复
- 处理器和内存恢复
- 数据库连接池恢复
- 容器实例停止反复重启
- 消息堆积开始下降
- 调用链异常比例恢复

### 2. 业务指标

- 下单成功率
- 支付成功率
- 登录成功率
- 核心交易量
- 业务漏斗转化率
- 订单积压量
- 核心任务完成率

### 3. 用户体验指标

- 前端真实用户错误率
- 页面加载时间
- 客户投诉数量
- 合成探测结果
- 不同地域的访问成功率
- 移动端崩溃率

### 4. 稳定观察窗口

不能因为指标恢复十秒就宣布事故结束。

需设置最小稳定观察时间：**连续十分钟满足服务等级目标，并且没有出现新的异常，才判定系统已经恢复。**

不同事故可以配置不同的稳定窗口：

| 事故类型 | 稳定窗口 |
|---------|---------|
| 普通接口故障 | 5 至 10 分钟 |
| 数据库切换 | 15 至 30 分钟 |
| 消息积压 | 需观察积压是否持续下降 |
| 支付故障 | 还需核对业务对账结果 |

## 十、主动式故障预防

高级阶段不再等告警发生后才启动调查。系统可以周期性执行主动检查。

### 1. 异常趋势巡检

例如：

- 数据库连接池使用率连续升高
- 磁盘空间预计七天后耗尽
- 消息队列积压长期增长
- 高分位延迟逐周恶化
- 内存使用量持续爬升
- 错误率虽然未告警但趋势持续变差

### 2. 发布前风险审查

在发布之前自动检查：

- 本次变更是否触及关键调用链
- 是否修改高风险配置
- 是否缺少监控和告警
- 是否没有明确回滚方案
- 是否与历史事故模式相似
- 是否缺少必要测试
- 是否同时修改了多个高风险依赖

### 3. 可观测性缺口发现

例如：

- 关键服务没有服务等级目标
- 调用链在某个服务处断裂
- 日志缺少请求标识
- 高风险接口没有合成测试
- 数据库缺少关键监控指标
- 关键告警没有关联故障处理手册
- 服务没有明确负责人

### 4. 故障处理手册健康检查

周期检查：

- 处理手册是否已经过期
- 命令是否还能执行
- 负责人是否仍然有效
- 文档链接是否失效
- 操作步骤是否符合当前架构
- 回滚步骤是否完整
- 是否缺少风险说明

## 十一、智能体自适应编排与成本优化

多专家并行调查虽然速度快，但成本可能很高。

如果每次事故都固定启动 `日志专家 + 指标专家 + 容器专家 + 数据库专家 + 发布专家 + 网络专家`，其中很多调用可能没有价值。

### 1. 分层漏斗式取证

1. 低成本快速筛查
2. 中等成本定向调查
3. 高成本深度分析

例如：先查询发布记录、核心指标和错误指纹 → 判断最可能的问题方向 → 再启动数据库专家或网络专家。

### 2. 动态选择专家

| 故障类型 | 执行专家 |
|---------|---------|
| 发布回归故障 | 发布专家 + 日志专家 + 指标专家 |
| 数据库性能下降 | 数据库专家 + 指标专家 + 调用链专家 |
| 网络故障 | 网络专家 + 容器专家 + 调用链专家 |
| 缓存故障 | 缓存专家 + 指标专家 + 应用日志专家 |

### 3. 模型分层

| 层级 | 负责内容 |
|------|---------|
| 小模型 | 故障分类、文本摘要、工具参数生成、格式修复、简单信息抽取 |
| 大模型 | 复杂因果分析、跨证据矛盾判断、根因候选生成、高难度调查计划调整 |
| 规则引擎 | 权限控制、流程路由、审批判断、重试策略、停止条件、风险控制 |

### 4. 查询缓存

在同一个事故调查窗口内，满足以下条件的查询不重复执行：

- 相同工具
- 相同参数
- 相同时间范围
- 相同数据版本

### 5. 调查预算控制

每次调查应设置：

- 最大工具调用次数
- 最大模型使用量
- 最大调查时长
- 最大专家数量
- 最大重新规划次数
- 最大补充取证次数

**调查计划需要在预算范围内，优先选择信息价值最高的检查。**

## 十二、智能体自身的可观测性

不仅要观测被调查的生产系统，还要观测智能体本身。

### 1. 运行指标

| 指标 | 说明 |
|------|------|
| 调查任务成功率 | 最终给出有效结论的比例 |
| 平均调查时长 | 从创建到结束的耗时 |
| 工具调用成功率 | 单次工具调用的成功概率 |
| 工具调用高分位延迟 | P99 工具调用响应时间 |
| 重新规划比例 | 需要再次规划的任务占比 |
| 转人工比例 | 超出能力范围转人工的比例 |
| 平均调用成本 | 模型+工具单次调查的费用 |
| 平均工具调用数量 | 每次调查使用的工具次数 |

### 2. 诊断质量指标

| 指标 | 说明 |
|------|------|
| 第一根因命中率 | 首个候选即为真实根因 |
| 前三根因覆盖率 | 前三候选至少包含真实根因 |
| 证据引用准确率 | 引用的证据是否真实存在 |
| 无证据结论比例 | 未引用证据的结论占比 |
| 矛盾识别率 | 正确识别证据间矛盾的能力 |
| 根因排序质量 | 真实根因排第一的频率 |

### 3. 门控质量指标

| 指标 | 说明 |
|------|------|
| 错误放行率 | 证据不足却被通过的占比 |
| 错误拦截率 | 证据充分却被拦截的占比 |
| 补充取证有效率 | 补充取证后提升了判断质量 |
| 重新规划有效率 | 重新规划后产出更准确 |
| 无效循环比例 | 门控-补充-再门控的无限循环 |
| 证据不足时正确转人工比例 | 该转人工时是否真的转了 |

### 4. 处置安全指标

| 指标 | 说明 |
|------|------|
| 自动处置成功率 | 自动动作执行后达到预期 |
| 自动回滚率 | 自动动作被撤回的比例 |
| 处置副作用发生率 | 修复动作引入新问题 |
| 人工否决率 | 人工审批时拒绝的比例 |
| 重复执行率 | 同一动作多次执行 |
| 越权调用拦截率 | 安全策略拦截的比例 |

### 5. 业务价值指标

| 指标 | 说明 |
|------|------|
| 平均故障发现时间 | 故障发生到被发现的时间 |
| 平均故障确认时间 | 发现到确认是真实故障的时间 |
| 平均故障恢复时间 | 确认到恢复的时间 |
| 人工调查耗时 | 人工参与调查的时间成本 |
| 夜间值班人员被唤醒次数 | 减少夜间打扰 |
| 重复事故发生率 | 同一根因事故再次发生 |
| 人工参与步骤数量 | 智能体完成的比例 |

### 6. 完整运行链路追踪

必须能看到：

1. 调查计划为什么选择这些专家
2. 每个专家调用了什么工具
3. 工具返回了什么状态
4. 证据如何被标准化和摘要
5. 候选根因置信度如何变化
6. 质量审核为什么放行或拦截
7. 执行了什么处置动作
8. 最终如何验证系统恢复

## 十三、故障仿真、故障注入和离线评测

没有完整评测体系，就不能安全扩大智能体自治范围。

### 1. 历史事故数据集

从真实事故复盘中构建：

- 输入告警
- 固定证据
- 标准根因
- 允许执行的动作
- 禁止执行的动作
- 最终恢复条件
- 人工复盘结论

### 2. 合成故障数据集

可以注入：

- 容器内存溢出
- 数据库连接池耗尽
- 缓存热点键
- 下游服务超时
- 域名解析失败
- 错误版本发布
- 配置漂移
- 消息队列积压
- 网络丢包
- 节点磁盘耗尽

### 3. 对抗性案例

专门测试：

- 多条证据互相矛盾
- 工具返回空结果
- 工具返回错误数据
- 故障处理手册过期
- 告警描述具有误导性
- 多个故障同时发生
- 根因不在最初怀疑服务
- 最近发生了发布但发布不是根因
- 高置信度候选缺乏直接证据

### 4. 分节点评测

不能只评测最终答案，还需要逐个节点检查：

1. 故障初步分类是否正确
2. 调查计划是否覆盖关键观测面
3. 证据查询是否有效
4. 证据聚合是否遗漏矛盾
5. 根因分析是否引用真实证据
6. 质量门控是否正确拦截
7. 处置方案是否安全
8. 执行结果是否真正恢复系统

通过分节点评测，才能准确定位系统问题究竟出现在哪个环节：

| 阶段 | 问题定位 |
|------|---------|
| 计划错误 | 调查方向没选对 |
| 工具错误 | 查询返回了错误数据 |
| 证据不足 | 关键信息未被采集 |
| 聚合错误 | 多条证据被错误合并 |
| 推理错误 | 正确证据但推导错误 |
| 门控错误 | 应该拦截但放行了 |
| 执行错误 | 处置动作执行失败 |
| 验证错误 | 恢复判断不准确 |

## 十四、事故协同与自动化事故指挥

大型事故不只是技术调查问题，还涉及组织协调。

高级系统可以承担：

- 自动创建事故协作群
- 自动拉入相关服务负责人
- 定时发布事故状态
- 生成当前影响范围
- 维护待办事项
- 记录关键决策
- 升级事故级别
- 通知业务负责人
- 创建故障工单
- 同步项目管理系统
- 生成事后事故报告

它相当于一个**智能事故协调员**。

但它不应替代人类事故负责人做高风险业务决策。它更适合承担：

- 信息汇总
- 时间线维护
- 行动项记录
- 状态同步
- 人员通知
- 会议纪要
- 复盘材料整理

## 对当前智能体的建设优先级建议

### 第一优先级：最值得先做

这些能力能够直接把当前系统提升一个层级：

1. 动态服务拓扑和影响范围分析
2. 统一变更事件建模
3. 显式假设树与证伪机制
4. 完整事故时间线
5. 证据快照和调查重放
6. 多维度闭环验证
7. 智能体自身可观测性
8. 离线评测体系

这些能力最能体现系统的技术深度，也最适合用于高级智能体、智能运维和人工智能架构岗位面试。

---

### 第二优先级：生产化增强

1. 告警去重与事故聚合
2. 多层事故记忆
3. 自适应专家选择
4. 工具调用预算控制
5. 分级自治
6. 小范围试运行和自动回滚
7. 事故协同和自动化指挥

---

### 第三优先级：高级但实现成本较高

1. 复杂因果推断
2. 主动异常预防
3. 自动发现可观测性缺口
4. 自动生成代码修复或基础设施配置修复
5. 数字孪生和故障仿真
6. 跨事故持续学习
7. 面向常见故障的完全闭环自治

---

## 最终形态

当前系统大致是：

1. 接收故障
2. 制定调查计划
3. 多专家取证
4. 汇总证据
5. 分析根因
6. 质量门控
7. 制定处置方案
8. 执行处置
9. 验证恢复

业界高级形态会扩展为：

1. 持续感知系统状态
2. 告警降噪与事故聚合
3. 动态识别服务拓扑和影响范围
4. 关联近期系统变更
5. 建立根因假设树并持续证伪
6. 汇总多源证据并重建事故时间线
7. 执行证据质量门控
8. 判断处置风险等级
9. 小范围试运行
10. 多维度验证恢复
11. 失败时自动回滚
12. 生成事故报告并沉淀知识
13. 主动识别未来风险

> **真正的技术分水岭不是再增加几个专家智能体，而是：从固定流程的多智能体调查系统，升级为具备拓扑理解、假设证伪、证据重放、渐进自治、闭环验证和持续学习能力的智能运维系统。**
