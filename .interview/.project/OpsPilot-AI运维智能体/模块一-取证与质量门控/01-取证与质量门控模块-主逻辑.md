# 模块一：取证与质量门控（主逻辑）

> 这份只讲一件事：**这个模块到底在干什么、为什么这么设计**。
> 目标是你能看懂、能复述，不是堆术语。先不碰任何 bug。
> 对应代码：`backend/app/graph/nodes/__init__.py` 里的 planner / evidence_fanout / aggregate / diagnose / critic 五个节点。

---

## 0. 一句话：这个模块是 OpsPilot 的「查案子」环节

整个 OpsPilot 处理一次故障，分三大段：

```
入口定性段  →  【取证与质量门控段】  →  处置段
(收工单、分类)    (这份文档讲的)        (出方案、审批、执行)
```

这个模块就是中间那段，干的是**「查案子」**：

- 进来时：手上有一张「已经定性的工单」——知道是哪个服务、什么类型的故障（比如"发布回归"）。
- 出去时：要么交出一份**有证据支撑的根因判断**（够格了，放行去处置），要么说**"证据不够，我得再查"**（退回去重查）。

**核心理念一句话**：不让大模型上来就猜根因，而是**先派人去查证据、查够了才让它下结论**。

---

## 1. 这个模块吃什么、吐什么

| | 内容 | 谁产出的 |
|---|---|---|
| **吃（输入）** | 一张定性工单：`triage` 结果（故障类型、怀疑的服务、环境） | 上游 triage 节点 |
| **吐（输出）** | ①一堆证据 `evidence_items` ②一个质量分 `quality_score` ③一组根因候选 `root_cause_candidates` ④一个门控裁决 `critic_decision`（放行 / 退回） | 本模块 |

记住这个**「吃定性、吐根因+裁决」**，整个模块就是把左边变成右边。

---

## 2. 五步主逻辑（这是骨架，背这个）

```
① planner    排调查计划：这种故障，该查哪些地方？
     ↓
② fanout     并行取证：派一队人，同时去查（只看不动）
     ↓
③ aggregate  汇总打分：证据揉一起，打个"够不够"的分
     ↓
④ diagnose   下根因假设：综合证据，给出可能的根因
     ↓
⑤ critic     质量门控：分够 → 放行；分不够 → 退回① 或 ②
```

下面一步步说，**每一步都回答"上一步给了我什么，我为什么必须存在"**。

---

### ① planner —— 排调查计划

**它拿到的**：故障类型（比如 `deployment_regression` 发布回归）+ 怀疑的服务列表。

**它干什么**：像一个老练的值班长，**按故障类型查一张"该查哪些地方"的对照表**，列出一组**调查任务**。

举例——如果是「发布回归」，它会排：
- 查**部署历史**（`deployments`）：最近发布了什么？
- 查**应用日志**（`logs`）：报错了吗？
- 查 **K8s** 状态：Pod 起来了吗、有没有崩溃重启？
- 查**监控指标**（`metrics`）：5xx、延迟涨了吗？
- 查**数据库**（`db`）：有没有慢查询？
- 查**历史处置手册**（`runbook`）：这类问题以前怎么处理的？

> 关键点：**查什么不是大模型临场拍的，是按故障类型预先编排好的**。发布回归就重点查部署和 rollout 状态，资源耗尽就重点查指标和 K8s 饱和度。这叫"确定性编排"——把"该查哪"这种关键决定交给固定规则，不交给模型。

**它吐出**：一个调查计划(investigation_plan)，里面是一串调查任务(InvestigationTask)（每个任务 = 查哪个类别 + 用哪个工具 + 查哪个服务）。

代码：`__init__.py:227`

---

### ② evidence_fanout —— 并行取证（这模块的"心脏动作"）

**它拿到的**：上一步的调查计划（一串任务）。

**它干什么**：把这串任务**同时**打出去执行——这就是"扇出"（fanout）这个词的意思：从一个点，散开成很多条并行的线。

三个关键性质，每个都要能讲：

1. **并行**：用并发收集器(asyncio.gather)一次性发起所有查询，不是查完一个再查下一个。查日志、查 K8s、查数据库**同时进行**，谁先回来算谁的。一个慢的不会卡住其他的。
2. **只读**：这一队人**只看、不动手**。查日志、查状态、查指标，全是只读操作。绝不会在取证阶段改任何线上东西。（要动手是后面"处置段"的事，且要过审批。）
3. **互不依赖**：每条线查自己的，不抢同一个资源、不互相等。所以**单条线挂了，不影响别的线**。

**它吐出**：一堆 `EvidenceItem`（证据条目）——每条证据带着：哪个工具查的、属于哪个类别、内容摘要、还有一个**置信度**（这条证据有多可信，0~1）。

代码：`__init__.py:406`

---

### ③ evidence_aggregate —— 汇总 + 打质量分

**它拿到的**：上一步并行查回来的一堆零散证据。

**它干什么**：当**"会计"**——把散落的证据揉到一起，算出一个**质量分**（`quality_score`），回答一个问题：

> **"我现在手上的证据，够不够下结论？"**

这个分大致看两件事（直觉版）：
- **覆盖够不够广**：该查的几个方面，是不是都查到了有用的东西？只查到日志、其他都空，那覆盖就差。
- **证据本身可不可信**：查回来的东西置信度高不高。

#### 为什么"覆盖度"是个变量？（派出去几个不是定死了吗）

容易有个疑问：派几路去查，planner 排计划时不就定死了吗？覆盖度怎么会变？

**关键在于：派出去 ≠ 带着有用东西回来。** 一个派出去的调查任务，回来时是这**四种状态**之一（`evidence_utils.py:6`）：

| 回来的状态 | 什么意思 | 算不算"覆盖到"？ |
|---|---|---|
| **SUCCESS_USABLE** | 跑通了，**带回了有用证据** | ✅ 算 |
| **SUCCESS_EMPTY** | 跑通了，但**啥也没查到**（空的） | ❌ 不算 |
| **FAILED_CONFIG** | **没跑成**——配置问题（没凭据、IP 没加白名单、real 模式下工具没接） | ❌ 不算 |
| **FAILED_RUNTIME** | **跑挂了**——运行时报错（超时、连不上数据库、K8s 没响应） | ❌ 不算 |

覆盖度**只数第一种**（`evidence_utils.py:157`）。所以：

- **派几个** = 定死的（planner 排计划时定，比如 6 个方面）。
- **覆盖到几个** = **不定**，取决于这 6 个里有几个真带回了有用证据。

举例：planner 派 6 路（部署/日志/K8s/指标/数据库/手册），结果——部署、日志、指标、K8s 查到了 ✅；数据库连接超时（FAILED_RUNTIME）❌；手册查了但没匹配（SUCCESS_EMPTY）❌。那覆盖就是 **4/6**，不是 6/6。

**一句话**：覆盖度衡量的不是"我计划查多广"，而是**"我实际真查到了多广"**——它反映这次取证的**实际成功率**，而成功率天生是变量。计划很丰满、但一半工具挂了或查空了，正是质量分要抓的"调查没打透"。

> 为什么需要这一步：并行查回来的是**一堆原始碎片**，有的有用、有的是空的、有的可信、有的存疑。**不先汇总打分，下游就没法判断"现在能不能下结论"**。这个分就是后面门控（critic）做决定的**主要依据**。

**它吐出**：质量分(quality_score) + 一份证据汇总摘要。

代码：`__init__.py:783`

---

### ④ diagnose —— 下根因假设

**它拿到的**：汇总后的证据 + 历史相似案例（之前 retrieve_memory 捞的）。

**它干什么**：这一步才真正**让大模型上场**——综合所有证据，给出**一组排好序的根因候选**（`root_cause_candidates`）。

每个候选带着：
- `hypothesis`：根因假设（比如"最近的发布引入了数据库慢查询，导致接口超时"）
- `confidence`：这个假设有多确信（0~1）
- 支撑它的证据有哪些

> 注意顺序：**先取证、先打分，最后才让模型下结论**。模型不是凭空猜，是**站在已经查到的证据上**总结。这就是"证据驱动"——把模型的角色从"猜答案"降级成"基于证据归纳答案"。

**它吐出**：根因候选列表(root_cause_candidates)，按置信度排序。

代码：`__init__.py:895`

---

### ⑤ critic —— 质量门控（这模块的"灵魂"）

**它拿到的**：质量分 + 根因候选。

**它干什么**：当**"质检员 / 关卡"**。它**自己不查证据、不下结论**，只做一件事——**判断"现在够不够格进入处置段"**，然后决定往哪走：

| 裁决 | 什么意思 | 往哪走 |
|---|---|---|
| **PASS** | 证据够、结论靠谱 | 放行 → 进处置段（出方案） |
| **NEED_MORE_EVIDENCE** | 证据不够 | **退一步**，回 ② 再查一轮（计划不变，多取点证据） |
| **REPLAN** | 查的方向就不对 | **退两步**，回 ① 重排调查计划 |
| （转人工） | 来回查几轮还摆不平 | 停下，交给人 |

> 为什么需要这个关卡：大模型最危险的毛病是**"自信地猜错"**——它会用很笃定的语气给你一个错根因。如果直接拿这个去修线上，就闯祸了。所以在"下结论"和"动手修"之间**硬插一道关卡**：先检查证据够不够硬，不够就**绕回去再查**，宁可慢，不要错。

**防失控设计**：来回退查不能无限循环。**最多转 2 圈**，还摆不平就**转人工**，不会让它自己一直烧下去。

**它吐出**：四选一的裁决(critic_decision)，决定整个模块是放行还是回炉。

代码：`__init__.py:1074`

## 3. 串起来：一个完整例子走一遍

故障：「支付服务发布后 5xx 升高」，定性为**发布回归**。

```
① planner：这是发布回归 → 排计划：查部署历史、日志、K8s、指标、数据库、手册
        ↓
② fanout：6 路并行查 →
        部署历史：30 分钟前刚发过版 ✓
        日志：大量 "数据库连接超时" 报错 ✓
        K8s：Pod 正常 ✓
        指标：5xx 从 0.1% 涨到 8% ✓
        数据库：出现慢查询，连接数打满 ✓
        手册：查到一条相关处置记录 ✓
        ↓
③ aggregate：6 个方面都查到了有用证据，覆盖广、置信度高 → 质量分 = 高
        ↓
④ diagnose：综合证据 → 根因候选：
        "新版本引入了未加索引的慢查询，拖垮数据库连接池，导致支付接口超时"（置信度 0.85）
        ↓
⑤ critic：质量分够高、根因置信度够 → 裁决 PASS → 放行进处置段
```

如果换一种情况——② 里只有日志查到了东西，其他全空：
```
③ aggregate：覆盖太窄 → 质量分 = 低
④ diagnose：证据太少，只能给个置信度 0.3 的猜测
⑤ critic：质量分不够 → 裁决 NEED_MORE_EVIDENCE → 退回 ② 再查一轮
```

---

## 4. 这个模块的一句话总结（背这句）

> **派队并行只读取证 → 汇总打个"够不够"的质量分 → 模型基于证据下根因 → 关卡按质量分放行或退回，最多转 2 圈转人工。**
>
> 一切是为了一个目的：**不让大模型上来就猜，证据查够了、过了门控，才允许它下结论。**
