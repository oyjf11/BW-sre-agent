## Q1 拿到一个故障，为什么不直接让大模型给根因，要绕一圈先取证？

**核心**：证据驱动——大模型最大的风险是「自信地猜错」，所以把它的角色从「猜答案」降级成「基于已查到的证据归纳答案」。

**展开**：
- **直接猜的后果**：模型只凭工单描述就能脑补出一个看起来很合理的根因，但没有任何线上实际数据支撑。这个幻觉一旦灌进后续的处置链路，就可能导致错误操作，造成的危害远大于查不出原因。
- **取证驱动的工作流**：先由 planner（计划节点）确定应该查哪些方向 → 再由 evidence_fanout（取证扇出节点）并行发起只读查询 → 然后 aggregate（证据聚合节点）对证据质量和覆盖度打分，判断证据是否足够 → 最后 diagnose（诊断节点）才在证据之上给出根因结论。
- **顺序是刻意设计的**：取证 → 打分 → 下结论，模型永远站在已经查到的事实上说话，不允许凭空发挥。

**项目印证**：这一段五个节点本质就是把「下结论」这件事用证据包起来——**模型只在 diagnose 一步真正上场，且上场前证据已经摆在桌上**。

**追问预判**：「为什么一定要取证驱动？为什么刻意设计成工作流？设计这么多节点的依据是什么？」→ 因为这是故障处置，不是普通问答；故障处置最怕「结论看起来合理但没有事实支撑」。所以系统必须把 LLM 从决策中心降级成**证据上的归纳器**，再用工作流把每一步变成可验证、可回退、可审计的控制点。

**展开补充**：
- **为什么要取证驱动**：故障场景里错结论比没结论更危险。模型只看「支付服务 5xx 升高」时，很容易猜发布回归、DB 慢查询、下游超时，每个都听起来合理；但如果没有日志、指标、部署记录、K8s 状态、DB 证据支撑，这个结论不能驱动 rollback、restart 这类处置动作。
- **SRE 本来就是 evidence-based**：真实排障不会上来拍脑袋说根因，而是先看最近是否发布、错误率是否同步上升、Pod 是否重启、DB 是否有锁等待、下游是否超时。这个系统只是把人的排障路径工程化：先计划查什么，再并行查证，再看证据质量，再诊断。
- **为什么要工作流**：这不是一次性生成答案，而是有状态、有分支、有回退、有人工介入的处置过程。工作流能强制顺序约束：先取证，再诊断，再门控，再修复；还能表达失败隔离、质量门控、人工审批、checkpoint 和审计事件。
- **为什么拆这么多节点**：依据不是「节点越多越好」，而是按职责和风险边界拆。取证是只读，修复是写操作，审批是人工控制点，验证是结果检查；风险等级不同，就不应该塞进同一个节点。每个节点只回答一个问题，才方便单测、观测和回退。

**项目印证**：`builder.py` 里的图结构把 `planner -> evidence_fanout -> evidence_aggregate -> diagnose -> critic` 固化成顺序链路；critic 后根据 `critic_decision` 回到 fanout、回到 planner、进入 remediation 或转 RCA。`GraphRunner` 又在每个节点后保存 checkpoint、持久化 evidence、记录节点事件。也就是说，安全约束不是 prompt 里一句「请谨慎」，而是写进了图结构。

**一句话总结**：节点多不是目的，控制点清晰才是目的。取证驱动解决「不要凭空猜」；工作流解决「按安全顺序推进」；多节点拆分解决「每一步可验证、可回退、可审计」。

## Q2 evidence_fanout 为什么要并行？串行不行吗？一路工具挂了会怎样？

**核心**：并行（通过 `asyncio.gather` 并发收集器实现）是为了快、同时保证各路径之间互不拖累；因为取证全部是只读操作且各路径之间互不依赖，所以单路失败不会阻塞整体流程。

**展开**：
- **为什么要并行**：查日志、查 K8s、查数据库、查指标这些操作同时发起，谁先返回就先收谁的结果，而不是查完一个再查下一个。串行方式下每条路径的等待时间会线性叠加，并行方式下总耗时约等于最慢那一路的耗时，显著缩短了取证阶段的整体延迟。
- **为什么要只读**：取证阶段只看不动，不触碰任何线上写操作。需要执行写操作是后面处置阶段的事，而且还要经过审批才能执行。
- **互不依赖，独立失败**：每一路查自己的数据源，和其他路之间没有依赖关系。某一路上因为超时或报错挂掉了，不会卡住其他路。挂掉的那一路结果标记为 FAILED，这个失败会反映到质量分上，但**不会让整个取证流程停摆**。

**项目印证**：`__init__.py:406` 用 `asyncio.gather` 扇出并发任务；返回的证据按**四种状态**（USABLE 有用 / EMPTY 空结果 / FAILED_CONFIG 配置失败 / FAILED_RUNTIME 运行失败）分类，失败的只影响自己这一路，不影响其他路。

**追问预判**：「并行了怎么保证证据之间不串？」→ 每一路是独立的只读查询，各自产出独立的 `EvidenceItem`（证据条目）对象，各路之间不共享可变状态、不争抢排他资源，所以天然没有并发竞争问题。

## Q3 你提到一个质量分，它到底衡量什么？派几路查不是计划时就定死了吗，这分怎么会变？

**核心**：质量分衡量的是「**多专家证据链的可信完成度**」——不是简单看调了几个工具，而是综合看专家覆盖度、专家置信度、降级情况和截断情况。

**展开**：
- **专家覆盖度**：看 `k8s / db / logs / metrics / deployments` 这 5 类 specialist agent 是否都有有效输出。只靠一个日志专家，即使它很自信，也不能代表全局证据质量高。
- **专家置信度**：每个 `SpecialistAnalysis` 都有自己的 `confidence`，aggregate 会对有效 agent 的 confidence 做平均，作为基础质量。
- **降级惩罚**：如果某个 agent 是 `partial=True`，说明它不是完整分析，而是降级结果，这个 agent 的 confidence 会被打折，比如乘以 0.5。
- **截断惩罚**：如果 agent 因为超时、轮次限制或上下文限制被 `truncated=True`，说明分析没有完整展开，aggregate 会按截断数量对整体质量做惩罚。
- 所以质量分可以理解成：`平均专家置信度 × 覆盖度 × 降级惩罚 × 截断惩罚`。它抓的不是「有没有返回」，而是「这轮多专家取证是否足够完整、可信、可用于下游诊断」。

**项目印证**：`aggregator.py` 的 `_compute_weighted_quality` 会跳过 `LLM_FAILED` 的 agent，对有效 agent 的 `confidence` 求平均；`partial=True` 时对该 agent 置信度打折；`truncated=True` 时施加整体 penalty；最后再乘以 `active_count / 5` 的覆盖度。质量分写入 `evidence_quality_score`，是下游 critic 做放行、补证、重规划或转人工的重要依据。

**追问预判**：「这几个维度是谁定的？有理论基础吗？」→ 不是 LLM 自己定的，是工程侧按生产 SRE 排障经验和可观测性原则定的：多信号覆盖、领域专家独立分析、对降级和不完整输出显式扣分，再由门控节点决定是否放行。K8s 看运行状态，DB 看连接/慢查询/锁，logs 看应用异常，metrics 看趋势，deployments 看变更；只有多个观测面互相印证，根因判断才有底座。

**追问预判**：「为什么单点高置信不够？」→ 因为单个专家只能说明一个观测面比较确定，不能代表全局可靠。比如 logs agent 置信度 0.95，但 metrics、db、k8s、deployments 都没完成，那只能说明日志方向比较强，不能说明整个诊断可以放行。所以质量分必须把 confidence 和 coverage 绑在一起。

## Q4 critic 这个节点是干嘛的？它和 diagnose 不都在判断根因吗，有啥区别？

**核心**：critic 是「**材料审核员**」，不是「方案评委」——它自己不查证据、也不下结论，只判断「现在**够不够格**放行进处置」。

**展开**：
- diagnose（诊断节点）负责**下结论**，即根据现有证据产出根因候选列表；critic（批评/门控节点）负责**审查这个结论的底座牢不牢**——证据够不够支持这个结论、证据之间有没有互相矛盾的地方。
- critic **不重新计算质量分**，它直接读取上游 aggregate 已经算好的质量分和矛盾信号，只做「放行还是退回」的路由决定。
- 这个设计叫做**「打分与决策解耦」**：aggregate 负责打分，critic 负责拿着分数做决定，各自职责单一、可以独立测试和调试。

**项目印证**：`__init__.py:1074`，critic 读取 `evidence_quality_score`（证据质量分），做四裁决（PASS / NEED_MORE_EVIDENCE / REPLAN / NEEDS_HUMAN），整个过程它自己不产生新的证据条目。

**追问预判**：「为什么打分与决策要解耦？不解耦行不行？」→ 不解耦功能上也能跑，比如 aggregate 算完质量分后直接决定 PASS / NEED_MORE_EVIDENCE / REPLAN，demo 里没问题；但生产故障处置里更适合拆开。aggregate 是**度量层**，回答「证据质量是多少、缺哪些类别、哪些工具失败、有没有矛盾信号」；critic 是**策略层**，回答「基于这些度量，现在该放行、补证、重规划，还是转人工」。这背后是 measurement 和 policy 分离，也可以类比控制系统里的「传感器」和「控制器」分离：传感器只给客观读数，控制器根据读数和阈值做动作。

**展开补充**：
- **可解释性**：拆开后能清楚看到 `evidence_quality_score`、`missing_evidence_categories`、`failed_evidence_tools` 和最终 `critic_decision`。如果混在一个节点里，只看到「决定 PASS」，很难判断是分数算得高，还是阈值策略太宽。
- **可测试性**：打分逻辑可以单测「有效 agent 数、confidence、partial、truncated 如何影响质量分」；决策逻辑可以单测「质量分低、缺失类别多、矛盾证据、循环耗尽」分别走什么路由。耦合后失败定位会变难。
- **可调参性**：质量分公式和放行策略变化频率不一样。质量分可以从覆盖率升级成加权质量分；critic 阈值可以按 P0/P1 更严格。拆开后改 scoring 不必动 routing，改 routing 也不必动 scoring。
- **避免自己给自己放行**：`diagnose` 是真正会用 LLM 归纳根因的地方，如果同一段逻辑既提出根因，又判断「这个根因是否足够可信」，容易形成确认偏差。critic 独立出来，只看质量分、缺失项、失败工具、矛盾证据和 loop guard，不重新编证据、不重新下根因。

**追问预判**：「第四点是不是指大模型自己给自己当裁判？」→ 对，可以这么理解，但要说准确：不是 aggregate 里有大模型，而是整个诊断链路里，如果「提出结论的人」和「判断结论够不够可靠的人」职责混在一起，就容易变成自己给自己当裁判。这个项目里 `diagnose` 负责基于证据提出根因候选，critic 只做门控审核；它更像材料审核员，不是诊断医生本人。

**追问预判**：「aggregate 和 diagnose 又为什么分开？」→ 因为它们回答的是两类问题：aggregate 负责把 fanout 回来的证据整理成**材料包**，diagnose 负责基于材料包提出**根因假设**。如果合在一起，一个节点就既整理证据、又解释证据、又下结论，职责太重，也很难判断错在哪里。

**展开补充**：
- **aggregate 是证据层工作**：汇总各 specialist agent 的 `SpecialistAnalysis`，整理 `evidence_items`、`evidence_summary`、`evidence_quality_score`、`cross_agent_causal_chains` 和 `contradiction_signals`。它回答的是「现在手上有什么材料？材料质量怎么样？不同观测面之间有没有互相印证或冲突？」
- **diagnose 是推理层工作**：读取 `evidence_summary` 和 `evidence_items`，结合 triage 的 `incident_type`，生成 2-3 个 `RootCauseCandidate`，每个候选带 hypothesis、confidence、supporting evidence、contradicting evidence 和 incident_type，再按 confidence 排序。它回答的是「基于这些材料，最可能的根因是什么？」
- **确定性和解释性分开**：aggregate 主要是统计、归类、打分、摘要，应该尽量稳定可复现；diagnose 才是模型发挥归纳能力的地方。拆开可以减少模型对底层事实整理的污染。
- **方便定位问题**：诊断错了可以先看 aggregate，判断是证据本来就缺、质量分低、工具失败，还是 evidence 没问题但 diagnose 推理错了。合在一起就很难区分「证据没采好」和「证据有了但模型读歪了」。
- **给 critic 独立质量信号**：critic 放不放行不能只听 diagnose 自己说「我有把握」，它需要 aggregate 给出的质量分、缺失类别和失败工具作为客观读数，再结合 diagnose 的候选结论做门控。

**一句话总结**：aggregate 是证据工程，diagnose 是根因推理；前者尽量确定性，后者允许模型归纳。拆开以后，证据质量、诊断结论、放行决策三件事各自可解释、可测试、可替换。

**追问预判**：「fanout 派了 3 个专家 agent 到 aggregate，aggregate 输出的根因也会有 3 条吗？」→ 不会。专家 agent 是按**观测域**划分的，不是按根因划分的。`logs_agent / metrics_agent / k8s_agent` 看到的是同一个事故的不同侧面，aggregate 会把这些侧面合成一个全局证据包，不会一人产一条根因。真正生成根因候选的是 diagnose。

**展开补充**：
- `evidence_fanout`：派专家取证，比如 logs、metrics、k8s 三个专家各自产出 `SpecialistAnalysis`。
- `aggregate`：把 3 个专家结果合并成全局证据视图，输出 `evidence_summary`、`evidence_quality_score`、`cross_agent_causal_chains`、`contradiction_signals` 等。
- `diagnose`：基于全局证据包生成 2-3 个 `RootCauseCandidate`。所以数量关系是 `N 个专家分析 -> 1 个全局证据包 -> 2-3 个根因候选`，不是 `N 个专家 = N 条根因`。

**追问预判**：「矛盾检测放在哪里？」→ 放在 aggregate 阶段。因为矛盾检测需要同时看到多个专家视角，单个专家只能看到自己的领域。项目里 aggregate 会基于多个 `SpecialistAnalysis` 建 correlation graph、推断 causal chains，并用 `_detect_cross_agent_contradictions` 检测跨专家矛盾，最后写入 `state["contradiction_signals"]`。critic 只消费这个信号做门控，不在自己里面重新做证据推理。

**追问预判**：「证据链都有矛盾了，diagnose 还做根因假设，不是自欺欺人吗？」→ 不是。要区分「有矛盾信号」和「证据完全不可用」。矛盾信号的意思是当前证据之间存在不一致，诊断置信度要下降，不能直接放行；但它不等于所有证据作废。比如 logs 和 metrics 异常、k8s 正常，反而说明根因可能不是 K8s 资源层，而更可能是应用层、发布变更、配置或下游依赖。

**展开补充**：
- aggregate 发现矛盾：输出 `contradiction_signals`，例如 `logs 异常 + k8s 正常 -> 应用层故障，非基础设施`。
- diagnose 带着矛盾信号生成**带不确定性的候选根因**，候选里保留 `supporting_evidence_ids`、`contradicting_evidence_ids`、`confidence` 和 `next_checks`。
- critic 负责阻止「有反证的候选」直接进入处置，必要时走 `CONTRADICTION / NEED_MORE_EVIDENCE / REPLAN / NEEDS_HUMAN`。
- 所以链路不是 `证据矛盾 -> 强行修复`，而是 `证据矛盾 -> 生成可检查假设 -> critic 不放行或要求补证`。

**示例**：支付服务 5xx 升高时，logs 专家发现 14:05 后大量 `NullPointerException`，metrics 专家发现 5xx 和 p95 延迟同步升高，k8s 专家显示 Pod 没重启、CPU/Memory/HPA 正常，deployments 专家显示 14:00 发布了 v2.8.3。aggregate 会输出「logs/metrics/deployments 异常，k8s 正常」以及矛盾信号 `logs 异常 + k8s 正常 -> 应用层故障，非基础设施`，同时推断因果链 `deployments -> logs -> metrics`。diagnose 会把这个矛盾当约束，优先生成「v2.8.3 发布引入空指针导致 5xx」这类候选，并把 k8s 正常作为反证或降置信因素。critic 看到存在矛盾和反证后，不让它直接处置，而是要求补查新旧版本 Pod 错误分布、deployment diff 或配置变更。

**追问预判**：「所以是先出根因分析，仲裁再判断这个根因分析可靠不可靠？」→ 对，但要说准确：先生成的是**候选根因分析**，不是最终裁决。diagnose 负责提出假设，candidate 带 hypothesis、confidence、supporting evidence、contradicting evidence 和 next checks；critic 再根据质量分、矛盾信号、缺失信息、失败工具、候选置信度和 loop 次数决定它是否可靠到可以进入处置。

## Q5 critic 怎么决定放行还是退回？退回又退到哪？

**核心**：critic 做四种裁决——**PASS 放行 / NEED_MORE_EVIDENCE 退一步回到 fanout / REPLAN 退两步回到 planner / 摆不平就转人工**。

**展开**：
- 证据充足、结论稳定 → 判 **PASS**，放行进入处置阶段，由 remediation（修复方案节点）产出修复动作。
- 证据不够但方向没问题（质量分偏低） → 判 **NEED_MORE_EVIDENCE**，**退一步**回到 evidence_fanout：计划不变，但让系统再跑一轮取证，争取多取一些证据回来。
- 调查方向本身就不对（可能 planner 排错了调查重点） → 判 **REPLAN**，**退两步**回到 planner：推翻现有计划，重新排列调查任务。
- 连续退回多次仍无法得到可靠结论 → 判 **NEEDS_HUMAN**，转人工介入。
- **「退一步 vs 退两步」的本质区别**：是「同一个计划没查够，再查一轮就行」，还是「计划本身排错了方向，需要重新想该查什么」——对应回退的深度不同，影响也不同。退一步轻量，退两步重排，各有适用场景。

**项目印证**：`builder.py:115` 的 `_route_after_critic`（critic 后的路由器）把四种裁决映射到对应的回边（返回 fanout / 返回 planner / 前进处置 / 转人工）。这是**「全程可退回重来」**的物理实现——证据不扎实，宁可绕回去再查也不急着下结论。

## Q6 证据来回查，会不会无限循环？

**核心**：有**防失控机制（loop guard）**——最多循环 2 轮，耗尽后**强制转人工**，不会让系统自己在取证循环里一直烧下去。

**展开**：
- 每次 critic 判 NEED_MORE_EVIDENCE 或 REPLAN 时，都会把 `loop_count`（循环计数器）加 1。
- 当 `loop_count` 到达上限（默认值 2）仍然没有拿到 PASS → critic 直接判 `NEEDS_HUMAN`（转人工），并附带结构化的 `terminal_reason`（终止原因），标记为 `EVIDENCE_LOOP_EXHAUSTED`（证据循环耗尽），清晰说明为什么自己停下来了。
- 这是编写 Agent 工作流时必须考虑的**防失控设计**：宁可主动转人工，也不能让模型在取证循环里自转出不来，消耗资源还拿不到结果。

**项目印证**：`__init__.py:1086` 的防失控判断；当循环耗尽时，critic 会把根因候选的置信度压到 ≤0.5、并标记 `requires_immediate_human`（需立即人工介入），不留「假装很确定」的尾巴给下游节点，下游看到这个标记就知道这是不确定的结果。

**追问预判**：「为什么定两轮？是拍脑门吗？三轮四轮不行吗？」→ 不是拍脑门，但两轮也不是数学上唯一正确的值；它是一个**工程阈值**，平衡的是补证收益、时间成本和自动化误判风险。默认两轮代表「首轮取证 + 一次纠偏」的自动化预算，超过预算还不能形成可靠结论，就进入人工接管。

**展开补充**：
- **第一轮是主路径取证**：planner 根据 triage 的故障类型排调查计划，fanout 并行查 logs、metrics、k8s、db、deployments 等证据，aggregate/diagnose/critic 判断是否能 PASS。
- **第二轮是纠偏机会**：critic 如果发现证据不够，就回到 fanout 补证；如果发现方向不对，就回到 planner 重规划。所以第二轮不是机械重试，而是给系统一次补证或重规划的机会。
- **再往后边际收益下降**：如果两轮后仍然没有可靠结论，通常说明不是简单缺一条日志，而是工具接入失败、权限/配置缺失、故障类型判断不准、观测面缺失，或者事故需要人工上下文。第三轮、第四轮很可能只是重复消耗时间。
- **事故处理中时间很关键**：自动化如果在取证循环里转太久，会拖慢人工介入。两轮后转人工，是保守策略：承认系统证据不足，把缺失类别、失败工具、当前候选结论和终止原因交给人。

**追问预判**：「那三轮四轮到底行不行？」→ 可以，但必须有策略依据，不能只是把数字调大。比如 P3/P4、非生产环境可以放宽；P0/P1 生产事故反而应该更早转人工；如果第二轮重规划后明显拿到了新证据，可以允许一次额外 fanout；但如果失败原因是配置错误或工具不可用，再多跑也没意义，应该直接人工/平台修复。

## Q7 diagnose 给了 2-3 个根因候选，最后怎么用？有个淘汰赛选出一个吗？

**核心**：不是淘汰赛逐一筛掉，而是「**排序后取第一名**」——按置信度降序排列，处置模块只吃第一名，其余候选作为陪跑信息进入归档。

**展开**：
- diagnose 产出 2-3 个根因候选，每个候选都带有一个 `confidence`（置信度）分数。然后按置信度从高到低排序，**不删除任何一个候选**，全部保留。
- remediation（修复方案节点）**只取排名第一的候选**，也就是 `candidates[0]`，用它的 `incident_type`（故障类型）来决定开出什么修复方案：如果是发布回归类型的故障就执行 rollback（回滚），否则执行 restart（重启）。
- 排名第 2、第 3 的候选**不驱动任何动作**，但它们保留在 state 里，最终被 rca（根因分析归档节点）写入归档——留痕记录「当时的诊断还考虑过这些可能性」。

**项目印证**：`__init__.py:1062` 的候选排序逻辑；`:1152` 取第一名 `candidates[0]` 做处置决策；在 rca 归档节点里，第一名的置信度 ≥0.7 才算「确认根因」，否则标记为存疑——**第一名不仅决定开什么药，还决定这次根因有没有把握拍板确认**。

**追问预判**：「提出了根因假设，critic 也放行了；如果假设有多条，最后给处置人的是哪条？」→ 给处置链路的是**排序第一的 top candidate**。diagnose 可以生成 2-3 个候选表达不确定性，但 remediation 必须收敛到一个主假设，否则动作会互相冲突。critic 放行后，remediation 读取 `candidates[0]`，用它的 `incident_type` 决定处置策略；其他候选保留在 state 和 RCA 里，用于审计和复盘，不驱动动作。

**追问预判**：「next_checks 是怎么来的？写了系统提示词吗？」→ `next_checks` 是 diagnose 输出的**假设验证清单**，不是执行计划。它回答的是：如果这个根因是真的，下一步应该看到什么证据；如果这个根因是假的，什么证据会推翻它。当前 diagnose prompt 要求每个候选按结构化 JSON 输出 `incident_type / hypothesis / confidence / next_checks`；系统提示词主要约束角色和中文输出，真正约束结构的是用户 prompt 里的 schema。LLM 失败时会走 fallback，给出规则化默认检查项。

**展开补充**：
- **证据反推**：根据当前 supporting evidence 和 contradicting evidence 推出缺口。比如发布回归候选有 deployment 和 logs 支持，但缺少新旧版本 Pod 对比，next check 就是查错误是否集中在新版本。
- **故障类型模板**：不同 `incident_type` 有固定验证套路。发布回归查 deployment diff、错误时间线、新旧版本对比；资源耗尽查 CPU/memory/HPA/DB 连接；依赖失败查下游超时、SLB、调用链和错误码分布。
- **结构化 LLM 补全**：LLM 可以根据证据摘要生成贴近现场的检查项，但只能作为「建议检查」，不能直接变成 rollback/restart 这类执行动作。
- **生产化形态**：更理想的 `next_checks` 不是字符串数组，而是结构化对象，包含 `check`、`purpose`、`target_hypothesis`、`expected_signal`、`tool_hint`、`priority`、`read_only`。它只能驱动后续只读取证，不能直接驱动修复。

**一句话总结**：diagnose 可以保留多个候选，但处置只吃 top candidate；`next_checks` 是候选根因的验证清单，用来指导补证和人工排查，不是自动执行动作。

## Q8 planner 排的调查计划，是大模型生成的吗？

**核心**：**不是大模型生成的**——而是按故障类型做**模板化编排**，走确定性规则。「该查哪」这种关键的路由决策不交给模型，交给固定规则。

**展开**：
- planner 拿到 triage（分诊节点）给出的 `incident_type`（故障类型），然后查一张「这类故障应该查哪些方面」的对照表，按表列出对应的调查任务清单。
- 举例：发布回归类型 → 重点查部署历史 + rollout 状态 + 相关日志；资源耗尽类型 → 重点查指标数据 + K8s 饱和度指标 + 数据库容量。
- **为什么不让模型来排**：「该查哪」这个决策一旦出错，后面所有步骤全都白做。这种关键的路由决定交给固定规则来做，可解释、可复现、不会因模型幻觉而跑偏。

**项目印证**：`__init__.py:227`，planner 按 `incident_type` 分支生成 `InvestigationTask`（调查任务）列表，**这一步不调用 LLM**——体现了「控制权归确定性系统、不归模型」的设计原则。

## Q9 既然 planner 接收的是结构化结果，那上游是怎么把自然语言转成结构化输出的？

**核心**：上游是 triage（分诊节点），它把工单里的自然语言 `title/description` 和半结构化字段 `service/env/severity` 收敛成固定 schema 的 `TriageResult`；这个过程是三段式：**规则优先 → LLM 补充 → fallback 兜底**。

**展开**：
- **输入不是纯裸文本**：入口工单本身是 `IncidentTicket`，其中 `title/description` 是自然语言，`service/env/severity/source` 是结构化字段。intake 先做 service、env、time_range 的基础归一化，然后 triage 从 ticket 里取出标题、描述、服务、环境和严重级别来判断。
- **规则优先处理高确定性场景**：`_triage_by_rules` 会扫描 `title + description`。命中 `deploy/release/rollback/发布/回滚` 归为 `deployment_regression`；命中 `cpu/memory/oom/disk/内存/磁盘` 归为 `resource_exhaustion`；命中 `timeout/connection refused/downstream/依赖/503/502` 归为 `dependency_failure`。这些是 SRE 场景里强先验信号，用规则更稳定、可解释、可测试。
- **LLM 只处理长尾补充**：规则没命中时才进入 `_triage_by_llm`。LLM 收到 title、description、service、env、severity 后，必须按 JSON 返回 `incident_type`、`severity`、`suspected_services`、`suggested_time_window`、`requires_immediate_human`、`rationale`，代码再把它构造成 `TriageResult`，不会把模型原文直接交给 planner。
- **fallback 保证流程不中断**：如果规则没命中、LLM 超时/失败/返回非 JSON，triage 会降级成 `service_degradation`，保留原始 severity 或默认 P2，把当前 service 放进 `suspected_services`，时间窗口设成近 1 小时。这样 planner 永远有结构化输入，不会因为模型失败没有计划可排。

**项目印证**：`__init__.py:45` 的 `intake_node` 先归一化 ticket；`__init__.py:67` 的 `_triage_by_rules` 做关键词规则分类；`__init__.py:126` 的 `_triage_by_llm` 要求模型输出 JSON 并构造成 `TriageResult`；`__init__.py:178` 的 `_triage_fallback` 做降级兜底；`triage.py` 定义 `TriageResult` 的固定字段；`test_diagnose_structured.py` 里验证发布、资源耗尽、依赖失败和 fallback 都会产出预期的 enum 字符串。

**追问预判**：「那这里是不是还是依赖 LLM？」→ 不是强依赖。LLM 是长尾补充路径，不是主路径也不是单点；高置信场景走规则，LLM 失败走 fallback，下游 planner 消费的一定是 `TriageResult` 这个结构化对象。

## Q10 planner 接收物长什么样？怎么从接收物生成 plan？plan 类型能穷举吗，怎么保证是对的？

**核心**：planner 接收的是上游已经结构化后的 `IncidentAgentState`，关键输入是 `ticket + triage`；它不是读裸文本自由发挥，而是用 `triage.incident_type` 选择确定性调查模板，再把 `ticket.service/env` 和 `triage.suspected_services` 填进任务参数，生成受控的 `InvestigationPlan`。

**展开**：
- **接收物长什么样**：planner 的输入不是一段 prompt，而是 graph state。关键字段包括 `ticket`（服务、环境、标题、描述、严重级别）和 `triage`（`incident_type`、`suspected_services`、`suggested_time_window`、`requires_immediate_human`、`rationale`）。例如发布后支付服务 5xx 升高，triage 会给出 `incident_type=deployment_regression`、`suspected_services=["payment-service"]`，planner 再基于这个结构化结果排调查任务。
- **怎么得出具体 plan**：planner 先取 `incident_type`，按故障类型选择调查模板；然后对每个 suspected service 展开任务，把 `service/env/incident_type` 填到工具参数里。比如 `deployment_regression` 优先查 `query_deployments`、`query_logs`、K8s rollout/pod/event/replicaset/configmap，再补 metrics、DB slow query 和 runbook；`resource_exhaustion` 则优先查 metrics、K8s 节点/Pod/HPA/quota/PVC、DB variables/processlist/slow query。
- **plan 类型能不能穷举**：要分两层看。`incident_type` 是闭集，由统一的 `IncidentType` 管理；具体 plan 实例会按服务数动态展开，所以不手写穷举每一种排列组合，但它的组成元素是穷举的：`category` 是固定取证域，`tool_name` 来自工具网关注册表，参数结构由工具 schema 校验。因此它不是开放式 plan，而是「闭集故障类型 × 固定调查模板 × 已注册工具」的确定性组合。
- **怎么保证 plan 是对的**：生产系统里不靠一句“模型会规划”来保证，而是多层约束：triage 先把自然语言收敛成结构化 incident type；planner 不调用 LLM，核心路由可复现；`InvestigationPlan / InvestigationTask` 用 Pydantic 约束结构；`tool_name` 必须存在于 `ToolGateway` 注册表；工具参数再过 schema 和 adapter 校验；最后 aggregate + critic 会检查证据质量，如果方向不够好就退回 fanout 或 planner。

**项目印证**：`state.py:31` 定义 `IncidentAgentState`，planner 从 `triage` 和 `ticket` 取输入；`__init__.py:227` 的 `planner_node` 兼容 Pydantic 对象和 dict，按 `incident_type` 分支生成 `InvestigationPlan`；`planning.py:26` 定义 `InvestigationTask` 的结构；`incident_type.py:10` 定义闭集 `IncidentType`；`gateway.py:204` 开始注册工具能力，未知工具不会被放过；`test_mysql_planning.py` 验证资源耗尽和 generic 类型会生成对应 DB/K8s 取证任务。

**追问预判**：「你能保证 planner 永远语义正确吗？」→ 不能这么说，生产系统没有“永远不错”的承诺。准确说是：planner 的输出空间被工程化收敛了，结构一定合法、工具一定受控、执行一定只读；调查方向是否足够好，由证据质量门控、回退重规划和离线评测持续兜底。

## Q11 这一整套取证 + 门控，和一个 ReAct agent 直接循环调工具，差在哪？

**核心**：差在「**可控性**」——裸 ReAct agent 在「需要有门控、需要能退回、需要能叫人工」这三件事上会失控，而这套系统用确定性编排把它们**显式拆成了独立节点**。

**展开**：
- **裸 ReAct 的问题**：模型自己决定下一步调什么工具、什么时候停下来。随着步骤变长，上下文越塞越满，模型容易跑偏，而且跑偏之后没法回头；遇到高危动作没法在中间截停，只能在事后补救。
- **这套系统怎么解决**：planner 拍板定计划（不由模型决定查什么）、critic 做门控（判断证据够不够放行，不够就退回）、loop guard 防失控（最多转两圈强制转人工）、回边支持退回重来——**控制权握在确定性系统手里，模型只做它擅长的事：理解和归纳**。
- **代价与收益**：代价是编排更复杂了（多了几个闸门节点），换来的是每一步都可验证、可解释、可以在中途插入人工介入。

**项目印证**：分解胜于强提示——`0.9¹³ ≈ 0.25` vs `0.98¹³ ≈ 0.77`，13 个节点各自职责单一让整体可靠性从不可接受变成了可接受。这里的 critic + loop guard 就是把「不能闯祸」这个约束焊进图结构里，而不是写进 prompt 里当一句「请注意安全」。
