## OpsPilot — 运维故障智能体 项目详解

> 面向面试场景的项目包装。第一优先级（8 项）已实现，第二优先级（7 项）实现中。

---

### 一、用户旅程

一次完整故障处置闭环，从告警到恢复覆盖 5 个阶段：

| 阶段 | 用户行为 | 系统行为 |
|------|---------|---------|
| **1. 故障接入** | 监控系统推送告警 / 值班人员手工创建工单 | intake 统一规范化 → triage 三阶段分诊（规则匹配 → LLM分类 → fallback），11 种封闭故障类型 |
| **2. 自主调查** | 无需干预，等待结果 | RAG 语义检索历史记忆 + runbook → planner 生成分层调查计划 → 5 个 SpecialistAgent 并行从 K8s/DB/日志/指标/部署 五维度采集证据，每个 Agent 独立运行 ReAct 循环 |
| **3. 证据聚合与诊断** | 可实时通过 SSE 流式查看事件进度 | cross-agent aggregator 构建因果关系图 + 矛盾检测 → LLM 生成 2-3 个根因假设（含支持/反对证据 + 置信度）→ critic 质量门控审查 |
| **4. 受控处置** | 低风险动作自动执行；高风险动作推送审批 | remediation 规则引擎生成修复方案 → risk_gate 多维度风险评估（动作风险 + 环境 + 置信度 + preflight）→ 分级路由：自动执行 / 人工审批 / 阻止 / 转人工 |
| **5. 验证与复盘** | 确认恢复，查看 RCA 报告 | executor 幂等执行 → verify_outcome 三维验证（K8s 状态 + LB 健康 + 流量指标）→ 失败自动重试/回滚 → RCA 报告生成并归档 OSS |

**关键体验细节**：
- 每一步都有 **26 种事件类型**通过 SSE 实时推送，前端 Stepper + Tabs 展示进度
- 人工审批中断后可随时 resume，系统从 checkpoint 精确恢复状态
- 证据支持**全链追溯**：每条证据记录原始查询参数、工具版本、采集时间、快照位置

### 二、架构设计

```
┌─────────────────────────────────────────────────────────┐
│                    API Layer (FastAPI)                    │
│  POST /incidents/runs  →  创建 & 启动调查                │
│  GET  /runs/{id}/stream →  SSE 事件推送                  │
│  GET  /runs/{id}/trace  →  完整调用链追踪                │
│  POST /approvals/{id}/decision → 人工审批决策            │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│              GraphRunner（编排引擎）                      │
│  • EventBus 事件注入 (ContextVar)                        │
│  • Checkpoint 持久化（每节点 1 次，支持 resume）          │
│  • Evidence 自动持久化 + dedupe                          │
│  • 多层 Tracing (本地 span + LangSmith/Langfuse)         │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│           LangGraph StateGraph（14 节点状态机）           │
│                                                         │
│  dispatcher → intake → triage → retrieve_memory         │
│     → planner → evidence_fanout → evidence_aggregate    │
│     → diagnose → critic ─┬─ PASS → remediation          │
│                          ├─ NEED_MORE_EVIDENCE ↺         │
│                          ├─ REPLAN/CONTRADICTION ↺      │
│                          └─ NEEDS_HUMAN → rca → END     │
│                                                         │
│  remediation → risk_gate ─┬─ LOW_ONLY → executor        │
│                           ├─ NEEDS_APPROVAL → interrupt  │
│                           └─ BLOCKED → rca → END        │
│                                                         │
│  executor → verify_outcome ─┬─ SUCCESS → rca → END      │
│                             └─ RETRYABLE ↺ (最多2次)     │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│              Tool Gateway（能力适配层）                   │
│  • 统一入口：schema 校验 → adapter 路由 → 重试 → 审计    │
│  • Mock/Real 双模式切换（TOOL_ADAPTER_MODE）             │
│  • 29 个注册工具 (14 K8s + 4 DB + SLB + 指标 + 部署...) │
│  • Eval fixture 注入短接 (ContextVar)                    │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│              LLM Client（推理层）                         │
│  OpenAI / MiniMax / DeepSeek 可切换                      │
│  用途：triage 分类 / diagnose 根因 / RCA 报告 /          │
│        SpecialistAgent ReAct 推理                        │
└─────────────────────────────────────────────────────────┘
```

**核心设计原则**：

1. **事件驱动状态机**：14 个节点通过条件路由形成有向图，支持循环（critic → evidence_fanout/planner）和中断-恢复（approval_interrupt → END → resume），非简单线性管道。

2. **ContextVar 跨异步上下文传递**：事件 hook、tracing span_id、eval fixture 三处均使用 Python ContextVar 实现零侵入的上下文注入，无需显式传参，天然支持 asyncio 并发隔离。

3. **双模式适配器**：Tool Gateway 通过单一开关 `TOOL_ADAPTER_MODE` 在 mock/real 间切换，开发调试用 mock 零依赖，生产环境接真实阿里云 RDS/K8s/SLB/CMS。

4. **两层评测分层**：Graph Quality（诊断准确率，真实 LLM 推理）和 Runtime Fidelity（生产链路正确性，checkpoint/事件/DB）完全分离，指标永不合并。

### 三、关键领域技术方案

#### 1. 动态服务拓扑（已实现）

**方案**：不是静态拓扑图，而是每次调查时基于证据**动态构建因果图**。

- 5 个 SpecialistAgent 各自输出 `correlation_hints`（如：K8s Pod 异常 → 可能与 DB 连接池耗尽相关），跨 Agent 聚合器将 hints 构建为有向图
- 基于 in-degree 识别根节点，DFS 发现异常传播路径（causal chains）
- LLM 诊断时不仅看到单个维度的证据，还看到跨维度因果链

```
K8s(CrashLoopBackOff) → Metrics(CPU spike) → DB(high_connections)
                                       ↘ Logs(connection_timeout)
```

#### 2. 统一变更事件建模（已实现）

**方案**：将变更信息作为一等证据维度。

- `deployment_specialist` Agent 查询部署历史，自动检测最近部署时间与故障时间的重合度
- 部署变更通过规则引擎自动生成跨维度 `correlation_hints`（指向 K8s 和 logs）
- LLM 诊断时将变更证据与其他维度证据共同作为输入，避免「发生发布就归因发布」的错误

#### 3. 显式假设树与证伪机制（已实现）

**方案**：每条证据同时服务于支持和反驳假设。

- `RootCauseCandidate` 同时持有 `supporting_evidence_ids` 和 `contradicting_evidence_ids`
- critic 节点执行矛盾检测：6 条 CONTRADICTION_RULES（如"K8s异常+metrics正常 → 可能非资源级故障"）
- 矛盾信号触发 REPLAN/CONTRADICTION 路由，而非直接淘汰假设——保留了人工判断空间
- LLM 生成 `next_checks` 建议下一步验证步骤，实现查证闭环

#### 4. 完整事故时间线（实现中）

**方案分两步走**：

- 当前：RCA 报告由 LLM 基于所有证据的 `source_timestamp` 生成 `timeline_summary`
- 进阶：自动提取各证据的异常信号时间戳，按因果顺序（原因 ≤ 结果）排序，过滤掉不符合时间约束的假设

#### 5. 证据快照与调查重放（已实现）

**方案**：四层保障确保证据可追溯、可复现。

| 层级 | 机制 | 存储 |
|------|------|------|
| Checkpoint | 每节点后完整 state 快照 | SQLite DB |
| Evidence | 每条证据持久化（含原始 payload + 查询参数 + 工具版本） | SQLite + OSS |
| Event Stream | 26 种 EventType 覆盖全生命周期 | DB + SSE |
| Trace | Span 层级调用链（graph.run → node.* → tool.* → llm.*） | 本地 + LangSmith/Langfuse |

**调查重放**：离线评测框架支持从固定证据集重新运行诊断逻辑，对比新旧模型/新 prompt 的表现差异。反事实重放也已支持：去掉某条关键证据后重跑，判断系统是否仍能正确诊断。

#### 6. 多维度闭环验证（已实现）

**方案**：不只看「命令执行成功」，而是三维验证系统真正恢复。

```
技术层：K8s Deployment 状态 (running/healthy/available)
      + SLB 健康检查 (healthy/ok/UP)
流量层：错误率 < 5%、QPS 恢复
      → SUCCESS / RETRYABLE / FATAL 三路路由
```

- RETRYABLE 自动重试最多 2 次，FATAL 进入 RCA 并标记 FAILED
- 部分通过（≥50%）视为 RETRYABLE，允许渐进式恢复
- 验证结果作为新一轮 evidence 追加到证据链

#### 7. 智能体自身可观测性（已实现 / 增强中）

**已实现**：

- **Tracing**：每个 graph run 生成完整 span 树，graph.run → node.{name} → specialist.{agent_id} → tool.{name} → llm.complete
- **审计**：每次工具调用持久化到 `IncidentToolAudit`（谁、什么工具、参数脱敏后、耗时、结果状态）
- **Agent 自报告**：每个 SpecialistAnalysis 包含 `execution_summary`（prompt 版本 + 截断状态 + 降级级别 L0/L1/L2/L3）
- **评测指标体系**：top1_accuracy、top3_accuracy、risk_accuracy、status_accuracy、per-class F1、confusion_matrix

**增强中**：LLM token 用量追踪、按 case 的 cost 监控、Agent 决策链路可视化

#### 8. 离线评测体系（已实现）

**核心设计决策**：

- **封闭枚举 vs 自由文本**：选了封闭枚举，主指标是纯 enum 等值比较，完全确定可复现
- **ContextVar fixture 注入**：比全局开关/ monkeypatch 更安全，asyncio 并发天然隔离，scope 退出自动回滚
- **真实 LLM + repeat=N**：不 mock LLM（mock 等于不测），重复 N 轮取分布而非单点
- **两层分离**：Graph Quality（诊断准确率）和 Runtime Fidelity（生产链路）永不合并
- **防陷阱设计**：`unknown`（证据不足）和 `other`（超纲）分离，避免模型被迫乱选

### 四、重点难点

#### 难点 1：多Agent并行取证的状态一致性与退化路径

**问题**：5 个 SpecialistAgent 并行运行独立的 ReAct 循环，每个都可能遇到 LLM 超时、工具调用失败、JSON 解析错误。不能让单个 Agent 的失败拖垮整个调查。

**方案**：设计了 **4 级降级路径**：

| 级别 | 状态 | 触发条件 | 行为 |
|------|------|---------|------|
| L0 | COMPLETED | 正常完成 | LLM 结构化输出 + 规则提取补充 |
| L1 | PARTIAL | JSON 解析失败 | 规则兜底提取信号，跳过 LLM |
| L2 | PARTIAL | LLM 超时/异常 | 规则兜底提取，confidence 降为 0.25 |
| L3 | LLM_FAILED | LLM 完全不可用 | 返回空 shell，不污染质量评分 |

aggregator 的加权质量评分自动排除 L3 的 Agent，L1/L2 的 confidence 乘以 0.5 惩罚。这确保即使部分 Agent 失效，系统仍能产出有意义的诊断。

#### 难点 2：证据质量门控的循环收敛问题

**问题**：critic 判断证据不足时可以触发重新取证，但如果证据采集本身有系统性缺陷（如工具全部不可用），会形成无限循环。

**方案**：三重防护：
1. `loop_count` 计数器，≥2 轮后强制转 NEEDS_HUMAN，不再循环
2. 质量门控分级：quality<0.4 且 missing≥2 → 重新取证（还有希望）；quality<0.3 且 items<2 → 重规划（换思路）；都不满足 → PASS（避免死循环）
3. `terminal_reason` 记录停止原因，可追溯

#### 难点 3：Pydantic 模型与 dict 的二义性

**问题**：LangGraph checkpoint 反序列化后，state 中的对象可能变成 dict，访问 `.service` 会崩溃。

**方案**：全局采用 `hasattr(obj, 'attr') else obj.get('attr')` 兼容模式，覆盖 `IncidentAgentState` 所有 40+ 字段的读写路径。

#### 难点 4：离线评测的并发隔离

**问题**：多个 eval case 并发运行时，如果工具调用走全局 mock 开关，case 之间会互相污染 fixture。

**方案**：使用 ContextVar + context manager 注入 per-case fixture：
- `fixture_scope({"query_logs": mock_data})` 内 spawn 的所有 asyncio Task 自动继承 fixture map
- scope 退出后通过 token 精确回滚，无论是否有异常
- 不同 case 在各自 Task 上下文中互不干扰，天然并发安全

#### 难点 5：审批中断后的精确状态恢复

**问题**：LangGraph 的 `interrupt` 机制保存的是当前节点前的 checkpoint。如果保存了 `node_approval_interrupt` 的 checkpoint，resume 时会回到 `node_intake` 重跑全流程。

**方案**：`ApprovalRuntime.prepare_resume_state()` 优先加载 `node_risk_gate` 的 checkpoint（在白名单 `_RESUME_ALLOWED_NODES` 内），而非 `node_approval_interrupt`。dispatcher 检查 `_resume_from_node` 标记，跳过已完成的节点直接路由到 executor。

### 五、面试问答对

> 按实际面试模拟顺序记录，随问随补。

---

#### Q1：RAG 语义检索历史记忆 + runbook 你是怎么设计的？

**A**：

整体是 **混合检索 + 工具调用** 双路径并行，最终合并到一个统一的 `MemoryHit` 列表。

**架构分层**：

```
retrieve_memory 节点
  ├─ 路径 A：RAG 混合检索（向量 + 关键词 + 重排序）
  └─ 路径 B：Tool-based runbook 查询（通过 ToolGateway）
  → 合并为 List[MemoryHit] → 写入 state
```

**RAG 的技术选型和 pipeline**：

| 层级 | 选型 | 理由 |
|------|------|------|
| 向量库 | ChromaDB（PersistentClient） | 轻量、零运维、本地文件存储，适合单机部署 |
| Embedding | `BAAI/bge-small-zh-v1.5` | 中文语义优化，推理快，轻量 |
| 分块 | SentenceSplitter, chunk_size=512, overlap=80 | 保证 chunk 有足够上下文，同时避免语义碎片化 |
| 关键词索引 | SQLite FTS5（unicode61 分词器） | 补齐向量检索对精确关键词（如错误码、异常类名）的漏召回 |
| 融合 | Reciprocal Rank Fusion（RRF, k=60） | 向量搜索结果和关键词搜索结果按排名融合，不需调权重超参 |
| 重排序 | `BAAI/bge-reranker-base` CrossEncoder | 对融合后的候选做精排，取 top_k=5 |
| 过滤 | metadata filter（service + env） | 缩小检索范围，避免跨服务噪声 |

**检索触发条件**：
- 从 ticket 提取 `service`、`env`、`title`、`description`
- 从 triage 提取 `incident_type`
- 拼接成查询字符串：`"{title} {description} {service} {incident_type}"`
- RAG 默认关闭（`RAG_ENABLED=false`），因为向量检索对于非结构化中文查询的语义召回升降不稳定的情况下，先作为可选能力

**双路径设计的原因**：

| | RAG 路径 | Tool 路径 |
|------|---------|----------|
| 检索内容 | 历史 RCA、runbook、服务文档 | 仅 runbook |
| 检索方式 | 混合检索（语义+关键词） | 直接工具调用 |
| 优势 | 跨文档类型、语义理解 | 结构化返回、可携带查询参数 |
| 适用场景 | 泛化知识召回 | 精确 runbook 匹配 |

为什么要两条路径？因为 **RAG 的语义检索和工具调用的结构化查询互为兜底**。如果 RAG 没召回（嵌入模型对专业术语如 "CrashLoopBackOff" 语义理解差），tool path 的 `query_runbook(service, env, incident_type)` 可以按 incident_type 精确匹配。反之，如果某个故障类型没有对应 runbook，RAG 能从历史 RCA 里找到相似案例。

**检索结果如何被下游消费**：
1. RAG 返回的 chunk 同时转为 `MemoryHit` 和 `EvidenceItem`（category="history"），后者直接进入证据链
2. Tool 返回的 runbook 转为 `MemoryHit`，也转为 evidence
3. Planner 节点拿到 `memory_hits` 后，在调查计划中自动为每个 service 增加 `query_runbook` 任务（优先级 3-5，视 incident_type 而定）

**知识写回闭环**：

```
人工确认 RCA
  → KnowledgeWritebackService.writeback()
    → build_rca_document（根因 + 处置 + 预防项 + Markdown）
    → index_documents（写入 ChromaDB + FTS5）
    → 未来故障可检索到本次经验
```

这里做了一个关键设计：**只有人工确认的 RCA 才写回知识库**。原因是 LLM 生成的 RCA 可能不准确，自动写回会污染知识库，导致后续检索到的"经验"其实是错误结论——这是一个正反馈污染问题。

**目前不足（第二优先级实现中）**：
- 缺少分层记忆：当前所有检索结果扁平化，没有短期/中期/长期记忆的时间衰减
- 相似事故匹配目前主要靠文本相似度，还没引入拓扑相似度、指标变化模式、错误指纹等结构化特征
- Runbook 的 real adapter 尚未实现，当前走 mock
