# 面试回答模版：Agent 评测框架 + 前端 E2E 测试 Agent 实战

> 总时长：5–6 分钟。五段式叙事：痛点 → 通用框架（图解）→ 转实战 → 扎深自愈 → 哲学收口。
> 用法：背第一句，其余现场推。被追问任何一点，去「纵深展开」查完整回答。

---

## ① 开局（30 秒）

Agent 从 demo 到生产，最大的坎是评测。因为 Agent 有三个传统软件没有的问题——非确定性：同一 prompt 跑两次结果不同；黑盒化：模型升级悄悄变差没人知道；错误级联放大：几步工具调用，一步偏差到最后结论全歪。没有一套嵌入研发流程的评测体系，团队就只能靠感觉和抽查过日子。

## ③ 转实战（40 秒）

这么一套框架，落到一个真实 Agent 上长什么样子？我做的是一个前端 E2E 测试 agent，五段完整闭环——编写用例、历史用例整合、执行、自愈、出报告。

先搞清楚三个对象，不然一开口就乱。第一层，产品——那个网页、主流程本身——这是我 agent 的工作对象，不是评测对象。第二层，我的测试 agent——评测集考它干活对不对。第三层，打分用的模型裁判——gold set 考它判得准不准。最常见的乱就是把第一层和第二层搅在一起。内心一问「我现在说的是产品、agent、还是裁判」，就分清了。

回到 agent 本身——评测它用的是前面那套逻辑：每一段的「对不对」都拆成两块，代码能自动判的，和只能上模型判的。五段共用同一台机器。

## ④ 扎深自愈（90 秒）

我拿自愈这一段展开。核心两步：把环境冻死，再让 agent 在冻死的环境里修。

先说环境怎么冻。因为是 CLI 工具，不能假设用户机器上有 Docker——我用 Playwright 的 browser context 做隔离，每个用例起独立上下文，MSW 做本地请求拦截，把录制好的 mock 数据直接返回。匹配逻辑是拿「方法 + 路径 + 请求体」算指纹去 mock 库里找对应的响应。问题就出在这个指纹上——请求体里有随机 ID、防缓存时间戳，回放时每次都不一样，同一个接口算出两个指纹，mock 命中不了。解法是在算哈希之前把这些动态字段按路径规则剔除。

挖掉动态字段后匹配率到了 70%，还是不够。剩下那 30% 查了大半个下午才定位——同一个请求因为 JSON 字段顺序不同，序列化后字符串不一样，算出两个哈希。`{role: 'admin', user: 'x'}` 和 `{user: 'x', role: 'admin'}` 语义一致，哈希不一致。

```js
// 错误做法：直接序列化，字段顺序影响哈希
const hash1 = sha256(JSON.stringify({ role: 'admin', user: 'x' }));
const hash2 = sha256(JSON.stringify({ user: 'x', role: 'admin' }));
// hash1 !== hash2 —— 同一个请求被当成两个

// 修正：序列化前排序
function stableStringify(obj) {
  return JSON.stringify(obj, Object.keys(obj).sort());
}
const hash = sha256(stableStringify({ role: 'admin', user: 'x' }));
```

就这一行，匹配率从 70% 拉到 95% 以上。这套本地隔离做自愈的单用例验证够用了。如果要跑全量回归、多个 agent 并行执行——那种不允许任何环境污染的场景，应该把执行层拆出去，放到 CI 流水线里用 Playwright 的 Docker 容器跑。CLI 做编排和触发，CI 做隔离执行，各管各的。

环境冻稳了，agent 修完之后怎么验它修对了？三道闸门，全是代码判的。第一，把修完的脚本丢回隔离的 browser context 真跑一遍，过了才算。第二，用语法树锁死断言——swc 把脚本解析成语法树，按节点角色判，定位语句允许改，但一流进断言节点就锁死。为什么要这么干？因为我抓到过 agent 把一个断言整行删掉，测试绿了，等于眼睛蒙上。提示词里写「不准删断言」没用，那个约束太软，必须在提交前用确定性脚本挡死。第三，选择器唯一性——修完的定位用 DOM 查询验证只命中一个元素。这三条过了，才上模型评分——修复语义合不合理，比如它选的新锚点在页面改版后的语境里是不是真合适。

作弊不是骂一顿就完了。那次删断言的事，我把它做成了陷阱题永久留在评测集里——以后每次 agent 升级，这道题都会测它还会不会作弊。同时回头改系统：那条「不准删断言」的规矩，从提示词里的软约束升级成提交前强制过的确定性校验。这个思路——agent 犯错之后，不是逐次纠正，而是去问「为什么我的系统当初没拦住它」，然后调整规则让同类错误更少发生，就是控制论里的 Steering Loop。它跟 SRE 的故障复盘同源——修的不是单次错误，是产生错误的系统条件。

## ⑤ 收口（30 秒）

回到一开始那套框架——三类评委、五大维度——你看它在自愈这一段上就是长这样：能代码判的全用代码判了，消不掉的那一点主观判断才上模型。其他四段也是同一台机器，每段都拆成客观和主观两块，尽量往客观那边推。

这里面有个更底层的认识：评测不是证明 agent 是对的，是把你不知道有多大的风险，量成一个有边界的错误率。你永远没法证明一个自动裁判正确——你只能拿一批人类判断当尺子，量出它错多少，然后赌这批尺子能代表真实情况。客观那半边推得越远，要赌的部分就越小。人判不齐的地方，比如三个人对同一段修复语义打不出共识——正确做法不是硬凑，是把这道题扔掉，诚实承认这块我量不了。

# 纵深展开

> 面试官追问某一点时，用下面的完整回答接住。每段 30–60 秒。

### 追② · 三类评委的落地细节

**怎么决定一件事给确定性评分还是模型评分？**

只有一个标准：这件事有没有确定的、可程序化的对错。文件存不存在、调用没调用指定工具、响应包不包含关键字——这些代码判，毫秒级、零成本、结果可靠。回答质量好不好、推理有没有跳步、修复语义合不合理——这些没有标准答案，才上模型。

**人工评分的六个必要场景具体指什么？**

1. 校准模型裁判——抽样 100-200 条，跟人类评分对齐，一致率不到 85% 说明裁判不能用。六成人力花在这里。为什么是最核心的？因为如果裁判本身的准确率没验证过，后面所有「模型打分」的结论都没有根基——你不知道它是真判对了还是蒙的。
2. 主观任务打分——回复同理心、报告论证严谨度。为什么代码判不了？因为「同理心」没有标准答案，什么叫「足够同理」因人而异，只能人去感受。
3. 诊断通过率异常——0% 或 100% 通常不是模型弱，是任务定义或评分器坏了。为什么必须人介入？机器不会质疑自己——一个空壳评分器可能永远给满分，只有人看一眼分布图才会发现「这数字太干净了，不对」。
4. 建立 ground truth——新套件上线的前 20-50 个参考解。为什么是前 20-50 个？因为评测集刚建的时候一道题都没有标准答案，必须先攒一批人工确认的「正确答案」才能启动后面的自动化流程。
5. Trace 采样审查——每周抽一批完整执行轨迹读一遍，找隐藏失败模式。为什么机器发现不了？因为 Trace 审查要找的不是「哪步出错了」，而是「表面都对了但推理在某个环节悄悄走歪了」——这种只有人逐行读思维链才能发现。
6. 高风险兜底——医疗、金融、安全的结论 100% 人工复核。为什么不能信任模型？因为模型幻觉不可预测，在零容忍的领域，任何自动判定的结论都可能是一个看起来自信的瞎编。

**五大维度里的过程质量怎么评？**

这是 P1，不是 P0 不代表不重要——它恰恰最能体现 agent 的「智能」水平。五个子维度：推理合理性（思考链是否自洽）、步骤最优性（有没有走不必要的弯路，跟参考解法比步数比）、信息完整性（输出是否覆盖了任务所需全部关键信息）、上下文利用率（给的信息有没有充分利用）、自我纠错能力（遇到错误能不能识别并修正）。这五个全是模型评分的主战场，代码判不了。

### 追② · 评分规则与用例设计

**负分制具体怎么算？**

满分 100，扣分制。结果维度：任务结果和预期不符，直接扣 100，这道题废了。过程维度：步骤没按预设工作流走、中间输出不对、调了不该调的或漏了该调的工具，每一项扣 10。效率维度：基准 5 分钟，超时每多 1 分钟扣 10。稳定性：同一道题跑 N 次（建议 N=5），全部达标取平均分，任何一次不达标这道题整体判不通过。最后输出的不只是分数——是每次扣分的 JSON 明细 + HTML 报告，方便追溯「为什么扣」。

**用例设计的四个场景怎么落地？**

场景一，触发条件——验证 agent 在该触发时触发、不该触发时别瞎触发。负向用例尤其重要：只测正例，agent 可能学会什么 prompt 都触发，过度触发比不触发更难发现。

场景二，核心逻辑——用例量最大的场景，通常是其他三类之和的 2-3 倍。做法是三步法：先画 Skill 的所有分支流程图，再每条分支至少一个用例（正向），最后补组合和边界。比如性能分析 Skill，单用例 CPU 分析、多用例对比、瓶颈结论、正常结论、压测无效——每条路径一个用例。

场景三，产物质量——文件存不存在、内容完不完整、格式对不对。正向测完整，负向测不编造、不泄露。

场景四，异常容错——不存在的 ID 明确提示「不存在」，非法格式提示格式错误，信息不足主动追问而不是瞎猜，工具故障优雅降级而不是死循环。

### 追② · 能力测评 vs 回归测评

**为什么要分两套？**

因为测评的目标随 agent 生命周期变化。能力测评问的是「agent 能把什么做好？」——起步通过率可能只有 20-50%，它是目标山峰，指导优化方向，频繁迭代、主动拓展。回归测评问的是「原有能力还在不在？」——期望接近 100% 通过，防御漂移，保住既有阵地，只增不减、CI 每次运行。

生命周期转化：能力测评通过率稳定 100% 后，用例「毕业」到回归套件，从此每次 CI 都跑。回归用例只加不减。根据 Anthropic 的推荐，确定性任务通过率需要 100%，非确定性推荐 ≥ 95%。

跟传统测试最大的不同：能力测评和 agent 开发是同步启动的，不是开发完再补。开发之初就定评测集，开发过程中不断跑评测，用结果反过来优化 agent。

### 追② · 基线管理

**基线是什么？怎么建？**

基线是一个用例执行一次后，人工确认正确的过程和结果的完整快照。它回答：「这个用例，正确的执行应该长什么样？」分为两部分——预期过程：思维链（推理过程、决策依据）、工具调用序列（调了什么、顺序、入参、返回值）、中间产物（临时文件、API 响应）；预期结果：最终响应文本、输出文件、输出报告。

建立流程：设计阶段只定义 prompt 和检查规则，不需要手写预期。执行一次后，人工审核过程是否合理、结果是否准确——不可接受就修 agent 重跑，确认后这次快照就是基线。

**基线在评分里怎么用？**

后续每次测评执行，拿本次的过程和结果跟基线对比。确定性评分用基线做程序化判定——工具调用序列是否一致、产物文件是否存在、token 数是否超标。模型评分用基线做参考答案，对比本次产出与基线的语义差异，按维度打分。

**什么时候更新基线？**

agent 逻辑变更、模型版本升级、用例本身修改——这三种情况都可能让预期过程或结果变化，都要重新执行一次并确认新基线。

### 追③ · 三层对象 & 评测集与 gold set 的关系

**三层对象怎么区分？**

最底层是产品本身——那个网页、主流程——这是我 agent 的工作对象，不是评测对象。产品稳不稳是产品的事，跟评测体系没关系。中间层是我的测试 agent——写用例、跑、自愈、出报告——评测集考它干的活对不对。最上层是模型裁判——给 agent 的活打分的那个 LLM——gold set 考它判得准不准。

最常见的乱是把产品和 agent 搅在一起。问「它是测产品主流程稳不稳吗」——不是。评测集考的不是产品，是 agent 交出来的活对不对。

**评测集和 gold set 什么关系？**

评测集里的题考 agent。一道题里有多个裁判——比如自愈那道题，四个裁判里前三个是代码判（沙箱重跑、AST、唯一性），只有第四个「修复语义合不合理」是模型在判。gold set 只建给这一个裁判用：抓几十条语义判定的记录，找三个人各自独立打分、不许商量，这几十条带人类标注就成了考这个模型裁判的卷子。裁判跑一遍 gold set，看它跟人类标注的吻合度——用 kappa 系数，扣掉「瞎蒙也能蒙对一半」的水分。够准才让它上岗去给几百道评测题打语义分。

纪律：gold set 跟着「模型判」走，不跟着「段」走。哪一段冒出了模型当裁判，哪一段就配 gold set。能代码判到底的段，一律不碰 gold set。昂贵的人类标注只花在消不掉的主观那一点上。

### 追④ · 自愈纵深

**自愈率 83% 怎么来的？**

第一版只有 60%。不是在换模型上使劲，是挂了一份组件库定位知识包给 agent。agent 在原始页面结构上瞎猜锚点，不懂自研组件库的门道。几个真坑：弹窗渲染被 Vue teleport 挂到页面末尾，不在触发它的结构里，agent 在原地找永远找不到；表格稳定锚点是每行业务主键，按「第几个子元素」定位的话虚拟滚动一滚就偏；下拉选项用到才渲染，不展开根本不存在。涨到 83%，多出来那二十几分不是我换模型换出来的，是我把组件库的定位约定整理成知识包喂进去的。

**三道闸门怎么演进的？**

防作弊那道语法树闸门踩了三版。第一版文本匹配——在文件里搜断言关键字，被注释和字符串里的关键字骗到。第二版手写解析器——不健全，被人一句「它解析得了 Vue 吗」问破。第三版换 swc 把代码解析成 AST，按节点角色判——定位语句的节点允许改，但一流进断言节点（`expect` 调用内部的期望值和匹配方式）就锁死。这是「约束要在执行前生效、不能只靠提示词」最实在的例子。

**自研组件库为什么是双刃？**

本钱在上面——我拿得到定位门道，所以自愈率高。风险也在上面——第三方库升级能控节奏，自研库动一个基础组件，全公司脚本可能一夜同时红。所以当最高变更等级管：每个 PR 强制跑回归集当门禁、先量影响面；定位门道表跟着组件库版本走、升级必同步；破坏性结构变更走灰度。

### 追⑤ · 评测的统计本质

**「有纪律的赌」是什么意思？**

评测经常被讲成从代码判到模型判到人类共识、严丝合缝的逻辑闭环——这是错的。真相是你永远没法证明一个自动裁判是对的，你只能拿一批人类判断当尺子，量出它错多少，然后赌这批尺子能代表真实情况。

三个常见困惑从这个根基解开：评测起什么作用？它不让 agent 变对、不让裁判变对，只做一件事——把「不知道有多大、没边界的风险」换成「量出来了、有边界的错误率」。几十条 gold set 凭什么撑起百万次判决？因为这是统计归纳，前提是那批样本从真实流量里同分布抽出来的——分布外的裁判照样会错，而且你不知道。承认这道「代表性假设」的缝恰恰是专业的标志——业余的假装没缝，专业的指着缝说我能用 kappa 和误差范围量出它有多宽。人类共识哪有那么干净？人判不齐的地方（kappa 低），正确做法不是硬凑，是把这道题扔掉，承认这块我量不了。

**稳定性评估和 pass^k 什么关系？**

pass^k 指 k 次试验每次都通过的概率，衡量稳定性。pass@k 是 k 次中至少一次通过，衡量峰值能力。评测用前者，因为一次偶发成功没有意义——要的是稳定可靠。

容忍阈值按 agent 使用类型分级：关键决策类（问题定位、故障诊断）——0%，任何一次失败都不可接受，因为它可能导致误判；辅助分析类（性能分析、报告生成）——≤ 10%，偶发偏差可接受但持续观察；创意生成类（代码建议、文案）——≤ 40%，多样性本身是特性，关注核心逻辑正确性。

如果 N 次试验一次都不过（0% pass^N），通常不是 agent 能力不行，是任务定义有问题——先查用例描述有没有歧义、评分器有没有配错、成功标准合不合理。

### 追⑤ · 其他四段怎么评

**编写段：**

对 = 该测的测了、不是空壳、能抓真 bug。客观：断言非空壳（AST）、好代码上跑绿（不误报）、退回到 bug 还没修的版本跑应该报错（证明真能抓，不是刷覆盖率的空壳）。主观：全新功能没有历史 bug 可回放时，「该测什么、够不够全」上模型判。

**历史整合段：**

对 = 该复用的复用了、原有覆盖没缩水、没把不同的错并、断言没丢。客观：合并后原有断言一条不少（集合比对）、整套仍然跑绿、覆盖需求集合没变小、无重复用例。主观：「这两条该不该合成一条」这类判断题上模型。

**执行段：**

对 = 该跑的真跑了、没漏跑、结果稳定、归因准。客观：看结果列表有没有漏跑、同输入多次跑结果是否一致。主观：flaky 归因——这次挂到底是真 bug 还是环境噪声、时序竞态，上模型判。

**报告段：**

对 = 事实对、该报的没漏、措辞不误导。客观：报告里的数字和执行结果结构化字段比对（防幻觉编数字）、该列的失败用例一条不少。主观：根因摘要写得准不准、有没有抓住重点。
